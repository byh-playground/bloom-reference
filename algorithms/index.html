구체 개발규칙
알고리즘 레퍼런스

게임 개발 중 문제가 생겼을 때 어떤 알고리즘을 검색하고 선택할지 빠르게 찾는 실전 위키. 이미 사용한 기술·비교만 해본 기술·도입 후보를 구분합니다. 각 항목의 작동 원리 → 3단계 흐름 → 실제 예시를 읽고, 가장 큰 실행 비용 절감 기회부터 살펴봅니다.

0총 기술 항목
0MECE 분류
0확인된 적용
0P0 절감 후보
범위: RALLY FRONTIER · BLOOM GameKit · Budmori.io · Rollback Netcode · 프로토타입 / 이 문서는 운영 코드를 직접 변경하지 않습니다.
01

비용 최적화 우선순위

분류는 기술의 책임으로 MECE하게, 우선순위는 같은 환경에서 절감 가능한 총 실행 비용으로 판단합니다. P0도 조건이 맞지 않으면 P1보다 효과가 작을 수 있습니다.

P0 구조적 절감O(N²) 제거, 전체 반복 삭제, 대량 재사용 등
P1 큰 비용 절감중복 계산·할당·Draw Call·전송 비용 대폭 감소
P2 조건부 절감특정 입력·장면·기능에서 유효
P3 미세 개선기타 대안·정밀 튜닝; 필요 시 추가
우선 비교 식   총 비용 ≈ 호출 수 × 호출당 비용 + 할당/GC + GPU/전송 비용
Big-O는 후보를 고르는 기준이며, 최종 결정은 실제 CPU 총시간·p95/p99 지연·메모리·복구 비용·권위 상태 동등성으로 검증합니다.
상세 항목 읽는 법   원리는 핵심 아이디어, 흐름 ①~③은 실제 데이터가 처리되는 순서, 예시는 RALLY/BLOOM 상황에서의 사용 모습을 뜻합니다. Big-O는 조건에 따른 예상 계산량이며 실측 속도를 보장하지 않습니다.
탐색 기준우선 확인주의할 점
시간복잡도O(N²) → O(NK) / O(Nlog N)최악·평균·상각 조건을 명시
중복 계산공통 목표 캐싱 · 증분 갱신 · 빈도 조정캐시 만료와 결정론 보장
연속 작업Allocation · Snapshot · GPU BufferGC 및 수명·alias 검증
실제 게임같은 Seed, TPS, 객체 수, 브라우저에서 비교속도만이 아니라 결과·순서 동등성

표기: N = 객체 수 · K = 가까운 후보 수 · P = 충돌 후보 쌍 수 · V/E = 그래프 정점/간선 수 · I = 반복 수 · S = 상태 크기 · D = 표시 객체 수 · Δ = 변경량. Big-O는 데이터 분포와 구현에 따른 전제조건이 있습니다.

02

알고리즘 빠른 색인

기술명·영문 검색어·작동 원리·적용처·대안을 한 번에 검색합니다. 비용 절감 우선 정렬이 기본값이며 이름을 누르면 해당 상세 항목으로 이동합니다.

검색 준비 중

검색 결과가 없습니다. 범위를 넓히거나 다른 영문 키워드를 입력해 보세요.
03

분류별 상세 설명

기술 이름을 누르면 핵심 원리 → 3단계 처리 흐름 → 게임 예시 → Big-O와 선택 기준을 한눈에 확인할 수 있습니다. 구현 코드는 생략하고 구조가 이해되도록 설명합니다.

상태를 구분하세요. 확인: 현재 저장소 문서·테스트에서 확인 / 사용 경험: 이전 프로토타입에서 사용 / 실험: 비교 평가만 수행 / 후보: 적용은 미확인. 이 위키는 실제 게임 코드의 적용·성능을 과장하지 않습니다.
04

출처 · 확장 원칙

같은 기술을 여러 카테고리에 중복 기록하지 않고, 기존 항목의 대안·키워드로 연결합니다. 기술 추가 필수 요소는 정식 명칭 / 핵심 원리 / 처리 흐름 / 실제 예시 / Big-O / 선택 조건 / 단점 / 상태 / 검색 키워드입니다.

RALLY 구현·경로 실험 ↗GameKit 공통 SDK ↗SAP 비교 보고서 ↗Rollback 계약 ↗Red Blob · A* ↗Box2D · Collision ↗Rapier · Joints ↗WebGL Instancing ↗
특별 기록 — SAP 도입 비교
RALLY FRONTIER는 Grid + Adaptive SAP를 서로 다른 목적에 사용 중. Budmori.io의 SAP 비교에서는 현재 Grid 충돌 순서·후보 제한을 바로 대체할 확실한 이득이 입증되지 않았음. 충돌 방문 순서를 바꾸면 최종 위치도 달라질 수 있다. 따라서 Big-O뿐 아니라 후보·순서·전체 틱을 함께 비교한다.

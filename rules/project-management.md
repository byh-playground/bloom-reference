> [!NOTE] **가장 중요한 원칙**
> 관리 체계가 프로젝트보다 복잡해지지 않게 한다. 기본값은 **메인 버전 하나, Stable 하나, 불필요한 호환 계층 없음**이다.

## 문서 범위 {#scope}

이 문서는 **개발 외 프로젝트 운영 규칙**만 다룬다. 코드 스타일·알고리즘·렌더링·구체 구현 방식은 별도 개발 규칙에서 관리한다.

| 이 문서에서 관리 | 별도 개발 규칙에서 관리 |
| --- | --- |
| 버전, Stable, 기준본, 마이그레이션, Git/PR, 배포, 전달, 검증 기록, 핸드오프, README 역할 | 코드 스타일, 자료구조, 알고리즘, 렌더링, 성능 구현, 클래스/믹스인 설계, 구체 기술 선택 |

## 버전 규칙 {#version}

> [!IMPORTANT] **최상위 규칙**
> **MAJOR는 제품 세대, MINOR는 비호환 변경, PATCH는 호환 변경.**

기본 버전은 프로젝트 전체를 대표하는 **하나의 메인 버전**이다.

```text
MAJOR.MINOR.PATCH
예: 0.8.3 / 1.0.0 / 1.4.2
```

### MAJOR — 제품 생애주기 / 세대 {#version-major}

MAJOR는 기술적인 Breaking Change 횟수가 아니다. 제품 자체의 큰 생애주기나 세대를 표현한다.

- `0.x.x` — 개발 / 알파 / 베타
- `1.x.x` — 최초 정식 릴리즈
- `2.x.x+` — 제품 자체가 다음 세대로 넘어갔다고 판단할 수준의 큰 전환

프로토콜·API·저장 포맷·렌더러·내부 아키텍처가 깨졌다는 이유만으로 MAJOR를 올리지 않는다.

### MINOR — 호환되지 않는 변경 {#version-minor}

> [!TIP] **판정 질문**
> 기존 버전과 그대로 함께 사용할 수 있는가? **아니라면 MINOR.**

- 네트워크 프로토콜 비호환 변경
- 저장 포맷 비호환 변경
- API / 인터페이스 계약 변경
- 외부 데이터 구조 비호환 변경
- 기존 Consumer를 수정해야 하는 변경
- 기존 사용 방식이 깨지는 마이그레이션

예: `0.7.5 → 0.8.0`. MINOR를 올리면 PATCH는 `0`으로 초기화한다.

### PATCH — 호환되는 변경 {#version-patch}

> [!TIP] **판정 질문**
> 기존 계약과 사용법을 그대로 유지하는가? **그렇다면 PATCH.**

- 버그 / 회귀 수정
- 성능 최적화
- 호환되는 UX·VFX 개선
- 밸런스 조정
- 기존 API를 유지하는 기능 보완

예: `0.8.0 → 0.8.1`.

### 버전을 올리지 않는 변경 {#version-none}

모든 커밋마다 PATCH를 올리지 않는다. 사용자 동작이나 외부 계약에 의미 있는 변화가 없다면 버전을 유지한다.

- 순수 리팩터링
- 변수명·내부 이름 정리
- Dead Code 제거
- 문서·주석 수정
- 테스트 추가·정리
- CI / 포맷팅 / 내부 파일 구조 정리

### 버전 판정 순서 {#version-decision}

- [PM-001][-] 버전 판정은 제품 세대 변경 → MAJOR, 비호환 변경 → MINOR, 호환되는 의미 있는 변경 → PATCH, 외부 동작·계약이 같은 내부 정리 → 버전 유지 순서로 한다. 위반 판별: 순수 리팩터링·문서 수정에 PATCH를 올렸거나, 비호환 변경에 PATCH만 올렸다.

1. 제품 세대 자체가 바뀌는가? → **MAJOR**
2. 기존 버전과 호환되지 않는가? → **MINOR**
3. 호환되는 의미 있는 변경인가? → **PATCH**
4. 외부 동작·계약이 동일한 내부 정리인가? → **버전 유지**

## 별도 버전 최소화 {#version-split}

- [PM-002][-] 기능·모듈별 별도 버전을 만들지 않고 메인 버전 하나만 둔다. 런타임 호환성 판정에 반드시 필요한 기술 식별자만 메인 버전과 분리해 둔다. 위반 판별: Consumer가 없는 `*_VERSION` 상수가 있다.

기능·모듈·서브시스템마다 별도 버전을 만들지 않는다. 기본적으로 프로젝트에는 **메인 버전 하나**만 존재한다.

`SIM_VERSION`, `NETWORK_VERSION`, `PROTOCOL_VERSION`, `SCHEMA_VERSION`, `SAVE_VERSION` 같은 값은 습관적으로 만들지 않는다.

> [!IMPORTANT] **예외**
> 실제 런타임에서 독립적인 호환성 판정이 반드시 필요한 경우에만 기술용 식별자를 둔다. 이 값은 사용자에게 보이는 메인 버전과 분리한다.

## BUILD_ID {#build-id}

`BUILD_ID`는 버전 번호가 아니라, **같은 버전 안의 특정 산출물을 추적하기 위한 식별자**다.

```text
Version: 0.8.2
Build: 20261007T193500+0900-a1b2c3d
```

파일명 숫자만으로 최신 여부를 판단하지 않는다. 제품 상태는 Version, 특정 결과물 추적은 BUILD_ID나 커밋으로 구분한다.

## SSOT · 최신 기준본 {#ssot}

- [PM-003][-] 작업 시작 시 기준본은 사용자 지정본 → 현재 Stable → 최근 Validated → Candidate 순서로 하나만 확정하고, 기억보다 실제 저장소·커밋 상태를 우선한다. 위반 판별: 기준 커밋·태그를 적지 않고 작업을 시작했다.

작업 시작 시 베이스는 하나로 확정한다. 중간본·실패본·과거 후보본이 암묵적으로 새 기준이 되지 않게 한다.

1. **사용자가 명시적으로 지정한 기준본**
2. 현재 **Stable**
3. 가장 최근 검증 완료된 **Validated**
4. 그 외 Candidate

과거 파일명이나 기억보다 **실제 저장소·파일·BUILD_ID·커밋 상태**를 우선한다.

## 마이그레이션 기본 정책 {#migration}

- [PM-004][-] 마이그레이션은 구 구조를 새 구조로 교체하고 구 참조·호환 계층·Legacy를 정리해야 완료다. 호환 계층은 대상·Consumer·사유·범위·제거 조건을 적은 명시적 예외만 둔다. 위반 판별: 요청 없는 fallback·adapter·alias가 남아 있다.

> [!IMPORTANT] **교체 후 정리, 호환은 명시적 예외**
> 마이그레이션은 기본적으로 새 구조를 덧붙이는 작업이 아니라 **구 구조를 새 구조로 교체하는 작업**이다.

사용자가 요청하지 않은 하위 호환 계층을 임의로 남기지 않는다.

| 기본 제거 대상 | 남기지 않는 이유 |
| --- | --- |
| legacy path / fallback | 신·구 경로 이중화로 실행 경로가 복잡해짐 |
| compatibility adapter / bridge / alias | 실제 Consumer가 없으면 유지비만 증가 |
| deprecated wrapper / 구 API forwarding | 새 구조 정착을 방해하고 잘못된 사용을 계속 허용 |
| 옛 설정 분기 / migration shim | 현재 포맷의 SSOT를 흐림 |

“혹시 나중에 쓸 수도 있어서”, “지우기 불안해서”, “과거에 사용했기 때문에”는 호환 계층 유지 사유가 아니다.

### 호환 계층은 명시적 예외 {#compat-exception}

호환을 유지한다면 최소한 다음이 명확해야 한다.

- 무엇과의 호환인가
- 실제 Consumer가 무엇인가
- 왜 유지해야 하는가
- 어디까지 유지하는가
- 제거 조건은 무엇인가

이 조건이 없다면 현재 구조로 완전히 전환한다.

### 마이그레이션 완료 기준 {#migration-done}

```flow
새 구조 구현 → Consumer 이전 → 구 참조 제거 → 호환 계층 제거 → Legacy / Dead Code 제거 → 검증
```

> **마이그레이션 완료 = 새 구조 적용 + 구 구조 정리.**

## Candidate · Validated · Stable {#states}

| 상태 | 의미 | 완료 조건 |
| --- | --- | --- |
| Candidate | 개발 중이거나 검증 전인 결과물 | 구현이 끝났어도 검증 전이면 Candidate |
| Validated | 정해진 검증 기준을 통과한 결과물 | 정적 검사뿐 아니라 프로젝트에 필요한 실제 실행 검증 완료 |
| Stable | 다음 작업·배포의 공식 기준선 | Validated 중 기준본으로 승격된 결과물 |

```flow
Working → Candidate → Validated → Stable
```

## Stable 승격 {#stable}

Stable은 단순히 “가장 최신 코드”가 아니라 **검증 완료된 공식 기준선**이다.

변경 성격에 맞는 실제 실행과 고정 사용자 시나리오 E2E를 수행하며 [검증 정책](#verification)을 따른다. 실제로 하지 않은 검증은 PASS로 기록하지 않는다.

### 릴리즈 태그 · HTML 프리뷰 배포 {#tag-preview}

- [PM-005][-] 전시용 릴리즈는 Git 태그가 가리키는 HTML 스냅샷을 직접 프리뷰한다. Nightly는 `main` 푸시마다 자동 태그이고, Stable은 커밋 SHA·제품 버전·검증 승인을 명시할 때만 만들며, 과거 태그를 재지정·삭제하지 않는다. 위반 판별: 태그를 다른 커밋으로 옮겼거나 Nightly를 Stable로 표시했다.

> [!IMPORTANT] **공통 원칙**
> 게임 전시용 릴리즈는 **각 Git 태그가 가리키는 시점의 HTML 스냅샷**을 직접 프리뷰한다. Stable/Nightly용 배포 브랜치·저장소·고정 URL을 별도로 만드는 것은 필수가 아니다. **한 게임이 두 채널을 동시에 가질 수 있다.**

| 채널 | 태그 예시 | 생성·공개 기준 |
| --- | --- | --- |
| Stable | `v0.28.14` | [Validated 검증과 승인](#stable)을 마친 동일 산출물에 고유 태그 부여. 기존 Stable 기준선을 임의로 교체하지 않는다. |
| Nightly | `nightly-20261024T030149Z-8846ed24be89` | 개발 중 새 HTML 스냅샷이 생성되면 고유 태그를 자동 발행한다. 실행·플레이·회귀 검증은 발행 조건이 아니며 실행 실패, 미완성 기능, 버그를 허용한다. |

Nightly는 Candidate/Validated/Stable과 같은 **품질 등급이 아니라 공개 채널**이다. Nightly 태그 생성만으로 검증 완료·Stable 승격으로 간주하지 않는다. Nightly 변경이 Stable 배포를 자동 갱신하지 않는다. 두 채널 모두 과거 태그를 재지정·삭제하지 않고 새 태그로 갱신한다.

**실제 운영:** 공통 [태그 발행 워크플로](https://github.com/byh-playground/bloom-reference/blob/main/.github/workflows/game-release-tags.yml)를 게임 저장소에서 불변 커밋으로 참조한다. `main` 푸시마다 `nightly-YYYYMMDDTHHMMSSZ-SHA12` 고유 태그를 자동 발행하며 별도 플레이 검증을 발행 조건으로 두지 않는다. Stable은 `workflow_dispatch`에서 **전체 커밋 SHA·제품 버전·검증 승인**을 명시할 때만 생성한다. 동일 태그 재발행은 같은 커밋이면 멱등 처리하고, 다른 커밋으로는 절대 이동하지 않는다.

적용 전시 사이트: [BLOOM PLAYGROUND](https://byh-playground.github.io/bloom-world/playground/). 태그 조회 실패·미등록은 Stable로 추정하지 않으며, Nightly 프리뷰 오류를 숨기지 않는다.

#### 태그가 담아야 하는 파일

- **기본 진입점은 태그 루트의 `index.html`이다.** 추가 JS/CSS/SVG/WASM 등 파일이 필요하면 같은 태그 스냅샷에 포함하고 상대 경로가 그 스냅샷 안에서 해결되도록 한다. 단일 HTML에 내장해도 된다.
- 외부 SDK·CDN 의존성은 불변 버전·커밋으로 고정한다. 가변 `main`/`latest`를 참조해 과거 태그의 동작이 바뀌게 하지 않는다.
- **원본 소스를 그대로 실행·배포한다.** `index.html`과 필요한 JS·CSS·자산을 같은 소스 커밋에 포함하고 브라우저에서 직접 실행한다. 게임 실행물을 생성·번들링·변환하는 빌드 단계나 별도 배포용 커밋은 두지 않는다. CI 검사는 문법·린트·정적 참조 검사 등 정적 검사로 한정하며, Pages에는 원본 파일을 그대로 게시한다.
- HTML 파일이 없거나 자산 경로가 누락되면 **프리뷰를 제공할 수 없음**으로 표시한다. 특히 Nightly는 HTML이 존재한다는 사실만으로 정상 작동을 보장하지 않으며, 깨진 최신 빌드를 Stable이나 과거 Nightly로 몰래 바꿔 보여주지 않는다.

#### 전시 사이트의 채널·실행 계약

- 사이트의 상단 탭은 **전체 게임 / Stable / Nightly**로 구분한다. 작품 목록은 게임 단위로 중복 없이 표시하며 해당 채널의 태그가 없는 게임은 그 탭에서 제외한다.
- 플레이 버튼은 현재 탭의 태그를 실행한다. **전체 게임에서는 Stable 우선, Stable이 없으면 Nightly**를 선택한다. 상세 화면에서는 채널을 바꿀 수 있다.
- 태그를 조회해 채널별 최신 릴리즈를 선택하고, **리포지토리·태그·`index.html` 경로**로 프리뷰 URL을 구성한다. 제품 버전은 기존 버전 규칙을 따르고, Nightly 날짜·커밋 식별자를 별도 제품 버전으로 취급하지 않는다.
- Nightly 실행 전 **“개발 중인 버전으로 정상 작동을 보장하지 않습니다”**를 표시한다. 실행 실패 시 프리뷰 이용 불가 또는 오류 상태를 숨기지 않는다.

#### 프리뷰 호스팅과 한계

GitHub의 원본 파일 주소는 브라우저용 HTML/JavaScript 호스팅이 아니다. 예를 들어 [GitHack](https://raw.githack.com/)의 불변 태그 CDN URL은 `https://rawcdn.githack.com/<owner>/<repo>/<tag>/index.html` 형태로 만들 수 있다. **태그 자체가 웹서버인 것은 아니며** MIME·상대 파일·CORS·보안 정책을 충족하는 HTTPS 제공자가 필요하다.

GitHack은 HTML 첫 진입에서 확인 화면이 나올 수 있고 무료 서비스라 가용성을 보장하지 않는다. 서비스 장애나 게임별 리소스 제약이 생기면 해당 프리뷰만 이용 불가로 안내하거나 별도 검증된 호스팅 URL을 사용할 수 있다. 기존 GitHub Pages Stable 주소는 유지 가능하지만 **전시용 태그마다 별도의 Pages 배포를 의무화하지 않는다.** 실제 브라우저 실행 여부는 게임별로 검증한 범위만 표기한다.

## Git 운영 {#git}

- [PM-006][-] 작업 브랜치에서 `main` 대상 PR을 만들고, 검증을 마친 PR은 별도 승인을 묻지 않고 머지한다. 작업 전 실제 Git 상태를 확인하고, 병합된 PR·Draft·CI 실패 상태를 Stable로 착각하지 않는다. 위반 판별: 검증이 끝난 PR의 머지를 질문으로 미뤘거나, Git 상태 확인 없이 브랜치를 만들었다.

- `main`은 변경을 통합하는 개발 브랜치이며, 각 푸시의 소스 스냅샷을 Nightly로 공개한다. Stable의 공식 기준선은 검증·승인한 불변 태그가 가리키는 커밋이다.
- Candidate와 Stable을 혼동하지 않는다.
- PR/브랜치 작업 전 실제 Git 상태를 먼저 확인한다.
- 이미 병합된 PR, 오래된 커밋, Draft 상태, CI 실패 상태를 Stable로 착각하지 않는다.

## 커밋 메시지 {#commit}

- [PM-007][-] 커밋 메시지는 한국어로 쓰고, 첫 줄에 `[bug-fix]`·`[feature]`·`[refactor]`·`[performance]`·`[docs]`·`[test]`·`[build]` prefix와 변경 목적을 적는다. 위반 판별: prefix가 없거나 첫 줄에 목적이 없다.

기본적으로 한국어를 사용하고 변경 목적이 즉시 보이게 작성한다.

```text
[bug-fix] 싱글 시작 오류 수정

- 캠페인 초기화 과정에서 발생하던 예외 수정
```

대표 prefix: `[bug-fix]`, `[feature]`, `[refactor]`, `[performance]`, `[docs]`, `[test]`, `[build]`

## 라이브러리 · Consumer 관리 {#consumer}

공통 라이브러리와 이를 사용하는 게임은 서로 다른 변경 단위로 본다.

```flow
공통 라이브러리 변경 → 라이브러리 검증 → 기준본 확정 → 각 Consumer에서 명시적 업데이트
```

라이브러리가 바뀌었다는 이유만으로 모든 Consumer를 자동으로 동시에 수정하지 않는다.

## 결과물 전달 {#delivery}

- [PM-008][-] 최종본으로 전달하는 파일은 검증이 끝난 것이어야 하고, Nightly·중간본은 미검증 상태를 명시할 때만 공개한다. 위반 판별: 검증 기록 없는 파일을 최종본으로 전달했다.

사용자에게 최종 결과물처럼 전달하는 파일은 검증이 끝난 결과물이어야 한다.

[Nightly 프리뷰](#tag-preview)는 최종본 전달과 구분하여 **개발 중·미검증 상태**를 명시할 때만 공개한다.

- 중간본·부분 구현본·실패 후보본·검증 전 파일을 최종본처럼 전달하지 않는다.
- 내부 Candidate는 여러 개 만들 수 있지만 최종 전달은 가능한 한 하나로 정리한다.
- 최종 전달 시 파일/커밋, 메인 버전, 필요 시 BUILD_ID, 기준 베이스, 주요 변경, 검증 결과를 남긴다.

## 검증 정책 · 배포 기록 {#verification}

### 개발 중 검증과 영구 시나리오를 구분 {#verification-policy}

- [PM-009][-] 단위 테스트는 개발 중 임시 검증에만 쓰고 완료 시 실행 목록에서 제거하며, 영구 테스트는 고정 사용자 시나리오 E2E만 유지한다. 한 번의 버그 검증 실행 전체는 180초를 넘기지 않고, 벤치마크는 별도 명령으로 분리한다. 위반 판별: 버그마다 회귀 테스트가 누적되거나, 검증 실행이 180초를 넘는다.

- **단위 테스트는 기능 개발 중 임시 검증에만 사용한다.** 작업 완료 시 테스트 실행 코드와 실행 목록에서 제거한다. 실행 결과는 해당 PR·검증 기록에 남길 수 있지만 회귀 파일로 계속 쌓지 않는다.
- **영구 테스트는 고정 사용자 시나리오 기반 E2E만 유지한다.** 입력 → 플레이 → 전환 → 저장·복구처럼 실제 사용 흐름과 관찰 가능한 결과를 검증한다. 내부 함수명·자료구조·중간 수치에 맞춘 단위 검사를 E2E라는 이름으로 옮겨 남기지 않는다.
- 구현을 바꿔도 같은 사용자 흐름의 기대 동작은 유지한다. 새 사용자 흐름이 실제로 추가되면 그 시나리오를 추가하며, 발견한 버그마다 별도 회귀 테스트를 누적하지 않는다.
- **한 번의 버그 검증 실행 전체는 3분(180초)을 넘기지 않는다.** 필요한 고정 시나리오를 선택하고 시간 초과·미실행 범위는 실패 또는 미검증으로 기록한다. 제한을 피하려고 성공 처리하거나 상한을 늘리지 않는다.
- **성능·부하·할당 벤치마크는 별도 명령으로 분리한다.** 버그 검증의 기본 실행 목록에 섞지 않으며 목적에 맞는 측정 시간을 사용한다. 벤치마크의 비교 조건·환경·관찰값을 기능 검증 결과와 구분한다.

이 절이 검증 정책의 원본이다. 저장소 README·AGENTS는 이 정책을 참조하고 해당 저장소의 실행 명령·시나리오 범위만 안내한다. 배포에 필요한 실제 빌드·산출물 검증은 테스트 파일 보존과 별개다.

### 검증한 의존성과 실패 단계를 기록 {#verification-evidence}

- [PM-010][-] 검증 기록에는 환경(커밋·브라우저/기기·로드한 라이브러리·mock/fallback 여부), 실패 단계, PASS·FAIL·미실행·환경 차단 범위를 적고, mock·소프트웨어 renderer 통과를 실제 경로의 성공으로 보고하지 않는다. 구현 완료·검증 완료·Stable 승격·배포 완료를 같은 것으로 취급하지 않는다. 위반 판별: 미실행 범위 없이 전체 PASS로 보고했다.

**실제 의존성·mock·fallback을 구분한다.** 대체 응답이나 소프트웨어 renderer로 통과한 검사를 실제 서비스·GPU 경로의 성공으로 보고하지 않는다. 실제 RTC 연결을 검증했다면 signaling, peer 연결, 데이터 송수신, 게임 흐름 중 어디까지 확인했는지 기록한다. 로컬 loopback·전송 mock만 통과한 결과는 실제 RTC 검증이 아니다.

- 환경: 실행물 커밋, 브라우저/기기, 실제로 로드한 라이브러리와 버전, backend/renderer, mock·fallback 사용 여부.
- 실패: 의존성 로드 → 초기화 → 연결 → 입력 → 화면/상태 결과 중 실패한 단계와 관찰 증거. 환경 차단과 제품 결함을 구분한다.
- 범위: PASS·FAIL·미실행·환경 차단을 각각 표시한다. 뒤 단계까지 실행하지 못했다면 앞 단계 성공으로 전체 성공을 선언하지 않는다.

시각·모바일 변경은 [UI/UX 확인 기준](visual-ux.html#verification), 수치 변경은 [STAT 계약](stats.html), 지형 변경은 [생성·이동 가능성 검증](../algorithms/terrain-generation.html)과 연결한다. 이 항목은 위 실행 상한과 테스트 보존 정책을 대체하지 않는다.

다음 상태를 서로 같은 것으로 취급하지 않는다.

```flow
구현 완료 ≠ 검증 완료 ≠ Stable 승격 ≠ 배포 완료
```

파일 생성은 배포 완료가 아니며, CI 실행은 검증 성공을 의미하지 않는다. **실제 결과**를 기록한다.

## 롤백 {#rollback}

- 롤백 대상은 명확한 기준본으로 지정한다.
- 파일명이 오래됐다는 이유만으로 롤백하지 않는다.
- 롤백 대상 기능과 독립적인 리팩터링·성능 개선·버그 수정·구조 정리는 가능한 한 유지한다.
- 롤백 대상에 종속된 변경은 함께 제거한다.

## 핸드오프 {#handoff}

- [PM-011][-] 작업 공간을 옮길 때는 기준본·메인 버전·커밋·완료/진행/남은 작업·중요 결정·폐기 방향·검증 결과·다음 작업 순서를 담은 핸드오프를 쓴다. 위반 판별: 요약만 있고 다음 작업 순서나 기준 커밋이 없다.

대화 또는 작업 공간을 옮길 때는 단순 요약이 아니라 **즉시 작업을 이어갈 수 있는 상태 전달**을 작성한다.

- 현재 Stable / 기준본
- 현재 메인 버전
- BUILD_ID 또는 커밋
- 완료 / 진행 중 / 남은 작업
- 중요 결정
- 폐기된 방향 및 재도입하면 안 되는 Legacy 방향
- 검증 결과
- 다음 작업 순서

새 작업에서는 오래된 기억보다 **핸드오프와 실제 저장소 상태**를 우선한다.

## 문서 역할 분리 {#docs}

- [PM-012][-] 작업 완료에는 변경된 API·사용법·실행 명령·운영 정책의 원본 문서 동기화가 포함되며, 정책 원문을 여러 문서에 복제하지 않는다. 위반 판별: 코드 변경 PR에 해당 원본 문서 갱신이 없다.

| 문서 | 역할 |
| --- | --- |
| README | 프로젝트 소개, 실행·운영 방법 |
| 개발 규칙 | 코딩, 아키텍처, 알고리즘, 구현 원칙 |
| 관리 규칙 | 버전, Stable, Git, 마이그레이션, 배포, 산출물 |
| 사용자 도움말 / Wiki | 게임 규칙과 최종 사용자 사용법 |
| 검증 기록 | 어떤 버전/커밋에서 무엇을 실제로 검증했는지 |

같은 내용을 여러 문서에 복제해 서로 다른 SSOT가 생기지 않게 한다.

**작업 완료에는 관련 문서 동기화가 포함된다.** 변경된 API·사용법·실행 명령·운영 정책의 원본을 갱신하고 오래된 설명·삭제된 경로 참조를 정리한다. 실제 검증 결과는 해당 작업 PR에 남기며 정책 원문을 여러 README에 복제하지 않는다.

## 최소 복잡성 원칙 {#complexity}

- [PM-013][-] 관리 계층(버전·호환 계층·문서·분기)은 실제 문제를 해결하는 경우에만 추가한다. 위반 판별: 사용처 없는 관리 요소가 추가되었다.

관리 체계 자체가 프로젝트보다 복잡해지지 않게 한다.

- 메인 버전 하나
- Stable 기준본 하나
- 불필요한 Compatibility Layer 없음
- 불필요한 별도 Schema / Protocol Version 없음
- 불필요한 중간 산출물 전달 없음
- 불필요한 문서 중복 없음

> 새 관리 계층은 **실제 문제를 해결하는 경우에만** 추가한다.

## 핵심 요약 {#summary}

| 영역 | 핵심 규칙 |
| --- | --- |
| 버전 | **MAJOR = 제품 세대 / MINOR = 비호환 변경 / PATCH = 호환 변경** |
| 마이그레이션 | **교체 후 정리. 호환 계층은 명시적 예외.** |
| 기준본 | 항상 하나의 명확한 Stable / SSOT에서 시작 |
| 승격 | Candidate → Validated → Stable |
| 전시 배포 | 고유 Git 태그의 HTML 스냅샷을 직접 프리뷰. Stable은 검증·승인, Nightly는 실행 보장 없음. |
| 완료 | 구현 + 시나리오 검증 + 임시 검사·Legacy 정리 + 관련 문서 동기화 |
| 복잡성 | 실제 필요가 없는 버전·호환 계층·문서·분기를 만들지 않음 |

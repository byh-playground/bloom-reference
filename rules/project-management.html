Project Management Rules

공통 프로젝트 관리 규칙

버전, 기준본, 마이그레이션, 검증, 배포, Git, 산출물, 핸드오프를 위한 공통 운영 규칙.

관리 규칙 SSOT단일 HTMLMAJOR.MINOR.PATCHCandidate → Validated → Stable
가장 중요한 원칙
관리 체계가 프로젝트보다 복잡해지지 않게 한다. 기본값은 메인 버전 하나, Stable 하나, 불필요한 호환 계층 없음이다.

1.문서 범위

이 문서는 개발 외 프로젝트 운영 규칙만 다룬다. 코드 스타일·알고리즘·렌더링·구체 구현 방식은 별도 개발 규칙에서 관리한다.

이 문서에서 관리별도 개발 규칙에서 관리
버전, Stable, 기준본, 마이그레이션, Git/PR, 배포, 전달, 검증 기록, 핸드오프, README 역할코드 스타일, 자료구조, 알고리즘, 렌더링, 성능 구현, 클래스/믹스인 설계, 구체 기술 선택

2.버전 규칙

최상위 규칙
MAJOR는 제품 세대, MINOR는 비호환 변경, PATCH는 호환 변경.

기본 버전은 프로젝트 전체를 대표하는 하나의 메인 버전이다.

MAJOR.MINOR.PATCH
예: 0.8.3 / 1.0.0 / 1.4.2

2.1.MAJOR — 제품 생애주기 / 세대

MAJOR는 기술적인 Breaking Change 횟수가 아니다. 제품 자체의 큰 생애주기나 세대를 표현한다.

  • 0.x.x — 개발 / 알파 / 베타
  • 1.x.x — 최초 정식 릴리즈
  • 2.x.x+ — 제품 자체가 다음 세대로 넘어갔다고 판단할 수준의 큰 전환

프로토콜·API·저장 포맷·렌더러·내부 아키텍처가 깨졌다는 이유만으로 MAJOR를 올리지 않는다.

2.2.MINOR — 호환되지 않는 변경

판정 질문
기존 버전과 그대로 함께 사용할 수 있는가? 아니라면 MINOR.
  • 네트워크 프로토콜 비호환 변경
  • 저장 포맷 비호환 변경
  • API / 인터페이스 계약 변경
  • 외부 데이터 구조 비호환 변경
  • 기존 Consumer를 수정해야 하는 변경
  • 기존 사용 방식이 깨지는 마이그레이션

예: 0.7.5 → 0.8.0. MINOR를 올리면 PATCH는 0으로 초기화한다.

2.3.PATCH — 호환되는 변경

판정 질문
기존 계약과 사용법을 그대로 유지하는가? 그렇다면 PATCH.
  • 버그 / 회귀 수정
  • 성능 최적화
  • 호환되는 UX·VFX 개선
  • 밸런스 조정
  • 기존 API를 유지하는 기능 보완

예: 0.8.0 → 0.8.1.

2.4.버전을 올리지 않는 변경

모든 커밋마다 PATCH를 올리지 않는다. 사용자 동작이나 외부 계약에 의미 있는 변화가 없다면 버전을 유지한다.

  • 순수 리팩터링
  • 변수명·내부 이름 정리
  • Dead Code 제거
  • 문서·주석 수정
  • 테스트 추가·정리
  • CI / 포맷팅 / 내부 파일 구조 정리

2.5.버전 판정 순서

  1. 제품 세대 자체가 바뀌는가? → MAJOR
  2. 기존 버전과 호환되지 않는가? → MINOR
  3. 호환되는 의미 있는 변경인가? → PATCH
  4. 외부 동작·계약이 동일한 내부 정리인가? → 버전 유지

3.별도 버전 최소화

기능·모듈·서브시스템마다 별도 버전을 만들지 않는다. 기본적으로 프로젝트에는 메인 버전 하나만 존재한다.

SIM_VERSION, NETWORK_VERSION, PROTOCOL_VERSION, SCHEMA_VERSION, SAVE_VERSION 같은 값은 습관적으로 만들지 않는다.

예외
실제 런타임에서 독립적인 호환성 판정이 반드시 필요한 경우에만 기술용 식별자를 둔다. 이 값은 사용자에게 보이는 메인 버전과 분리한다.

4.BUILD_ID

BUILD_ID는 버전 번호가 아니라, 같은 버전 안의 특정 산출물을 추적하기 위한 식별자다.

Version: 0.8.2
Build: 20261007T193500+0900-a1b2c3d

파일명 숫자만으로 최신 여부를 판단하지 않는다. 제품 상태는 Version, 특정 결과물 추적은 BUILD_ID나 커밋으로 구분한다.

5.SSOT · 최신 기준본

작업 시작 시 베이스는 하나로 확정한다. 중간본·실패본·과거 후보본이 암묵적으로 새 기준이 되지 않게 한다.

  1. 사용자가 명시적으로 지정한 기준본
  2. 현재 Stable
  3. 가장 최근 검증 완료된 Validated
  4. 그 외 Candidate

과거 파일명이나 기억보다 실제 저장소·파일·BUILD_ID·커밋 상태를 우선한다.

6.마이그레이션 기본 정책

교체 후 정리, 호환은 명시적 예외
마이그레이션은 기본적으로 새 구조를 덧붙이는 작업이 아니라 구 구조를 새 구조로 교체하는 작업이다.

사용자가 요청하지 않은 하위 호환 계층을 임의로 남기지 않는다.

기본 제거 대상남기지 않는 이유
legacy path / fallback신·구 경로 이중화로 실행 경로가 복잡해짐
compatibility adapter / bridge / alias실제 Consumer가 없으면 유지비만 증가
deprecated wrapper / 구 API forwarding새 구조 정착을 방해하고 잘못된 사용을 계속 허용
옛 설정 분기 / migration shim현재 포맷의 SSOT를 흐림

“혹시 나중에 쓸 수도 있어서”, “지우기 불안해서”, “과거에 사용했기 때문에”는 호환 계층 유지 사유가 아니다.

6.1.호환 계층은 명시적 예외

호환을 유지한다면 최소한 다음이 명확해야 한다.

  • 무엇과의 호환인가
  • 실제 Consumer가 무엇인가
  • 왜 유지해야 하는가
  • 어디까지 유지하는가
  • 제거 조건은 무엇인가

이 조건이 없다면 현재 구조로 완전히 전환한다.

6.2.마이그레이션 완료 기준

새 구조 구현→Consumer 이전→구 참조 제거→호환 계층 제거→Legacy / Dead Code 제거→검증
마이그레이션 완료 = 새 구조 적용 + 구 구조 정리.

7.Candidate · Validated · Stable

상태의미완료 조건
Candidate개발 중이거나 검증 전인 결과물구현이 끝났어도 검증 전이면 Candidate
Validated정해진 검증 기준을 통과한 결과물정적 검사뿐 아니라 프로젝트에 필요한 실제 실행 검증 완료
Stable다음 작업·배포의 공식 기준선Validated 중 기준본으로 승격된 결과물
Working→Candidate→Validated→Stable

8.Stable 승격

Stable은 단순히 “가장 최신 코드”가 아니라 검증 완료된 공식 기준선이다.

변경 성격에 따라 빌드, 실제 실행, 브라우저 E2E, 핵심 흐름, 회귀, 결정론, 관련 라이브러리 테스트 등을 수행한다. 실제로 하지 않은 검증은 PASS로 기록하지 않는다.

9.Git 운영

  • main은 기본적으로 안정 기준선을 나타낸다.
  • Candidate와 Stable을 혼동하지 않는다.
  • PR/브랜치 작업 전 실제 Git 상태를 먼저 확인한다.
  • 이미 병합된 PR, 오래된 커밋, Draft 상태, CI 실패 상태를 Stable로 착각하지 않는다.

10.커밋 메시지

기본적으로 한국어를 사용하고 변경 목적이 즉시 보이게 작성한다.

[bug-fix] 싱글 시작 오류 수정

- 캠페인 초기화 과정에서 발생하던 예외 수정

대표 prefix: [bug-fix], [feature], [refactor], [performance], [docs], [test], [build]

11.라이브러리 · Consumer 관리

공통 라이브러리와 이를 사용하는 게임은 서로 다른 변경 단위로 본다.

공통 라이브러리 변경→라이브러리 검증→기준본 확정→각 Consumer에서 명시적 업데이트

라이브러리가 바뀌었다는 이유만으로 모든 Consumer를 자동으로 동시에 수정하지 않는다.

12.결과물 전달

사용자에게 최종 결과물처럼 전달하는 파일은 검증이 끝난 결과물이어야 한다.

  • 중간본·부분 구현본·실패 후보본·검증 전 파일을 최종본처럼 전달하지 않는다.
  • 내부 Candidate는 여러 개 만들 수 있지만 최종 전달은 가능한 한 하나로 정리한다.
  • 최종 전달 시 파일/커밋, 메인 버전, 필요 시 BUILD_ID, 기준 베이스, 주요 변경, 검증 결과를 남긴다.

13.검증 · 배포 기록

다음 상태를 서로 같은 것으로 취급하지 않는다.

구현 완료≠검증 완료≠Stable 승격≠배포 완료

파일 생성은 배포 완료가 아니며, CI 실행은 검증 성공을 의미하지 않는다. 실제 결과를 기록한다.

14.롤백

  • 롤백 대상은 명확한 기준본으로 지정한다.
  • 파일명이 오래됐다는 이유만으로 롤백하지 않는다.
  • 롤백 대상 기능과 독립적인 리팩터링·성능 개선·버그 수정·구조 정리는 가능한 한 유지한다.
  • 롤백 대상에 종속된 변경은 함께 제거한다.

15.핸드오프

대화 또는 작업 공간을 옮길 때는 단순 요약이 아니라 즉시 작업을 이어갈 수 있는 상태 전달을 작성한다.

  • 현재 Stable / 기준본
  • 현재 메인 버전
  • BUILD_ID 또는 커밋
  • 완료 / 진행 중 / 남은 작업
  • 중요 결정
  • 폐기된 방향 및 재도입하면 안 되는 Legacy 방향
  • 검증 결과
  • 다음 작업 순서

새 작업에서는 오래된 기억보다 핸드오프와 실제 저장소 상태를 우선한다.

16.문서 역할 분리

문서역할
README프로젝트 소개, 실행·운영 방법
개발 규칙코딩, 아키텍처, 알고리즘, 구현 원칙
관리 규칙버전, Stable, Git, 마이그레이션, 배포, 산출물
사용자 도움말 / Wiki게임 규칙과 최종 사용자 사용법
검증 기록어떤 버전/커밋에서 무엇을 실제로 검증했는지

같은 내용을 여러 문서에 복제해 서로 다른 SSOT가 생기지 않게 한다.

17.최소 복잡성 원칙

관리 체계 자체가 프로젝트보다 복잡해지지 않게 한다.

  • 메인 버전 하나
  • Stable 기준본 하나
  • 불필요한 Compatibility Layer 없음
  • 불필요한 별도 Schema / Protocol Version 없음
  • 불필요한 중간 산출물 전달 없음
  • 불필요한 문서 중복 없음
새 관리 계층은 실제 문제를 해결하는 경우에만 추가한다.

18.핵심 요약

영역핵심 규칙
버전MAJOR = 제품 세대 / MINOR = 비호환 변경 / PATCH = 호환 변경
마이그레이션교체 후 정리. 호환 계층은 명시적 예외.
기준본항상 하나의 명확한 Stable / SSOT에서 시작
승격Candidate → Validated → Stable
완료구현 + 검증 + 불필요한 Legacy 정리
복잡성실제 필요가 없는 버전·호환 계층·문서·분기를 만들지 않음
검색어와 일치하는 규칙이 없습니다.
공통 세계관 / 게임 프로젝트 · 개발 외 관리 규칙 SSOT

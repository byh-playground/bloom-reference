0. 핵심 원칙

의도 정리 → 최소 한 번 검색·비교 → 구체 동작 확정 → 구현 → 같은 사례로 검증
AI는 용어를 맞췄다는 이유로 사용자의 의도까지 이해했다고 간주하지 않는다.

모든 프로젝트의 AI 개발 작업에 적용하는 사용자 확정 작업 원칙이다. 구현 전에 요청한 목적·기대 결과와 일반적인 처리 방식을 함께 검토하고, 수용 가능한 구체 동작으로 방향을 정한다. 기술적으로 가능한 구현이어도 사용자가 기대한 결과와 다르면 완료가 아니다.

관련 원본: 공통 개발 규칙 · 프로젝트 관리 규칙 · AI 개발 규칙 HTML 프리뷰. 이 문서는 AI의 요청 해석·작업 순서·공통 모듈 제약 처리 흐름을 소유하며 구조 원칙과 버전·검증 정책 전문을 복제하지 않는다.

1. 구현 전 · 요구와 동작을 확정

  1. 기대 결과를 먼저 적는다. 누가 어떤 상황에서 무엇을 하면 어떤 결과가 나와야 하는지 짧게 정리한다. 최신 저장소·기존 합의·제약을 읽고, 요청에 없는 동작을 확정 사양으로 추가하지 않는다.
  2. 항상 최소 한 번 검색·비교한다. 요청한 기능의 일반적인 처리 방식과 관련 공식 문서·일차 자료를 검색하고 실제 내용을 읽는다. 검색어만 입력하거나 결과 제목을 보는 것으로 검토를 끝내지 않는다. 현재 API·구현도 필요한 범위에서 대조한다.
  3. 일치와 차이를 설명한다. 사용자 요구 / 조사에서 확인한 관례·기술 제약 / 이번에 적용할 동작을 나눠 비교한다. 출처 링크·조회 기준과 중요한 가정을 남긴다. 검색 결과를 사용자 의도의 대체물로 쓰지 않는다.
  4. 동작 사례로 방향을 확정한다. 정상 상황과 해석이 갈리는 반례를 각각 적고 기대 결과를 정한다. 같은 용어라도 결과가 달라지는 해석을 비교한 뒤 구현한다.

1.1. 미지정 수치 초안 · 정규화와 기준값 파생

새 초안에는 단순한 척도를, 연관 수치에는 하나의 기준값을 사용한다
  • 사용자가 지정한 값과 이미 확정된 계약을 우선한다. 이 원칙은 새로 필요한 미지정 수치의 초안을 제안할 때 적용한다. 단위와 적정 범위를 확인한 뒤 100, 50, 25, 1, 0.5, 0.25, 0.1처럼 비교하기 쉬운 값을 후보로 삼는다. 해당 수치의 규모에 맞는 값을 선택하며, 이 목록은 닫힌 선택지나 모든 게임에 강제하는 기본값이 아니다.
  • 연관 수치는 기준값에서 파생한다. 가능하면 기본값 또는 기준 스탯 하나를 원본으로 두고, 다른 값은 배율·비율로 표현해 서로 독립된 임의 상수로 만들지 않는다. 예를 들어 공격력이 40이라면 미지정 스킬 공격력의 초안으로 공격력 × 1.5 = 60을 제안할 수 있다. 1.5배는 관계를 설명하는 예일 뿐 보편 계수는 아니다. 서로 다른 규칙의 수치라면 독립 기준과 근거를 명시한다.
  • 기존 게임 수치를 이 규칙으로 다시 쓰지 않는다. 현재 프로젝트에 이미 합의되거나 구현된 값, 합성·희귀도·드롭 확률 등은 별도 요청 없이 변경·재정규화하지 않는다. 초안의 단위·기준값·파생식과 가정은 함께 기록하고, 최종값은 프로젝트의 기획과 검증으로 확정한다.

게임 기획의 적용 위치는 게임 기획 가이드의 수치 초안 절, 스탯의 의미·단위·계약은 공통 STAT 사전을 따른다.

방향 확정은 매번 승인 대기가 아니다

명확한 요청이나 기존 합의로 정할 수 있으면 그 근거와 동작을 정리하고 진행한다. 해석에 따라 결과가 달라지는 중요한 미결정 사항만 선택지와 차이를 붙여 최소한으로 질문한다. 이미 정한 내용을 반복 승인받지 않는다.

기술적 관례와 게임 기획 선택을 구분한다. 관례와 요청이 다르면 그 차이·기술적 한계·대안을 설명하고 사용자가 의도한 결과를 보존한다. 검색이 막히거나 근거를 확보하지 못하면 검토 완료로 꾸미지 말고 미확인 범위와 영향부터 알린다.

2. 구현 중 · 공통 모듈 개선과 소비 게임 적용

공통 모듈 제약은 스스로 판단하고 끝까지 반영

제품 구현·마이그레이션 중 공통 모듈의 한계나 버그를 만나면 원인과 최소 재현을 먼저 확보한다. 재사용성, 공통 API의 책임 범위, 하위 호환성, 수정·검증·배포·Consumer 비용을 기준으로 공통 개선 적합성을 스스로 판단하며, 매번 사용자 지시를 기다리지 않는다. 공통 개발 규칙의 DRY·YAGNI 원칙도 따른다.

  • 공통에 맞으면: 공통 모듈을 수정하고 회귀 검증한 뒤 공통 프로젝트 관리 규칙에 따라 버전을 판정하고 공식 배포한다. 이어 소비 게임에 반영하고 실제 게임에서 검증한다.
  • 게임 고유 요구면: 공통 API를 넓히지 않고 제품 계층에 두며, 공통화하지 않은 근거를 기록한다.

제약만 보고하고 방치하거나 제품별 중복·임시 우회 구현으로 끝내지 않는다. 기존 승인 범위와 보안 제한을 지키며 넓히거나 우회하지 않는다.

3. 구현 후 · 확정한 사례로 검증

구현 전 정한 정상·반례 시나리오를 그대로 실행해 관찰 가능한 결과와 비교한다. 내부 함수명·수식이 의도대로 작성됐다는 확인만으로 사용자 결과 검증을 대신하지 않는다.

  • 보고할 것: 확정한 기대 동작, 실제 관찰 결과, 실행 환경·커밋과 근거, 실패·미실행·환경 차단 범위.
  • 다르면: 요구 해석·규칙·구현 중 어디가 달라졌는지 찾아 수정하고 같은 사례를 다시 확인한다. 기대 결과를 구현에 맞춰 몰래 바꾸지 않는다.
  • 문서 동기화: 새로 확정된 계약은 해당 기능의 원본 문서와 PR에 남긴다. 검증 완료와 병합·공개 완료는 각각 확인한다.

실행 상한·검증 기록·임시 검사 보존 등 운영 정책은 프로젝트 관리 규칙 HTML 프리뷰의 검증 정책을 따른다.

4. 사례 · 공과 고양이로 요구 해석

특정 게임의 요청 해석 사례 “충격량 기반 피해”라는 표현만으로 양쪽 공통 solver 충격량이나 상대속도를 피해식에 연결하면, 고양이가 정지한 공에 달려들어도 고양이가 피해를 받는 결과가 생길 수 있다. 이 사례에서 사용자가 원한 결과와 다르다.

나쁜 처리 “충격량 기반”이라는 단어만 보고 익숙한 공통 충돌 공식을 적용하고, 양쪽의 공통 solver 충돌값이 커졌다는 이유로 고양이 자체 이동도 같은 피해로 처리한다. 자료를 찾았거나 물리 충돌 테스트를 통과했다는 이유로 사용자의 요구가 충족됐다고 단정한다.

요구에 맞는 처리 일반 물리의 충돌 처리와 게임에서 피해를 주는 공격원의 의미를 비교하고, 어떤 장면에서 누가 피해를 받아야 하는지 먼저 정한다. 고양이 자체 속도가 아니라 고양이에게 날아오는 공격원인 공의 동작이 피해를 결정한다는 계약을 확정하고, solver의 물리 반작용과 공격원별 게임플레이 피해를 구분한다. 기존 합의로 정할 수 없는 부분만 묻는다.

  • 반례: 고양이가 정지한 공으로 달려듦 → 고양이 자체 속도만으로 고양이 피해가 생기지 않아야 한다.
  • 공격 사례: 공이 고양이에게 날아옴 → 공의 공격 동작에 따른 피해 계약을 적용한다. 피해를 산정하는 동작·조건·수식은 해당 게임의 합의로 정한다.
  • 동일 사례 검증: 구현 뒤 두 상황을 다시 실행해 물리 반응과 피해 결과를 각각 확인한다. 공의 동작은 같고 고양이 자체 속도만 달라질 때 의도와 다르게 피해를 키우지 않는지도 확인한다.

이 예시는 일반 물리의 절대 법칙이나 모든 게임의 공통 피해식을 정하지 않는다. 다른 공격원·장르·기획에서는 다른 피해 계약이 가능하다. 핵심은 용어가 아니라 요청한 원인과 결과를 구현하는 것이다.

5. 완료 체크리스트

  • 요청 의도·기대 결과와 기존 합의를 정리했는가?
  • 일반적인 처리 방식·공식/일차 자료를 최소 한 번 검색해 읽고 비교했는가?
  • 관례·기술 제약과 사용자 기획 선택의 차이를 근거와 함께 구분했는가?
  • 정상 사례와 반례의 기대 동작을 확정하고, 중요한 미결정만 최소 질문했는가?
  • 공통 모듈 제약의 원인·최소 재현과 개선 적합성을 판단했는가? 공통에 맞으면 소비 게임까지 검증하고, 게임 고유면 제품 계층에 둔 근거를 기록했는가?

6. 근거와 문서 역할

AI 개발 규칙 원본 작성 2026-10-15 · 공통 모듈 원칙 갱신 2026-10-16 UTC. “최소 한 번 검색·비교하고 구체 사례로 의도를 확정한다”와 “공통 모듈 제약을 스스로 판단해 적합한 개선을 Consumer까지 반영한다”는 사용자 확정 작업 원칙이다. 공과 고양이는 사용자 요구를 해석하는 사례이며 새로운 보편 물리 규칙이 아니다.

NASA · How to Write a Good Requirement는 필요한 결과와 구현 방법을 구분하고 명확성·가정·검증 가능성을 살피는 공식 참고 자료다. NASA · System Design Processes는 사용 시나리오로 기대를 정리하고 설계를 기대 결과와 대조하는 접근을 설명한다. 이 자료가 AI의 검색 횟수나 이번 게임의 피해식을 정한다는 뜻은 아니다.

공통 개발 규칙은 구조·코딩 원칙, 관리 규칙은 버전·검증·Git·배포 정책, 이 문서는 AI의 요청 해석·검색 비교·동작 확정과 공통 모듈 제약 처리 흐름을 소유한다. 관련 정책을 여러 문서에 복사하지 않는다.

AI 개발 규칙

요청한 방향을 구체적인 동작과 검증 결과로 맞춘다.

사용자 확정 작업 원칙2026-10-16

0. 핵심 원칙

의도 정리 → 최소 한 번 검색·비교 → 구체 동작 확정 → 구현 → 같은 사례로 검증
AI는 용어를 맞췄다는 이유로 사용자의 의도까지 이해했다고 간주하지 않는다.

모든 프로젝트의 AI 개발 작업에 적용하는 사용자 확정 작업 원칙이다. 구현 전에 요청한 목적·기대 결과와 일반적인 처리 방식을 함께 검토하고, 수용 가능한 구체 동작으로 방향을 정한다. 기술적으로 가능한 구현이어도 사용자가 기대한 결과와 다르면 완료가 아니다.

관련 원본: 공통 개발 규칙 · 프로젝트 관리 규칙 · AI 개발 규칙 HTML 프리뷰. 이 문서는 AI의 요청 해석·작업 순서·공통 모듈 제약 처리 흐름을 소유하며 구조 원칙과 버전·검증 정책 전문을 복제하지 않는다.

1. 구현 전 · 요구와 동작을 확정

  1. 기대 결과를 먼저 적는다. 누가 어떤 상황에서 무엇을 하면 어떤 결과가 나와야 하는지 짧게 정리한다. 최신 저장소·기존 합의·제약을 읽고, 요청에 없는 동작을 확정 사양으로 추가하지 않는다.
  2. 항상 최소 한 번 검색·비교한다. 요청한 기능의 일반적인 처리 방식과 관련 공식 문서·일차 자료를 검색하고 실제 내용을 읽는다. 검색어만 입력하거나 결과 제목을 보는 것으로 검토를 끝내지 않는다. 현재 API·구현도 필요한 범위에서 대조한다.
  3. 일치와 차이를 설명한다. 사용자 요구 / 조사에서 확인한 관례·기술 제약 / 이번에 적용할 동작을 나눠 비교한다. 출처 링크·조회 기준과 중요한 가정을 남긴다. 검색 결과를 사용자 의도의 대체물로 쓰지 않는다.
  4. 동작 사례로 방향을 확정한다. 정상 상황과 해석이 갈리는 반례를 각각 적고 기대 결과를 정한다. 같은 용어라도 결과가 달라지는 해석을 비교한 뒤 구현한다.

1.1. 미지정 수치 초안 · 정규화와 기준값 파생

새 초안에는 단순한 척도를, 연관 수치에는 하나의 기준값을 사용한다
  • 사용자가 지정한 값과 이미 확정된 계약을 우선한다. 이 원칙은 새로 필요한 미지정 수치의 초안을 제안할 때 적용한다. 단위와 적정 범위를 확인한 뒤 100, 50, 25, 1, 0.5, 0.25, 0.1처럼 비교하기 쉬운 값을 후보로 삼는다. 해당 수치의 규모에 맞는 값을 선택하며, 이 목록은 닫힌 선택지나 모든 게임에 강제하는 기본값이 아니다.
  • 연관 수치는 기준값에서 파생한다. 가능하면 기본값 또는 기준 스탯 하나를 원본으로 두고, 다른 값은 배율·비율로 표현해 서로 독립된 임의 상수로 만들지 않는다. 예를 들어 공격력이 40이라면 미지정 스킬 공격력의 초안으로 공격력 × 1.5 = 60을 제안할 수 있다. 1.5배는 관계를 설명하는 예일 뿐 보편 계수는 아니다. 서로 다른 규칙의 수치라면 독립 기준과 근거를 명시한다.
  • 기존 게임 수치를 이 규칙으로 다시 쓰지 않는다. 현재 프로젝트에 이미 합의되거나 구현된 값, 합성·희귀도·드롭 확률 등은 별도 요청 없이 변경·재정규화하지 않는다. 초안의 단위·기준값·파생식과 가정은 함께 기록하고, 최종값은 프로젝트의 기획과 검증으로 확정한다.

게임 기획의 적용 위치는 게임 기획 가이드의 수치 초안 절, 스탯의 의미·단위·계약은 공통 STAT 사전을 따른다.

방향 확정은 매번 승인 대기가 아니다

명확한 요청이나 기존 합의로 정할 수 있으면 그 근거와 동작을 정리하고 진행한다. 해석에 따라 결과가 달라지는 중요한 미결정 사항만 선택지와 차이를 붙여 최소한으로 질문한다. 이미 정한 내용을 반복 승인받지 않는다.

기술적 관례와 게임 기획 선택을 구분한다. 관례와 요청이 다르면 그 차이·기술적 한계·대안을 설명하고 사용자가 의도한 결과를 보존한다. 검색이 막히거나 근거를 확보하지 못하면 검토 완료로 꾸미지 말고 미확인 범위와 영향부터 알린다.

2. 구현 중 · 공통 모듈 개선과 소비 게임 적용

공통 모듈 제약은 스스로 판단하고 끝까지 반영

제품 구현·마이그레이션 중 공통 모듈의 한계나 버그를 만나면 원인과 최소 재현을 먼저 확보한다. 재사용성, 공통 API의 책임 범위, 하위 호환성, 수정·검증·배포·Consumer 비용을 기준으로 공통 개선 적합성을 스스로 판단하며, 매번 사용자 지시를 기다리지 않는다. 공통 개발 규칙의 DRY·YAGNI 원칙도 따른다.

  • 공통에 맞으면: 공통 모듈을 수정하고 회귀 검증한 뒤 공통 프로젝트 관리 규칙에 따라 버전을 판정하고 공식 배포한다. 이어 소비 게임에 반영하고 실제 게임에서 검증한다.
  • 게임 고유 요구면: 공통 API를 넓히지 않고 제품 계층에 두며, 공통화하지 않은 근거를 기록한다.

제약만 보고하고 방치하거나 제품별 중복·임시 우회 구현으로 끝내지 않는다. 기존 승인 범위와 보안 제한을 지키며 넓히거나 우회하지 않는다.

2.1. SVG 자산 · 원본을 보존하고 공통 브라우저 로더에서 한 번 컴파일

SVG 정적 벡터 아트의 단일 원본은 SVG이며, 생성된 메시를 게임에 포장하지 않는다
  • 원본 SVG를 유지한다. SVG로 제공된 정적 벡터 아트는 원본 SVG만 게임의 해당 자산으로 포함하고 이를 형상·뷰박스·식별자·메타데이터·작성된 애니메이션의 단일 기준으로 삼는다. 메시에 맞춘 별도 복제본을 만들거나 메타데이터·애니메이션을 지우지 않는다. 동적 효과는 SVG 규칙으로 덮어씌우지 않고 프로젝트에 맞는 셰이더·절차적 방식을 계속 사용한다.
  • 공통 브라우저 로더가 시작 시 한 번 컴파일한다. 게임 시작 때 원본 SVG를 검증하고 인덱스드 기하(Indexed Geometry)로 컴파일한 뒤, 콘텐츠 식별자로 캐시하여 GPU에서 유지·재사용한다. 프레임마다 파싱·삼각분할·컴파일하지 않는다. 변환과 지원되는 애니메이션은 보유한 기하에 적용하고 원본 SVG를 반복 컴파일하지 않는다.
  • SDK의 공백을 소비 게임의 산출물로 감추지 않는다. Node 전용 소스 도구만 제공되는 SDK를 브라우저에서 직접 import할 수 없다는 사실을, 소비 게임이 빌드 때마다 대형 메시를 미리 만들어 포함해야 한다는 요구로 오해하지 않는다. 브라우저 로더·내보내기·런타임 API가 빠졌다면 공통 SDK에서 먼저 설계·구현·검증한다. 소비 게임마다 별도 컴파일러나 메시 복사본을 추가하지 않는다.
  • 입력과 실패를 제한하고 드러낸다. 공통 로더는 허용하는 SVG 기능과 소스 크기·복잡도·처리 시간 상한을 문서화하고 검증한다. 다운로드·파싱·컴파일 실패는 자산 경로·실패 단계·원인을 보고한다. 일시적인 전송 오류만 최대 한 번 재시도하고, 잘못되었거나 지원하지 않는 소스는 재시도하지 않는다. 래스터 이미지로 조용히 대체하거나 애니메이션을 버리지 않는다.
  • 생성된 확장 메시를 배포물에 넣지 않는다. 미리 계산한 메시를 Base64로 게임 JS/HTML에 박거나 generated resources로 저장소·배포 패키지에 포함하지 않는다. SVG 경로의 런타임 컴파일은 공짜라고 가정하지 않는다. 초기 로드 시간·컴파일 시간·GPU 메모리를 실제 브라우저에서 측정하고, 프로젝트별 패키지 크기 예산을 두어 빌드/리뷰에서 큰 재생성 산출물의 포함을 잡는다.
  • 원본과 게임 화면을 대조한다. 같은 뷰박스·크기·색상·애니메이션 상태에서 원본 SVG와 게임 렌더를 나란히 비교한다. 모양·레이어·메타데이터·애니메이션의 기대 결과와 오류·미검증 범위를 기록한다. 일반 실행 성공이나 파일 크기만으로 시각 검증을 대신하지 않는다.

나쁜 예 · Farm 번들 사례 원본은 SVG 5개 합계 66,621 B였지만, 최종 게임 번들은 11.22 MB이고 그중 98.37%가 확장된 생성 정점 데이터였다. Node 전용 SDK 소스 도구를 “브라우저에서 쓸 수 없다”로 오해해 미리 만든 대형 메시를 게임 번들에 포함하면, 작은 원본을 유지하는 대신 전송·저장 크기만 크게 늘어난다.

요구에 맞는 처리 SVG 원본만 자산으로 포함하고 공통 SDK의 브라우저 로더를 바로잡아 시작 시 한 번 컴파일·캐시·재사용한다. 해당 게임에서 원본과 렌더를 비교하고 시작 비용·메모리·패키지 크기를 측정한다.

이 규칙은 SVG로 제공된 정적 벡터 아트의 입력·렌더·패키징 계약이다. 모든 그래픽을 SVG로 강제하지 않으며 동적 VFX·절차적 표면에는 해당 표현 방식을 쓴다. 검증 기록의 범위·PASS/FAIL/미실행 구분과 배포 확인은 공통 프로젝트 관리 규칙의 검증 정책을 따른다.

2.2. 자동 저장 · 변경 확인과 저장 비용 측정

고정 주기보다 dirty 감지, 배치 저장, 복원 경계를 먼저 설계한다
  • 3초 저장을 일률적으로 금지하지 않는다. 짧은 주기가 복구 목표에 맞을 수 있다. 안티패턴은 변경 확인 없이 전체 상태를 자주 스냅샷·직렬화하고, 즉시 전체 복원·검증과 동기 I/O까지 렌더/프레임 경로에서 반복하는 조합이다. 허용할 데이터 손실 구간과 저장 빈도를 사용 흐름에 맞춰 정한다.
  • 저장할 상태의 변경 revision 또는 dirty 상태를 확인한다. 렌더 프레임이나 일시적인 물리 변화 전체를 자동으로 저장 대상으로 삼지 말고, 지속돼야 할 게임 상태가 마지막 저장본과 달라진 때만 저장한다. 짧은 연속 변화는 coalescing/debounce로 묶되 maxWait 상한을 두어 변화가 계속될 때 저장이 무기한 밀리는 기아를 막는다. 보상 수령·전투 종료 등 복구 목표상 중요한 체크포인트도 정의한다.
  • 직렬화·검증과 hydrate/restore를 분리한다. 저장 시 필요한 스냅샷·직렬화·경량 무결성 확인과 전체 normalize·마이그레이션·객체 복원은 별도 경로로 둔다. 전체 복원은 시작·가져오기·마이그레이션·복구처럼 필요한 시점에 하고, 저장마다 문자열을 다시 파싱해 Garden 전체를 재구축하지 않는다. 비동기 저장은 저장한 revision을 확인하고 완료 순서를 관리해 오래된 쓰기가 새 상태를 덮지 않게 한다.
  • 큰 직렬화와 저장 I/O를 렌더 핫패스에서 수행하지 않는다. Web Storage의 localStorage는 동기식이다. 큰 스냅샷·검증·복원이나 getItem/setItem을 requestAnimationFrame/렌더 경로에서 호출하지 않는다. 저장량·복구 요구가 맞는지 확인한 뒤 IndexedDB 같은 비동기 저장소나 Worker 처리를 평가한다. IndexedDB를 선택해도 JSON 변환이 자동으로 메인 스레드를 벗어나는 것은 아니므로 전체 경로를 측정한다.
  • 페이지 종료 이벤트 하나에 영속성을 맡기지 않는다. 상태 변경 뒤의 안전한 체크포인트와 목표한 저장 간격을 기본으로 둔다. 탭이 숨겨질 때 visibilitychange를 추가 저장 기회로 활용할 수 있지만, pagehide나 종료 직전 이벤트만으로 저장이 보장된다고 가정하지 않는다. 모바일에서 종료 이벤트가 생략될 수 있다.
  • 실패와 여러 탭의 경합에서 원본 저장을 보호한다. 저장 공간 부족·접근 거부·스키마 오류·마이그레이션 실패·다른 탭의 동시 변경을 각각 다룬다. 충돌한 탭이 최신 저장을 덮지 않게 하고, 복구 가능한 오류를 알리며 원본 데이터를 조용히 초기화하거나 잃지 않도록 한다. 탭 간 최신성·복구 동작도 실제 브라우저에서 확인한다.
  • 비용과 사용자 지연을 실제로 측정한다. 상태 크기·기기·브라우저·변경 없음/변경됨 조건을 기록하고 스냅샷, 직렬화, 검증·복원, 저장 I/O 시간을 나눠 관찰한다. 프레임 시간과 저장 호출 빈도도 비교한다. 프로파일이나 추적 결과 없이 특정 코드 경로를 사용자가 느낀 렉의 유일 원인이라고 단정하지 않는다.

나쁜 예 · Farm 0.6.1 저장 경로 지정 커밋의 farm-app.js에서 frame()이 매 프레임 sync()를 부르고, sync()는 3초를 넘으면 저장 revision/dirty 확인 없이 persist()를 호출한다. 집 화면에서도 프레임 함수는 계속 sync()를 실행하며, 일시 정지는 저장 조건을 막지 않는다. 집 화면 전환·창 blur·문서 숨김·pagehide에도 별도 저장 경로가 있다.

FarmStorage는 snapshot() 결과를 직렬화한 뒤 저장 직전에 다시 parse하고 restore()해 전체 Garden을 정규화·검증·재구축한 다음 localStorage.setItem()을 호출한다. 매번 전체 검증·복원이 필요한지, 저장본이 실제 변경됐는지 분리하지 않은 경로가 반복 비용을 만든다. 코드에서 불필요한 작업 경로는 확인되지만 사용자 기기에서의 지연 기여도나 유일 원인은 측정으로 확인해야 한다.

더 나은 방향 영속 상태 변경 revision으로 저장을 걸고, 저장 요청은 묶되 maxWait와 중요한 체크포인트로 복구 창을 보장한다. 직렬화·기본 무결성 확인은 복원·마이그레이션과 분리하고, 저장 경로를 프레임 핫패스 밖으로 옮긴 뒤 실제 기기 프로파일로 비용을 비교한다. 저장 실패·탭 경합·원본 보존 시나리오도 함께 검증한다.

이 항목은 저장 주기 숫자 하나를 금지하는 규칙이 아니다. 무변경 상태의 반복 전체 직렬화·복원과 동기 I/O를 핫패스에서 피하고, 내구성 목표와 실측 근거에 맞춰 체크포인트를 고른다.

2.3. 논리 틱과 물리 하위 단계 · 이름이 아니라 호출 범위를 검증

필요한 물리만 세분화하고 전체 갱신의 중복을 비용으로 계산한다
  • 진입 루프 → 논리 틱 → 하위 단계 → 실제 호출 범위를 정적으로 추적한다. 함수명·주석의 “물리”를 믿고 기존 월드 갱신을 그대로 감싸지 않는다. 빈도 × 대상 수 × 중첩 반복으로 초당 총량과 catchup 한 번의 최악 작업량을 계산한다.
  • 물리·의사결정·렌더·저장의 주기 소유자를 나눈다. AI·생활·검색·성장·생명주기·스킬 판단·전체 정리를 물리 횟수만큼 반복하지 않는다. 이동·접촉처럼 세분화가 필요한 작업만 하위 단계에 두고, 총 dt와 지속시간·생성/소멸·공격 사건·Signal의 단일 실행 책임을 유지한다. dt 없는 접촉 계수와 표시 캡처 경계도 함께 검토한다.
  • 필요 횟수를 근거와 계측으로 정한다. 이동량·몸 크기·충돌 방식과 고속/밀집 반례를 확인하고, 실제 논리/물리/catchup 횟수와 AI·공간 인덱스·충돌·렌더·저장 비용을 구분해 기록한다. 기존 공통 진단 API를 우선 사용하고, 짧은 요약과 동일 프레임의 경량 숫자 기록으로 추적 가능하게 한다. 부모·자식 시간의 중첩과 CPU/GPU 미측정 범위를 명시한다.
  • 기능 E2E 통과를 성능 근거로 쓰지 않는다. 속도 보존·이벤트 중복·관통·접촉을 기능 사례로 검증하고, 빈도·작업량·실제 시간은 별도로 측정한다. 프레임 분산으로 총량 문제를 숨기거나 측정 없이 실제 기기 개선 배율을 단정하지 않는다.

나쁜 예 · Farm 0.8.4 전체 월드 반복 FarmSession.advance는 20Hz 틱마다 Garden.step(1/120)을 6번 실행했다. 실제 step에는 AI·생활·먹이·번식/합성·성장·스킬·효과 정리와 공간 인덱스 전체 재구축까지 들어 있었다. 물리만 6회라고 설명했지만 전체 월드가 초당 120회였고, catchup 4틱이면 한 번에 24회였다. 기능 E2E 통과만으로 필요한 횟수나 성능을 정당화할 수 없다.

요구에 맞는 처리 논리는 한 틱의 총 dt로 한 번 갱신하고, 필요한 이동·충돌만 근거 있는 하위 단계로 나눈다. 전체 rebuild/정리와 임시 할당을 반복 경로에서 제거하고 이동 뒤 인덱스 정확성을 유지한다. 변경 전후 호출 수·시간·이벤트 수와 같은 동작 사례를 함께 확인한다.

20Hz나 120Hz 자체를 금지하는 규칙이 아니다. 고정 시간 간격과 물리 세분화는 유효한 도구이며, 금지 대상은 필요 없는 전체 월드 반복을 이름과 기능 통과로 정당화하는 방식이다. Box2D의 Simulation은 물리 solver를 나누는 범위와 정확도/비용을, Fix Your Timestep은 dt 보존과 누적 작업량의 한계를 설명하는 일차 참고다. 해당 예시의 횟수를 모든 게임에 그대로 적용하지 않는다.

3. 구현 후 · 확정한 사례로 검증

구현 전 정한 정상·반례 시나리오를 그대로 실행해 관찰 가능한 결과와 비교한다. 내부 함수명·수식이 의도대로 작성됐다는 확인만으로 사용자 결과 검증을 대신하지 않는다.

  • 보고할 것: 확정한 기대 동작, 실제 관찰 결과, 실행 환경·커밋과 근거, 실패·미실행·환경 차단 범위.
  • 다르면: 요구 해석·규칙·구현 중 어디가 달라졌는지 찾아 수정하고 같은 사례를 다시 확인한다. 기대 결과를 구현에 맞춰 몰래 바꾸지 않는다.
  • 문서 동기화: 새로 확정된 계약은 해당 기능의 원본 문서와 PR에 남긴다. 검증 완료와 병합·공개 완료는 각각 확인한다.

실행 상한·검증 기록·임시 검사 보존 등 운영 정책은 프로젝트 관리 규칙 HTML 프리뷰의 검증 정책을 따른다.

4. 사례 · 공과 고양이로 요구 해석

특정 게임의 요청 해석 사례 “충격량 기반 피해”라는 표현만으로 양쪽 공통 solver 충격량이나 상대속도를 피해식에 연결하면, 고양이가 정지한 공에 달려들어도 고양이가 피해를 받는 결과가 생길 수 있다. 이 사례에서 사용자가 원한 결과와 다르다.

나쁜 처리 “충격량 기반”이라는 단어만 보고 익숙한 공통 충돌 공식을 적용하고, 양쪽의 공통 solver 충돌값이 커졌다는 이유로 고양이 자체 이동도 같은 피해로 처리한다. 자료를 찾았거나 물리 충돌 테스트를 통과했다는 이유로 사용자의 요구가 충족됐다고 단정한다.

요구에 맞는 처리 일반 물리의 충돌 처리와 게임에서 피해를 주는 공격원의 의미를 비교하고, 어떤 장면에서 누가 피해를 받아야 하는지 먼저 정한다. 고양이 자체 속도가 아니라 고양이에게 날아오는 공격원인 공의 동작이 피해를 결정한다는 계약을 확정하고, solver의 물리 반작용과 공격원별 게임플레이 피해를 구분한다. 기존 합의로 정할 수 없는 부분만 묻는다.

  • 반례: 고양이가 정지한 공으로 달려듦 → 고양이 자체 속도만으로 고양이 피해가 생기지 않아야 한다.
  • 공격 사례: 공이 고양이에게 날아옴 → 공의 공격 동작에 따른 피해 계약을 적용한다. 피해를 산정하는 동작·조건·수식은 해당 게임의 합의로 정한다.
  • 동일 사례 검증: 구현 뒤 두 상황을 다시 실행해 물리 반응과 피해 결과를 각각 확인한다. 공의 동작은 같고 고양이 자체 속도만 달라질 때 의도와 다르게 피해를 키우지 않는지도 확인한다.

이 예시는 일반 물리의 절대 법칙이나 모든 게임의 공통 피해식을 정하지 않는다. 다른 공격원·장르·기획에서는 다른 피해 계약이 가능하다. 핵심은 용어가 아니라 요청한 원인과 결과를 구현하는 것이다.

6. 근거와 문서 역할

AI 개발 규칙 원본 작성 2026-10-15 · 공통 모듈 원칙 갱신 2026-10-16 UTC · 같은 날 Farm 0.6.1 저장 경로 사례를 확인해 추가했다. 코드상 반복 비용은 근거로 설명하되 사용자 기기 지연의 원인 단정은 하지 않는다. “최소 한 번 검색·비교하고 구체 사례로 의도를 확정한다”와 “공통 모듈 제약을 스스로 판단해 적합한 개선을 Consumer까지 반영한다”는 사용자 확정 작업 원칙이다. 공과 고양이는 사용자 요구를 해석하는 사례이며 새로운 보편 물리 규칙이 아니다.

NASA · How to Write a Good Requirement는 필요한 결과와 구현 방법을 구분하고 명확성·가정·검증 가능성을 살피는 공식 참고 자료다. NASA · System Design Processes는 사용 시나리오로 기대를 정리하고 설계를 기대 결과와 대조하는 접근을 설명한다. 이 자료가 AI의 검색 횟수나 이번 게임의 피해식을 정한다는 뜻은 아니다.

자동 저장 사례의 고정 코드는 Farm 0.6.1의 프레임·저장 호출, 저장 어댑터, 스냅샷·복원에서 확인할 수 있다. 브라우저 근거: MDN Web Storage API의 동기 동작, IndexedDB API의 비동기 트랜잭션, visibilitychange의 hidden 전환, pagehide의 모바일 신뢰성 한계를 참고한다. 이는 특정 저장소 선택을 강제하지 않으며 복구 목표와 실제 측정이 선택 기준이다.

공통 개발 규칙은 구조·코딩 원칙, 관리 규칙은 버전·검증·Git·배포 정책, 이 문서는 AI의 요청 해석·검색 비교·동작 확정, 공통 모듈 제약 처리, SVG 자산의 원본·브라우저 렌더 파이프라인, 자동 저장 비용·검증 기준을 소유한다. 검증·배포 정책 전문은 중복하지 않는다.

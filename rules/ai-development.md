## 대전제 · 통용 용어로 의미를 고정한다 {#terminology}

- [AI-000][-] **Ubiquitous Language · Shared Vocabulary** — 규칙·문서를 쓸 때 사용자가 설명한 내용과 같은 뜻을 가진 통용 용어나 해시태그(SSOT, KISS, MECE, YAGNI 등)가 있으면 그 용어를 규칙 줄 앞에 함께 적는다. 용어가 뜻을 전부 덮지 못하면 용어 뒤에 차이를 한 절로 적는다. 위반 판별: 같은 뜻의 통용 용어가 있는데 규칙에 용어가 없거나, 뜻이 다른 용어를 붙였다.

용어: **Ubiquitous Language**(DDD) — 팀 전원이 같은 뜻으로 쓰는 공용 어휘. **Shared Vocabulary** — 설명 없이도 같은 뜻으로 통하는 통용 용어.

> [!IMPORTANT] **왜 용어를 먼저 적는가**
> 통용 용어는 원문 의도를 짧게 고정한다. 읽는 사람과 AI가 긴 설명 대신 이미 아는 뜻으로 규칙을 이해하고, 이후 문서를 재구성할 때 용어를 기준으로 묶고 나눌 수 있다. 용어는 설명을 대체하지 않고 설명 앞에 붙는 제목이다.

- 적용 형식: `- [ID][우선순위] **용어 · 용어** — 규칙 문장. 위반 판별: …`. 용어는 2개 이하로 두고, 더 필요하면 본문에 `용어:` 줄로 정의한다.
- 용어 선택 기준: 공식 정의가 있거나(SemVer, Conventional Commits, ADR) 업계에서 한 가지 뜻으로 쓰이는 것(SSOT, KISS, YAGNI, DRY, MECE, Given-When-Then). 이 레포에서만 쓰는 조어는 용어 자리에 두지 않는다.
- 뜻이 부분만 겹치면 그대로 쓰되 본문에서 차이를 밝힌다(예: AI-006의 One-way/Two-way Door는 "되돌릴 수 있는가"를 보고, 이 규칙은 "해석에 따라 결과가 갈리는가"도 본다).

## 완료 조건 · 무엇이 끝났다는 뜻인가 {#verification}

AI가 "완료"라고 보고할 수 있는 조건을 정한다. 작업 순서보다 먼저 읽는다. 완료 조건이 없으면 코드만 쓰고 넘기게 되고, 사용자가 결과를 확인해 수정을 지시하는 왕복이 작업마다 쌓인다.


- [AI-013][-] **Acceptance Test · Moving the Goalposts 금지** — 구현 전 확정한 정상·반례 시나리오를 그대로 실행해 관찰 결과를 비교하고, 기대 동작·실제 결과·환경·커밋·실패·미실행 범위를 보고하며, 기대 결과를 구현에 맞춰 바꾸지 않는다. 위반 판별: 함수명·수식 확인만으로 검증 완료라고 보고했거나 미실행 범위 기록이 없다.

용어: **Acceptance Test** — 사전에 정한 조건으로 합격을 판정한다. **Moving the Goalposts** — 결과에 맞춰 기준을 바꾸는 오류.

- [AI-014][-] **Definition of Done · Docs as Code** — 새로 확정된 계약은 해당 기능의 원본 문서와 PR에 남기고, 검증 완료와 병합·공개 완료를 각각 확인한다. 위반 판별: 계약 변경이 PR 본문과 원본 문서에 없다.

용어: **Definition of Done** — 완료 조건에 문서 동기화와 공개 확인을 포함한다. **Docs as Code** — 문서를 코드와 같은 PR·리뷰로 바꾼다.

- [AI-015][-] **Observable Evidence · Show, Don't Tell** — 완료의 기준은 코드를 쓴 것이 아니라 AI가 실제 실행 결과를 직접 본 것이다. 변경한 장면·파라미터를 실제로 실행해 관찰물(화면·연출은 스크린샷이나 키프레임, 로직·수치는 실행 로그나 출력값)을 얻어 기대 결과와 비교하고, 그 관찰물과 비교 결과를 보고에 첨부한다. 위반 판별: 관찰물 없이 "구현했다"고 보고했거나, 사용자가 직접 실행해야 결과를 알 수 있다.

용어: **Observable Evidence** — 주장 대신 관찰할 수 있는 증거(화면·출력·로그)로 결과를 보인다. **Show, Don't Tell** — "했다"는 말 대신 결과물 자체를 보여 준다.

관찰물은 변경 종류에 따라 정한다. 변경한 파라미터를 실제로 넣은 상태의 결과여야 하고, 비슷한 다른 상태로 대신하지 않는다.

| 변경 종류 | 관찰물 | 비교 방법 |
| --- | --- | --- |
| 화면·UI·연출·VFX | 해당 상태의 스크린샷, 움직임이면 키프레임 여러 장(시작·중간·끝) | 변경 전후 나란히, 기대한 모양과 대조 |
| 시뮬레이션·물리·수치 | 변경 전후의 실행 로그, 출력값, 호출 횟수 | 기대값·허용 범위와 대조 |
| 빌드·배포·생성물 | 생성 파일 경로·크기, 실행 결과(열림·오류 없음) | 생성물이 실제로 열리는지 |
| 문서·규칙 | 렌더된 화면 또는 변환기 검사 결과 | 링크·앵커·표가 의도대로 보이는지 |

이 규칙은 [AI-013](#verification)의 "시나리오를 실행해 비교한다"에서 **누가 보는가**를 정한다. 사용자가 실행해 보고 알려 주는 것이 아니라 AI가 먼저 보고 결과를 가져온다. 코드만 쓰고 넘기면 초반에는 문제가 없지만, 사용자가 결과를 확인하고 수정을 지시하는 왕복이 작업마다 쌓여 뒤로 갈수록 수정 요청이 늘어난다. 관찰물을 첨부한 보고는 이 왕복을 없앤다. 관찰이 불가능한 환경(브라우저·기기 없음)이면 [AI-007](#known-unknowns)에 따라 미관찰 범위를 먼저 알린다. 기록 항목은 [관리 규칙의 검증 기록](project-management.md#verification-evidence)을 따른다.

- [AI-016][-] **Ephemeral Evidence · Keep Only Reusable** — 관찰물(스크린샷·키프레임·로그)과 검증용 임시 코드(스크립트·단위 테스트·디버그 출력)는 그 시점에 사용자와 결과를 공유하기 위한 증거다. 보고에 첨부한 뒤 폐기하고 레포에 남기지 않는다. 레포에 남기는 기준은 재사용 하나다: 다음 작업에서도 같은 검증을 다시 돌리는 것(고정 사용자 시나리오 E2E, 변환기 검사)만 남기고, 요청하지 않은 테스트는 만들지 않는다. 위반 판별: PR에 1회용 스크린샷·임시 스크립트·디버그 테스트가 들어 있거나, 재사용 근거 없이 테스트 파일이 추가되었다.

용어: **Ephemeral** — 그 시점에만 쓰고 버리는 것. **Keep Only Reusable** — 저장소에는 다시 쓸 것만 남긴다.

증거의 목적은 그 순간 사용자와 AI가 같은 결과를 보는 것이다. 목적이 끝나면 증거도 끝난다.

| 산출물 | 처리 | 이유 |
| --- | --- | --- |
| 스크린샷·키프레임·실행 로그 | 보고에 첨부(이미지·표·수치) 후 폐기. 작업 폴더나 PR 본문에만 둔다 | 다음 작업에서 다시 볼 일이 없다 |
| 검증용 임시 스크립트·디버그 테스트 | 작업 중 임시 경로에 두고 커밋하지 않는다. 완료 시 삭제 | [PM-009](project-management.md#verification-policy)의 "단위 테스트는 개발 중 임시 검증에만" |
| 고정 사용자 시나리오 E2E | 레포에 유지 | 모든 변경에서 같은 흐름을 다시 검증한다 |
| 변환기·빌드의 자체 검사(`--check` 등) | 레포에 유지 | 매 push마다 다시 돌린다 |
| 새 테스트 파일 | 요청이 있거나 위 두 줄에 해당할 때만 추가 | 요청하지 않은 테스트가 쌓이면 전체 실행이 느려진다 |

관찰물을 PR에 첨부할 수단이 없으면(이미지 업로드 불가 등) 관찰한 수치·결과를 표로 적고, 이미지가 미첨부임을 [AI-007](#known-unknowns)에 따라 밝힌다.

- [AI-017][-] **Deterministic Capture · Parameterized Scene** — 관찰물은 아래 표준 절차 하나로 얻는다: 결정론적 실행(고정 dt·시드 난수)에 장면 파라미터(seed·설정·tick)를 넣어 같은 장면을 재현하고, 헤드리스 브라우저의 고정 뷰포트에서 캡처해 변경 전후를 같은 파라미터로 비교한다. 사람이 화면을 보며 찍거나 작업마다 다른 방식으로 캡처하지 않는다. 위반 판별: 관찰물에 재현 파라미터(커밋·seed·tick·뷰포트)가 없거나, 전후 비교가 다른 조건에서 이뤄졌다.

용어: **Deterministic** — 같은 입력이면 항상 같은 결과. **Parameterized Scene** — 장면을 "언제·어떤 설정"의 값으로 지정해 호출로 재현하는 것. 캡처를 위해 실제 시간이나 사람의 조작에 의존하지 않는다.

#### 표준 관찰 절차 {#observation-procedure}

모든 AI가 같은 순서·같은 기본값으로 한다. 기본값을 바꿔야 하면 보고에 바꾼 값과 이유를 적는다.

| 순서 | 할 일 | 기본값·판별 |
| --- | --- | --- |
| A | **결정론 확인** — 대상이 고정 dt·시드 난수로 돌고, 시뮬레이션 안에서 `Date.now`·`performance.now`·`Math.random`을 쓰지 않는지 확인한다. 아니면 먼저 그렇게 바꾼다([AI-012](#simulation-cadence), 공통 모듈이면 [AI-009](#shared-modules)). | 같은 seed·tick에서 두 번 실행한 상태 스냅샷이 같아야 한다 |
| B | **캡처 진입점** — 게임이 캡처 모드로 열리면 자동 루프(rAF)를 돌리지 않고, 전역 1개로 `init(seed, params)` · `stepTo(tick)` · `render()` · `state()`를 노출한다. 입력은 사람이 쓰는 것과 같은 입력 함수로 넣는다. | 모드 전환은 URL `?capture=1`. 진입점 이름과 구현은 bloom-gamekit 공통 모듈에 1개(SSOT), 게임은 그것을 켠다. 게임마다 따로 만들지 않는다 |
| C | **장면 지정** — 관찰할 장면을 (커밋, seed, params, tick)로 적는다. 변경이 영향을 주는 구간의 시작·중간·끝 각 1장 + 반례([AI-005](#examples)) 1장이 기본이다. | 키프레임 최소 3장, 최대 12장. tick 단위는 시뮬 틱, 시간으로 말하면 `tick = 초 × 틱레이트` |
| D | **캡처 실행** — 헤드리스 Chromium(Playwright)으로 고정 뷰포트에서 `stepTo(tick)` → `render()` → 스크린샷. 수치 관찰은 `state()`를 JSON으로 저장. 콘솔 오류도 함께 수집한다. | 뷰포트 1280×720과 390×844(모바일) 2종, DPR 1, `scroll-behavior`·CSS 애니메이션 끔. 파일명 `{장면}-t{tick}-{폭}x{높이}.png`. 캡처 스크립트는 임시 경로에 두고 커밋하지 않는다. 전체 캡처는 180초 안에 끝낸다([PM-009](project-management.md#verification-policy)) |
| E | **전후 비교** — 기준 커밋(main 또는 지정 기준본)과 변경 커밋을 같은 (seed, params, tick)로 캡처해 나란히 둔다. 기대 결과([AI-002](#given-when-then))와 대조하고, 차이마다 의도된 변화인지 아닌지 적는다. | 비교 조건이 하나라도 다르면 비교가 아니다 |
| F | **보고** — 장면 1개당 표 1행: 장면 · tick · 기대 · 관찰 · 판정(일치/불일치/미관찰). 이미지는 첨부할 수 있는 채널(채팅 첨부, PR 본문)에 넣고, 불가하면 수치 표로 대체하고 미첨부를 밝힌다([AI-007](#known-unknowns)). | 재현 파라미터(커밋·seed·tick·뷰포트)를 표 위에 1줄로 적는다 |
| G | **폐기** — 스크린샷·JSON·캡처 스크립트를 지운다. B의 캡처 진입점은 제품 코드이므로 남는다. | [AI-016](#verification) |

예외 처리:

- 결정론을 만들 수 없는 대상(실제 네트워크·외부 서비스·실제 입력 장치): 같은 입력 시퀀스를 녹화해 재생하고, mock·loopback 사용 여부를 보고에 적는다([PM-010](project-management.md#verification-evidence)). 실제 경로 성공으로 보고하지 않는다.
- 시각 요소가 없는 변경(수치·로직): D에서 스크린샷 대신 `state()` 수치를 tick별 표로 남긴다. 절차의 나머지는 같다.
- 문서·규칙 변경: 변환기 검사 결과 + 렌더 스크린샷 1장. seed·tick은 없다.
- 이 세션처럼 브라우저가 없는 환경: 캡처 불가를 먼저 알리고([AI-007](#known-unknowns)) `state()` 수치만 보고한다.

디스플레이 없는 리눅스(CI·VM·클라우드 세션)에서의 실행 방식은 하나로 정한다.

| 방식 | 언제 | 명령·판별 |
| --- | --- | --- |
| 헤드리스 Chromium (기본) | 항상 먼저 쓴다. 가상 디스플레이(Xvfb)가 필요 없고 WebGL은 SwiftShader로 동작한다 | Playwright `chromium.launch()` 기본. 확인 2026-10-30: Chromium 153, `DISPLAY` 없음, Xvfb 미사용 상태에서 WebGL2 컨텍스트 생성과 렌더러 `SwiftShader` 확인 |
| Xvfb + headed Chromium | 헤드리스에서만 재현되는 문제(컨텍스트 손실 반복, headless 미지원 API)를 가려내야 할 때만 | `xvfb-run -a -s "-screen 0 1280x720x24" python3 capture.py` 에 `headless=False`. 결과가 헤드리스와 다르면 그 차이를 보고에 적는다 |
| 실제 GPU | 소프트웨어 렌더러로는 판단할 수 없는 것(GPU 드라이버 차이, 실제 프레임 시간) | 사용자 기기 또는 GPU가 있는 러너. 헤드리스·Xvfb는 모두 소프트웨어 렌더러이므로 실제 GPU 경로의 성공으로 보고하지 않는다([PM-010](project-management.md#verification-evidence)) |

소프트웨어 렌더러(헤드리스 GPU 없음)에서 WebGL 컨텍스트가 끊겨 빈 프레임이 나올 수 있다. `render()` 뒤 컨텍스트 손실을 확인하고 손실이면 페이지를 다시 열어 같은 tick을 재캡처한다. 영상으로 묶을 때 가로·세로는 짝수 픽셀로 맞춘다.

구현 전 정한 정상·반례 시나리오를 그대로 실행해 관찰 가능한 결과와 비교한다. 내부 함수명·수식이 의도대로 작성됐다는 확인만으로 사용자 결과 검증을 대신하지 않는다.

- **보고할 것:** 확정한 기대 동작, 실제 관찰 결과와 관찰물(스크린샷·키프레임·로그), 실행 환경·커밋과 근거, 실패·미실행·환경 차단 범위.
- **다르면:** 요구 해석·규칙·구현 중 어디가 달라졌는지 찾아 수정하고 같은 사례를 다시 확인한다. 기대 결과를 구현에 맞춰 몰래 바꾸지 않는다.
- **문서 동기화:** 새로 확정된 계약은 해당 기능의 원본 문서와 PR에 남긴다. 검증 완료와 병합·공개 완료는 각각 확인한다.

실행 상한·검증 기록·임시 검사 보존 등 운영 정책은 [프로젝트 관리 규칙의 검증 정책](project-management.md#verification)을 따른다.

## 소통 포맷 · 내용 유형에 맞는 매체를 고른다 {#media}

- [AI-018][-] **Cognitive Fit · Media Richness · Executable Specification** — 소통 포맷은 내용 유형에 맞춘다: 느낌·방향처럼 해석이 갈리는 것일수록 풍부한 매체(무드보드·참고 작품·이미지)로, 규칙·계약·설정·API처럼 확정된 것일수록 간결한 매체(코드·스키마·실행 가능한 목업 그대로 + 의도·제약 1~2줄)로 한다. 시각 결과는 이미지, 시간에 따른 변화는 스토리보드·키프레임·영상과 상태 다이어그램, 구조·관계는 코드로 그린 다이어그램, 개별 값 조회는 표, 패턴·추세는 차트, 절차는 번호 목록이다. 한 메시지에 여러 유형이 있으면 유형마다 나눠 쓴다. 위반 판별: 코드로 적을 수 있는 규칙·계약을 산문으로 적었거나, 시각 결과·구조·느낌을 문단으로만 설명했다.

용어: **Cognitive Fit** — 표현 형식이 과제·내용 유형과 맞을 때 이해와 판단이 빨라진다는 이론(표 vs 그래프 연구). **Media Richness** — 메시지의 모호성이 높을수록 단서가 많은 풍부한 매체가, 낮을수록 간결한 매체가 맞다는 이론(Daft & Lengel). **Executable Specification / Specification by Example** — 요구·규칙을 산문이 아니라 실행하거나 그대로 가져다 쓸 수 있는 예시·코드로 적는 것. **Diagrams as Code** — 다이어그램을 Mermaid 같은 텍스트 코드로 정의해 diff·재생성이 되게 하는 것. **Mood Board** — 느낌·톤을 이미지·색·질감·참고 작품으로 모아 합의하는 도구. **Storyboard / Animatic** — 장면을 순서대로 그려 흐름을, 임시 사운드에 맞춰 이어 붙여 타이밍을 제작 전에 확인하는 것. **Lo-fi / Hi-fi Prototype** — 구조·흐름 확인용 거친 목업과 최종 외형·상호작용 확인용 정밀 목업. **C4 Model** — 소프트웨어 구조를 Context·Container·Component·Code 4단계 다이어그램으로 청중별로 나눠 보여 주는 방법.

하나의 축으로 정리하면 **모호성**이다. 해석이 갈릴수록 단서가 많은 매체(이미지·참고 작품·영상)로 가고, 확정될수록 단서가 적고 정확한 매체(표·코드)로 간다. Markdown 산문은 그 중간에 있고 기본값이 아니다. 코드로 쓸 수 있는 것을 말로 다시 쓰면 해석이 갈리고 원본이 2개가 된다([DEV-001](development.md#ownership)).

| 내용 유형 | 기본 포맷 | 쓰지 않는 것 | 근거 |
| --- | --- | --- | --- |
| 느낌·분위기·재미 방향·아직 수치 없는 목표 | 무드보드(참고 작품·장면·색·질감 이미지 3~8개) + 방향 1~2문장 | 긴 서술만, 표, 코드 | 조사: 디자인·게임 아트 관행은 무드보드. Media Richness: 모호한 메시지에는 풍부한 매체. 참고 작품명은 가장 짧은 공유 어휘([AI-000](#terminology)) |

| 구조·구성·관계: 모듈 의존, 데이터 흐름, 클래스·Mixin 관계, 화면 구성 | 코드로 그린 다이어그램(Mermaid 등). 시스템 구조는 C4처럼 청중별 단계로 나눈다. 화면 구성은 와이어프레임 | 문단 | 조사: C4 Model, Diagrams as Code. 관계는 2차원으로 봐야 빠진 것이 보이고 코드로 그리면 diff가 된다 |
| 규칙·계약·설정값·API·데이터 형식 | 코드·스키마·설정 파일·실행 가능한 예시(목업)를 그대로. 그 옆에 의도·제약 1~2줄(왜 이렇게 했는지). 코드로 쓴 규칙은 실제로 실행·검사되는 것이어야 한다 | 산문으로 재서술, 의도 없는 코드만, 검사되지 않는 예시 코드 | **사용자 확정(2026-10-30)**: 목업·코드가 제일 싸고 소통이 잘 된다. 조사: Executable Specification, Media Richness의 간결 매체. 코드가 SSOT. 보완(조사): 코드는 "무엇"만 담고 "왜"는 담지 못해 이유 없이 바뀌기 쉬우므로(Chesterton's Fence) 의도를 1~2줄 곁들인다. 실행·검사되지 않는 명세 코드는 원본과 어긋나도 아무도 모르므로(spec drift) 검사 대상이어야 한다 |
| 개별 값 조회·여러 항목의 정확한 수치 비교 | 표 | 나열 문장, 차트 | 조사: Cognitive Fit(표는 정확한 값 읽기). 열을 맞춰야 빠진 칸이 보인다 |
| 패턴·추세·시간에 따른 수치 변화 | 차트(연속 변화는 선, 항목 비교는 막대) | 표만 | 조사: Few — 패턴·추세는 그래프, 연속 변화는 선·개별 값 비교는 막대 |
| 순서가 있는 절차·체크 | 번호 목록 또는 체크리스트 | 문단 | 건너뛴 단계가 보인다 |

적용 방법:

- 쓰기 전에 유형을 먼저 고른다. 한 메시지·문서에 유형이 섞이면 유형별로 블록을 나누고 각각 맞는 포맷으로 쓴다.
- 규칙 문서도 같다. 이 레포의 규칙 줄은 ID·용어·판별이 있는 고정 형식이고, 표기 규약·검사는 산문이 아니라 `tools/build-rules.py` 코드가 원본이다.
- 포맷을 바꿀 수 없는 채널(이미지 첨부 불가 등)에서는 가장 가까운 포맷으로 대체하고 대체했음을 밝힌다([AI-007](#known-unknowns)).
- 코드·목업으로 쓴 규칙은 "작업 과정에서 자연히 남는 것"을 우선한다: 설정 파일, 스키마, 변환기 검사, 시나리오 E2E처럼 실제로 실행되는 것. 실행되지 않는 설명용 코드 조각은 산문과 같은 정도로 어긋난다. 이 레포에서는 `tools/build-rules.py --check`가 규칙 줄의 검사다.

## 핵심 원칙 {#principle}

- [AI-001][-] **XY Problem 회피 · Specification by Example** — 작업 순서는 의도 정리 → 최소 한 번 검색·비교 → 구체 동작 확정 → 구현 → 같은 사례로 검증이며, 용어가 맞았다는 이유로 사용자 의도를 이해했다고 간주하지 않는다. 위반 판별: 검색·비교 기록이나 확정한 동작 사례 없이 구현을 시작했다.

용어: **XY Problem** — 사용자가 진짜 목표(X) 대신 자기가 떠올린 해법(Y)을 말하고, 답하는 쪽이 Y만 처리해 X를 놓치는 문제. **Specification by Example** — 요구를 추상 문장이 아니라 구체 예시로 확정하는 방법.

```flow
의도 정리 → 최소 한 번 검색·비교 → 구체 동작 확정 → 구현 → 같은 사례로 검증
```

> [!IMPORTANT] **핵심**
> AI는 용어를 맞췄다는 이유로 사용자의 의도까지 이해했다고 간주하지 않는다.

모든 프로젝트의 AI 개발 작업에 적용하는 **사용자 확정 작업 원칙**이다. 구현 전에 요청한 목적·기대 결과와 일반적인 처리 방식을 함께 검토하고, 수용 가능한 구체 동작으로 방향을 정한다. 기술적으로 가능한 구현이어도 사용자가 기대한 결과와 다르면 완료가 아니다.

관련 원본: [공통 개발 규칙](development.md) · [프로젝트 관리 규칙](project-management.md). 이 문서는 AI의 요청 해석·작업 순서·공통 모듈 제약 처리 흐름을 소유하며 구조 원칙과 버전·검증 정책 전문을 복제하지 않는다.

## 구현 전 · 요구와 동작을 확정 {#workflow}

구현 전에 아래 순서로 요구를 동작으로 바꾼다. 각 절은 규칙 1개다.

### 기대 결과를 먼저 적는다 {#given-when-then}

- [AI-002][-] **Given-When-Then · YAGNI** — 구현 전에 "누가 어떤 상황에서 무엇을 하면 어떤 결과"를 적고, 요청에 없는 동작을 확정 사양으로 추가하지 않는다. 위반 판별: 기대 결과 문장이 없거나 요청에 없는 기능이 사양에 들어 있다.

용어: **Given-When-Then** — "상황(Given)–행동(When)–결과(Then)" 형식으로 인수 조건을 적는 BDD 서식. **YAGNI** — 지금 필요하지 않은 것은 만들지 않는다.

누가 어떤 상황에서 무엇을 하면 어떤 결과가 나와야 하는지 짧게 정리한다. 최신 저장소·기존 합의·제약을 읽고, 요청에 없는 동작을 확정 사양으로 추가하지 않는다.

### 항상 최소 한 번 검색·비교한다 {#prior-art}

- [AI-003][-] **Prior Art 조사 · Primary Source** — 요청 기능의 일반적 처리 방식과 공식 문서·일차 자료를 최소 한 번 검색해 실제 내용을 읽고, 현재 API·구현과 대조한다. 위반 판별: 검색어나 결과 제목만 보고 검토를 끝냈다.

용어: **Prior Art** — 같은 문제의 기존 해법·표준·관례. **Primary Source** — 2차 요약이 아닌 공식 문서·명세·원본 코드.

요청한 기능의 일반적인 처리 방식과 관련 공식 문서·일차 자료를 검색하고 실제 내용을 읽는다. 검색어만 입력하거나 결과 제목을 보는 것으로 검토를 끝내지 않는다. 현재 API·구현도 필요한 범위에서 대조한다.

### 일치와 차이를 기록한다 {#decision-record}

- [AI-004][-] **ADR (Decision Record)** — 사용자 요구 / 조사로 확인한 관례·기술 제약 / 이번에 적용할 동작을 나눠 비교하고 출처·조회 기준·가정을 남긴다. 위반 판별: 세 항목 중 하나가 기록에 없다.

용어: **ADR**(Architecture Decision Record) — 결정의 맥락·선택지·결정·결과를 한 기록으로 남기는 형식. 여기서는 "요구 / 관례·제약 / 적용 동작 + 출처·가정"이 그 항목이다.

사용자 요구 / 조사에서 확인한 관례·기술 제약 / 이번에 적용할 동작을 나눠 비교한다. 출처 링크·조회 기준과 중요한 가정을 남긴다. 검색 결과를 사용자 의도의 대체물로 쓰지 않는다. 기술적 관례와 게임 기획 선택을 구분한다. 관례와 요청이 다르면 그 차이·기술적 한계·대안을 설명하고 사용자가 의도한 결과를 보존한다.

### 동작 사례로 방향을 확정한다 {#examples}

- [AI-005][-] **Happy Path / Edge Case · Example Mapping** — 정상 사례와 해석이 갈리는 반례의 기대 결과를 구현 전에 확정한다. 위반 판별: 반례 사례가 0개다.

용어: **Happy Path** — 정상 입력의 기본 흐름. **Edge Case** — 경계·예외 입력. **Example Mapping** — 규칙마다 예시와 반례를 뽑아 요구를 확정하는 BDD 기법.

정상 상황과 해석이 갈리는 반례를 각각 적고 기대 결과를 정한다. 같은 용어라도 결과가 달라지는 해석을 비교한 뒤 구현한다. 사례 1개는 [공과 고양이](#damage-example)에 있다.

### 방향 확정은 매번 승인 대기가 아니다 {#two-way-door}

- [AI-006][-] **One-way / Two-way Door** — 되돌릴 수 없는 결정(One-way Door)만 선택지와 차이를 붙여 묻는다. 되돌릴 수 있는 결정(Two-way Door)은 해석이 갈리더라도 묻지 않고, 무엇을 어떻게 하기로 했는지 사용자가 바로 알아볼 수 있게 먼저 알린 뒤 진행한다. 이미 정한 내용을 반복 승인받지 않는다. 위반 판별: 되돌릴 수 있는 결정을 질문으로 멈췄거나, 해석이 갈리는 선택을 알리지 않고 진행했거나, 되돌릴 수 없는 결정을 묻지 않고 정했다.

용어: **One-way Door** — 되돌릴 수 없는 결정. 사용자 데이터·저장 포맷·외부 계약(API, 프로토콜)·공개된 산출물·삭제처럼 실행 뒤 원상복구에 큰 비용이 드는 것. **Two-way Door** — 되돌릴 수 있는 결정. 코드·문서·화면 값처럼 다음 커밋에서 바꾸면 끝나는 것.

| 상황 | 문 | 행동 |
| --- | --- | --- |
| 요청이 명확하고 되돌릴 수 있다 | Two-way | 근거를 적고 진행한다 |
| 해석이 갈리지만 되돌릴 수 있다 (예: “버튼 색 바꿔줘”에서 톤 선택) | Two-way | 고른 해석을 먼저 알리고 진행한다. 묻고 기다리지 않는다 |
| 요청이 명확하지만 되돌릴 수 없다 (예: 저장 포맷 필드명 변경) | One-way | 영향 범위와 선택지를 붙여 묻는다 |
| 해석이 갈리고 되돌릴 수 없다 | One-way | 묻는다 |

되돌릴 수 있는데도 질문으로 멈추면 사용자가 답할 때까지 작업이 서고, 틀린 해석이어도 작업이 끝난 뒤 한 번 고치면 되므로 알리고 진행하는 쪽이 비용이 적다. 알림은 “A로 하겠다”처럼 선택한 값이 바로 보이는 한 문장으로 쓴다. 선택의 근거·대안은 [AI-004](#decision-record)의 기록 항목이고, 해석이 갈리는 사례의 기대 결과 확정은 [AI-005](#examples)를 따른다. 이미 정한 내용을 반복 승인받지 않는다.

### 근거가 없으면 미확인을 먼저 알린다 {#known-unknowns}

- [AI-007][-] **Known Unknowns · Fail Loudly** — 검색이 막히거나 근거를 확보하지 못하면 검토 완료로 꾸미지 않고 미확인 범위와 영향을 먼저 알린다. 위반 판별: 미확인 범위 없이 "확인됨"으로 보고했다.

용어: **Known Unknowns** — 모른다는 사실을 아는 항목을 목록으로 드러낸다. **Fail Loudly** — 실패·결손을 숨기지 않고 즉시 드러낸다.

검색이 막히거나 근거를 확보하지 못하면 검토 완료로 꾸미지 말고 미확인 범위와 영향부터 알린다.

### 미지정 수치 초안 · 정규화와 기준값 파생 {#numeric-drafts}

- [AI-008][-] **No Magic Number · SSOT(기준값)** — 미지정 수치 초안은 사용자 지정값·확정 계약을 우선하고, 새 값은 100·50·25·1·0.5·0.25·0.1처럼 비교하기 쉬운 값을 후보로, 연관 수치는 기준값 하나에서 배율로 파생한다. 이미 합의·구현된 수치는 요청 없이 재정규화하지 않는다. 위반 판별: 서로 독립된 임의 상수가 연관 수치로 추가되었거나, 기존 수치가 요청 없이 바뀌었다.

용어: **Magic Number** — 출처·근거 없이 코드에 박힌 상수. **SSOT** — 값의 원본은 한 곳(기준값)이고 나머지는 거기서 파생한다.

> [!IMPORTANT] **새 초안에는 단순한 척도를, 연관 수치에는 하나의 기준값을 사용한다**

- **사용자가 지정한 값과 이미 확정된 계약을 우선한다.** 이 원칙은 새로 필요한 미지정 수치의 초안을 제안할 때 적용한다. 단위와 적정 범위를 확인한 뒤 100, 50, 25, 1, 0.5, 0.25, 0.1처럼 비교하기 쉬운 값을 후보로 삼는다. 해당 수치의 규모에 맞는 값을 선택하며, 이 목록은 닫힌 선택지나 모든 게임에 강제하는 기본값이 아니다.
- **연관 수치는 기준값에서 파생한다.** 가능하면 기본값 또는 기준 스탯 하나를 원본으로 두고, 다른 값은 배율·비율로 표현해 서로 독립된 임의 상수로 만들지 않는다. 예를 들어 공격력이 40이라면 미지정 스킬 공격력의 초안으로 공격력 × 1.5 = 60을 제안할 수 있다. 1.5배는 관계를 설명하는 예일 뿐 보편 계수는 아니다. 서로 다른 규칙의 수치라면 독립 기준과 근거를 명시한다.
- **기존 게임 수치를 이 규칙으로 다시 쓰지 않는다.** 현재 프로젝트에 이미 합의되거나 구현된 값, 합성·희귀도·드롭 확률 등은 별도 요청 없이 변경·재정규화하지 않는다. 초안의 단위·기준값·파생식과 가정은 함께 기록하고, 최종값은 프로젝트의 기획과 검증으로 확정한다.

게임 기획의 적용 위치는 [게임 기획 가이드의 수치 초안 절](game-design.html#numeric-drafts), 스탯의 의미·단위·계약은 [공통 STAT 사전](stats.html)을 따른다.

## 구현 중 · 공통 모듈 개선과 소비 게임 적용 {#shared-modules}

- [AI-009][-] **Upstream First · Rule of Three** — 공통 모듈의 한계·버그를 만나면 원인과 최소 재현을 확보하고, 재사용성·API 책임 범위·하위 호환·비용을 기준으로 공통 개선 여부를 스스로 판단해 끝까지 반영한다. 공통이면 모듈 수정 → 회귀 검증 → 버전 판정·배포 → 소비 게임 반영·검증, 게임 고유면 제품 계층에 두고 근거를 기록한다. 위반 판별: 제약만 보고하고 멈췄거나 게임 쪽 임시 우회로 끝냈다.

용어: **Upstream First** — 수정은 사용처(하류)가 아니라 공통 모듈(상류)에 먼저 넣고 사용처로 내린다. **Rule of Three** — 같은 요구가 3번 반복될 때 공통화한다.

> [!IMPORTANT] **공통 모듈 제약은 스스로 판단하고 끝까지 반영**

제품 구현·마이그레이션 중 공통 모듈의 한계나 버그를 만나면 원인과 최소 재현을 먼저 확보한다. 재사용성, 공통 API의 책임 범위, 하위 호환성, 수정·검증·배포·Consumer 비용을 기준으로 공통 개선 적합성을 스스로 판단하며, 매번 사용자 지시를 기다리지 않는다. [공통 개발 규칙](development.md)의 DRY·YAGNI 원칙도 따른다.

- **공통에 맞으면:** 공통 모듈을 수정하고 회귀 검증한 뒤 [공통 프로젝트 관리 규칙](project-management.md)에 따라 버전을 판정하고 공식 배포한다. 이어 소비 게임에 반영하고 실제 게임에서 검증한다.
- **게임 고유 요구면:** 공통 API를 넓히지 않고 제품 계층에 두며, 공통화하지 않은 근거를 기록한다.

제약만 보고하고 방치하거나 제품별 중복·임시 우회 구현으로 끝내지 않는다. 기존 승인 범위와 보안 제한을 지키며 넓히거나 우회하지 않는다.

### SVG 자산 · 원본을 보존하고 공통 브라우저 로더에서 한 번 컴파일 {#svg-assets}

- [AI-010][-] **SSOT(원본) · Derived Artifact 비커밋 · Memoization** — SVG 정적 벡터 아트는 원본 SVG만 자산으로 포함하고, 공통 브라우저 로더가 시작 시 1회 컴파일·캐시하며, 생성된 메시를 배포물에 넣지 않고, 원본과 렌더를 나란히 비교한다. 위반 판별: Base64 메시나 generated resources가 번들에 있거나, 프레임마다 SVG를 파싱한다.

용어: **Derived Artifact** — 원본에서 재생성할 수 있는 산출물. 저장소·배포물에 넣지 않는다. **Memoization** — 같은 입력의 계산 결과를 한 번만 만들고 캐시한다.

> [!IMPORTANT] **SVG 정적 벡터 아트의 단일 원본은 SVG이며, 생성된 메시를 게임에 포장하지 않는다**

- **원본 SVG를 유지한다.** SVG로 제공된 정적 벡터 아트는 원본 SVG만 게임의 해당 자산으로 포함하고 이를 형상·뷰박스·식별자·메타데이터·작성된 애니메이션의 단일 기준으로 삼는다. 메시에 맞춘 별도 복제본을 만들거나 메타데이터·애니메이션을 지우지 않는다. 동적 효과는 SVG 규칙으로 덮어씌우지 않고 프로젝트에 맞는 셰이더·절차적 방식을 계속 사용한다.
- **공통 브라우저 로더가 시작 시 한 번 컴파일한다.** 게임 시작 때 원본 SVG를 검증하고 인덱스드 기하(Indexed Geometry)로 컴파일한 뒤, 콘텐츠 식별자로 캐시하여 GPU에서 유지·재사용한다. 프레임마다 파싱·삼각분할·컴파일하지 않는다. 변환과 지원되는 애니메이션은 보유한 기하에 적용하고 원본 SVG를 반복 컴파일하지 않는다.
- **SDK의 공백을 소비 게임의 산출물로 감추지 않는다.** Node 전용 소스 도구만 제공되는 SDK를 브라우저에서 직접 import할 수 없다는 사실을, 소비 게임이 빌드 때마다 대형 메시를 미리 만들어 포함해야 한다는 요구로 오해하지 않는다. 브라우저 로더·내보내기·런타임 API가 빠졌다면 공통 SDK에서 먼저 설계·구현·검증한다. 소비 게임마다 별도 컴파일러나 메시 복사본을 추가하지 않는다.
- **입력과 실패를 제한하고 드러낸다.** 공통 로더는 허용하는 SVG 기능과 소스 크기·복잡도·처리 시간 상한을 문서화하고 검증한다. 다운로드·파싱·컴파일 실패는 자산 경로·실패 단계·원인을 보고한다. 일시적인 전송 오류만 최대 한 번 재시도하고, 잘못되었거나 지원하지 않는 소스는 재시도하지 않는다. 래스터 이미지로 조용히 대체하거나 애니메이션을 버리지 않는다.
- **생성된 확장 메시를 배포물에 넣지 않는다.** 미리 계산한 메시를 Base64로 게임 JS/HTML에 박거나 generated resources로 저장소·배포 패키지에 포함하지 않는다. SVG 경로의 런타임 컴파일은 공짜라고 가정하지 않는다. 초기 로드 시간·컴파일 시간·GPU 메모리를 실제 브라우저에서 측정하고, 프로젝트별 패키지 크기 예산을 두어 빌드/리뷰에서 큰 재생성 산출물의 포함을 잡는다.
- **원본과 게임 화면을 대조한다.** 같은 뷰박스·크기·색상·애니메이션 상태에서 원본 SVG와 게임 렌더를 나란히 비교한다. 모양·레이어·메타데이터·애니메이션의 기대 결과와 오류·미검증 범위를 기록한다. 일반 실행 성공이나 파일 크기만으로 시각 검증을 대신하지 않는다.

**나쁜 예 · Farm 번들 사례** 원본은 SVG 5개 합계 66,621 B였지만, 최종 게임 번들은 11.22 MB이고 그중 98.37%가 확장된 생성 정점 데이터였다. Node 전용 SDK 소스 도구를 “브라우저에서 쓸 수 없다”로 오해해 미리 만든 대형 메시를 게임 번들에 포함하면, 작은 원본을 유지하는 대신 전송·저장 크기만 크게 늘어난다.

**요구에 맞는 처리** SVG 원본만 자산으로 포함하고 공통 SDK의 브라우저 로더를 바로잡아 시작 시 한 번 컴파일·캐시·재사용한다. 해당 게임에서 원본과 렌더를 비교하고 시작 비용·메모리·패키지 크기를 측정한다.

이 규칙은 SVG로 제공된 정적 벡터 아트의 입력·렌더·패키징 계약이다. 모든 그래픽을 SVG로 강제하지 않으며 동적 VFX·절차적 표면에는 해당 표현 방식을 쓴다. 검증 기록의 범위·PASS/FAIL/미실행 구분과 배포 확인은 [공통 프로젝트 관리 규칙의 검증 정책](project-management.md#verification-policy)을 따른다.

### 자동 저장 · 변경 확인과 저장 비용 측정 {#autosave}

- [AI-011][-] **Dirty Flag · Debounce(maxWait) · Profile Before Optimizing** — 자동 저장은 지속 상태의 revision/dirty가 바뀔 때만 묶어서(maxWait 상한 포함) 하고, 직렬화·검증과 전체 복원을 분리하며, 큰 직렬화와 동기 I/O를 렌더 경로에서 호출하지 않고, 비용을 실측한다. 위반 판별: 프레임 함수에서 변경 확인 없이 전체 스냅샷 직렬화나 localStorage.setItem을 호출한다.

용어: **Dirty Flag** — 변경 표시가 있을 때만 처리한다. **Debounce(maxWait)** — 연속 변화를 묶되 상한 시간 안에는 반드시 한 번 처리한다. **Profile Before Optimizing** — 측정 없이 원인과 개선 폭을 단정하지 않는다.

> [!IMPORTANT] **고정 주기보다 dirty 감지, 배치 저장, 복원 경계를 먼저 설계한다**

- **3초 저장을 일률적으로 금지하지 않는다.** 짧은 주기가 복구 목표에 맞을 수 있다. 안티패턴은 변경 확인 없이 전체 상태를 자주 스냅샷·직렬화하고, 즉시 전체 복원·검증과 동기 I/O까지 렌더/프레임 경로에서 반복하는 조합이다. 허용할 데이터 손실 구간과 저장 빈도를 사용 흐름에 맞춰 정한다.
- **저장할 상태의 변경 revision 또는 dirty 상태를 확인한다.** 렌더 프레임이나 일시적인 물리 변화 전체를 자동으로 저장 대상으로 삼지 말고, 지속돼야 할 게임 상태가 마지막 저장본과 달라진 때만 저장한다. 짧은 연속 변화는 coalescing/debounce로 묶되 `maxWait` 상한을 두어 변화가 계속될 때 저장이 무기한 밀리는 기아를 막는다. 보상 수령·전투 종료 등 복구 목표상 중요한 체크포인트도 정의한다.
- **직렬화·검증과 hydrate/restore를 분리한다.** 저장 시 필요한 스냅샷·직렬화·경량 무결성 확인과 전체 normalize·마이그레이션·객체 복원은 별도 경로로 둔다. 전체 복원은 시작·가져오기·마이그레이션·복구처럼 필요한 시점에 하고, 저장마다 문자열을 다시 파싱해 Garden 전체를 재구축하지 않는다. 비동기 저장은 저장한 revision을 확인하고 완료 순서를 관리해 오래된 쓰기가 새 상태를 덮지 않게 한다.
- **큰 직렬화와 저장 I/O를 렌더 핫패스에서 수행하지 않는다.** Web Storage의 `localStorage`는 동기식이다. 큰 스냅샷·검증·복원이나 `getItem`/`setItem`을 `requestAnimationFrame`/렌더 경로에서 호출하지 않는다. 저장량·복구 요구가 맞는지 확인한 뒤 IndexedDB 같은 비동기 저장소나 Worker 처리를 평가한다. IndexedDB를 선택해도 JSON 변환이 자동으로 메인 스레드를 벗어나는 것은 아니므로 전체 경로를 측정한다.
- **페이지 종료 이벤트 하나에 영속성을 맡기지 않는다.** 상태 변경 뒤의 안전한 체크포인트와 목표한 저장 간격을 기본으로 둔다. 탭이 숨겨질 때 `visibilitychange`를 추가 저장 기회로 활용할 수 있지만, `pagehide`나 종료 직전 이벤트만으로 저장이 보장된다고 가정하지 않는다. 모바일에서 종료 이벤트가 생략될 수 있다.
- **실패와 여러 탭의 경합에서 원본 저장을 보호한다.** 저장 공간 부족·접근 거부·스키마 오류·마이그레이션 실패·다른 탭의 동시 변경을 각각 다룬다. 충돌한 탭이 최신 저장을 덮지 않게 하고, 복구 가능한 오류를 알리며 원본 데이터를 조용히 초기화하거나 잃지 않도록 한다. 탭 간 최신성·복구 동작도 실제 브라우저에서 확인한다.
- **비용과 사용자 지연을 실제로 측정한다.** 상태 크기·기기·브라우저·변경 없음/변경됨 조건을 기록하고 스냅샷, 직렬화, 검증·복원, 저장 I/O 시간을 나눠 관찰한다. 프레임 시간과 저장 호출 빈도도 비교한다. 프로파일이나 추적 결과 없이 특정 코드 경로를 사용자가 느낀 렉의 유일 원인이라고 단정하지 않는다.

**나쁜 예 · Farm 0.6.1 저장 경로** [지정 커밋의 `farm-app.js`](https://github.com/byh-playground/budmori-io/blob/990349c08a260bc4cf147b7269f4d295b6296e40/src/farm-app.js#L169-L185)에서 `frame()`이 매 프레임 `sync()`를 부르고, `sync()`는 3초를 넘으면 저장 revision/dirty 확인 없이 `persist()`를 호출한다. 집 화면에서도 프레임 함수는 계속 `sync()`를 실행하며, 일시 정지는 저장 조건을 막지 않는다. 집 화면 전환·창 blur·문서 숨김·pagehide에도 별도 저장 경로가 있다.

[`FarmStorage`](https://github.com/byh-playground/budmori-io/blob/990349c08a260bc4cf147b7269f4d295b6296e40/src/farm-storage.js#L10-L12)는 `snapshot()` 결과를 직렬화한 뒤 저장 직전에 다시 parse하고 [`restore()`](https://github.com/byh-playground/budmori-io/blob/990349c08a260bc4cf147b7269f4d295b6296e40/src/farm-state.js#L11-L37)해 전체 Garden을 정규화·검증·재구축한 다음 `localStorage.setItem()`을 호출한다. 매번 전체 검증·복원이 필요한지, 저장본이 실제 변경됐는지 분리하지 않은 경로가 반복 비용을 만든다. 코드에서 불필요한 작업 경로는 확인되지만 사용자 기기에서의 지연 기여도나 유일 원인은 측정으로 확인해야 한다.

**더 나은 방향** 영속 상태 변경 revision으로 저장을 걸고, 저장 요청은 묶되 `maxWait`와 중요한 체크포인트로 복구 창을 보장한다. 직렬화·기본 무결성 확인은 복원·마이그레이션과 분리하고, 저장 경로를 프레임 핫패스 밖으로 옮긴 뒤 실제 기기 프로파일로 비용을 비교한다. 저장 실패·탭 경합·원본 보존 시나리오도 함께 검증한다.

이 항목은 저장 주기 숫자 하나를 금지하는 규칙이 아니다. 무변경 상태의 반복 전체 직렬화·복원과 동기 I/O를 핫패스에서 피하고, 내구성 목표와 실측 근거에 맞춰 체크포인트를 고른다.

### 논리 틱과 물리 하위 단계 · 이름이 아니라 호출 범위를 검증 {#simulation-cadence}

- [AI-012][-] **Fixed Timestep / Sub-stepping · Functional ≠ Non-functional** — 논리 틱은 총 dt로 1회 갱신하고 이동·충돌처럼 세분화가 필요한 작업만 물리 하위 단계로 반복하며, 빈도 × 대상 수 × 중첩으로 총량을 계산하고 실측한다. 기능 E2E 통과를 성능 근거로 쓰지 않는다. 위반 판별: AI·생성/소멸·전체 인덱스 재구축이 물리 하위 단계 횟수만큼 반복된다.

용어: **Fixed Timestep / Sub-stepping** — 고정 dt로 갱신하고, 물리처럼 필요한 것만 더 작은 단계로 반복한다. **Functional ≠ Non-functional** — 기능(동작) 검증과 비기능(성능) 검증은 별개다.

> [!IMPORTANT] **필요한 물리만 세분화하고 전체 갱신의 중복을 비용으로 계산한다**

- **진입 루프 → 논리 틱 → 하위 단계 → 실제 호출 범위**를 정적으로 추적한다. 함수명·주석의 “물리”를 믿고 기존 월드 갱신을 그대로 감싸지 않는다. 빈도 × 대상 수 × 중첩 반복으로 초당 총량과 catchup 한 번의 최악 작업량을 계산한다.
- **물리·의사결정·렌더·저장의 주기 소유자를 나눈다.** AI·생활·검색·성장·생명주기·스킬 판단·전체 정리를 물리 횟수만큼 반복하지 않는다. 이동·접촉처럼 세분화가 필요한 작업만 하위 단계에 두고, 총 dt와 지속시간·생성/소멸·공격 사건·Signal의 단일 실행 책임을 유지한다. dt 없는 접촉 계수와 표시 캡처 경계도 함께 검토한다.
- **필요 횟수를 근거와 계측으로 정한다.** 이동량·몸 크기·충돌 방식과 고속/밀집 반례를 확인하고, 실제 논리/물리/catchup 횟수와 AI·공간 인덱스·충돌·렌더·저장 비용을 구분해 기록한다. 기존 공통 진단 API를 우선 사용하고, 짧은 요약과 동일 프레임의 경량 숫자 기록으로 추적 가능하게 한다. 부모·자식 시간의 중첩과 CPU/GPU 미측정 범위를 명시한다.
- **기능 E2E 통과를 성능 근거로 쓰지 않는다.** 속도 보존·이벤트 중복·관통·접촉을 기능 사례로 검증하고, 빈도·작업량·실제 시간은 별도로 측정한다. 프레임 분산으로 총량 문제를 숨기거나 측정 없이 실제 기기 개선 배율을 단정하지 않는다.

**나쁜 예 · Farm 0.8.4 전체 월드 반복** [FarmSession.advance](https://github.com/byh-playground/budmori-io/blob/c95d6f6eef301983a48f730ebadca4403cab29cf/src/farm-session.js)는 20Hz 틱마다 `Garden.step(1/120)`을 6번 실행했다. [실제 step](https://github.com/byh-playground/budmori-io/blob/c95d6f6eef301983a48f730ebadca4403cab29cf/src/farm-model.js)에는 AI·생활·먹이·번식/합성·성장·스킬·효과 정리와 공간 인덱스 전체 재구축까지 들어 있었다. 물리만 6회라고 설명했지만 전체 월드가 초당 120회였고, catchup 4틱이면 한 번에 24회였다. 기능 E2E 통과만으로 필요한 횟수나 성능을 정당화할 수 없다.

**요구에 맞는 처리** 논리는 한 틱의 총 dt로 한 번 갱신하고, 필요한 이동·충돌만 근거 있는 하위 단계로 나눈다. 전체 rebuild/정리와 임시 할당을 반복 경로에서 제거하고 이동 뒤 인덱스 정확성을 유지한다. 변경 전후 호출 수·시간·이벤트 수와 같은 동작 사례를 함께 확인한다.

20Hz나 120Hz 자체를 금지하는 규칙이 아니다. 고정 시간 간격과 물리 세분화는 유효한 도구이며, 금지 대상은 필요 없는 전체 월드 반복을 이름과 기능 통과로 정당화하는 방식이다. [Box2D의 Simulation](https://box2d.org/documentation/md_simulation.html)은 물리 solver를 나누는 범위와 정확도/비용을, [Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)은 dt 보존과 누적 작업량의 한계를 설명하는 일차 참고다. 해당 예시의 횟수를 모든 게임에 그대로 적용하지 않는다.

## 사례 · 공과 고양이로 요구 해석 {#damage-example}

특정 게임의 요청 해석 사례다. “충격량 기반 피해”라는 표현만으로 양쪽 공통 solver 충격량이나 상대속도를 피해식에 연결하면, **고양이가 정지한 공에 달려들어도 고양이가 피해를 받는** 결과가 생길 수 있다. 이 사례에서 사용자가 원한 결과와 다르다.

**나쁜 처리** “충격량 기반”이라는 단어만 보고 익숙한 공통 충돌 공식을 적용하고, 양쪽의 공통 solver 충돌값이 커졌다는 이유로 고양이 자체 이동도 같은 피해로 처리한다. 자료를 찾았거나 물리 충돌 테스트를 통과했다는 이유로 사용자의 요구가 충족됐다고 단정한다.

**요구에 맞는 처리** 일반 물리의 충돌 처리와 게임에서 피해를 주는 공격원의 의미를 비교하고, 어떤 장면에서 누가 피해를 받아야 하는지 먼저 정한다. 고양이 자체 속도가 아니라 **고양이에게 날아오는 공격원인 공의 동작**이 피해를 결정한다는 계약을 확정하고, solver의 물리 반작용과 공격원별 게임플레이 피해를 구분한다. 기존 합의로 정할 수 없는 부분만 묻는다.

- **반례:** 고양이가 정지한 공으로 달려듦 → 고양이 자체 속도만으로 고양이 피해가 생기지 않아야 한다.
- **공격 사례:** 공이 고양이에게 날아옴 → 공의 공격 동작에 따른 피해 계약을 적용한다. 피해를 산정하는 동작·조건·수식은 해당 게임의 합의로 정한다.
- **동일 사례 검증:** 구현 뒤 두 상황을 다시 실행해 물리 반응과 피해 결과를 각각 확인한다. 공의 동작은 같고 고양이 자체 속도만 달라질 때 의도와 다르게 피해를 키우지 않는지도 확인한다.

이 예시는 일반 물리의 절대 법칙이나 모든 게임의 공통 피해식을 정하지 않는다. 다른 공격원·장르·기획에서는 다른 피해 계약이 가능하다. 핵심은 용어가 아니라 **요청한 원인과 결과**를 구현하는 것이다.

- 요청 의도·기대 결과와 기존 합의를 정리했는가?
- 일반적인 처리 방식·공식/일차 자료를 최소 한 번 검색해 읽고 비교했는가?
- 관례·기술 제약과 사용자 기획 선택의 차이를 근거와 함께 구분했는가?
- 정상 사례와 반례의 기대 동작을 확정하고, 중요한 미결정만 최소 질문했는가?
- 공통 모듈 제약의 원인·최소 재현과 개선 적합성을 판단했는가? 공통에 맞으면 소비 게임까지 검증하고, 게임 고유면 제품 계층에 둔 근거를 기록했는가?
- SVG 정적 벡터 아트라면 원본만 배포하고 공통 브라우저 로더에서 한 번 컴파일해 캐시·재사용했는가? 생성 메시·무제한 재시도·래스터 대체가 없고 원본과 렌더를 비교했는가?
- 자동 저장은 지속 상태가 바뀔 때만 묶어서 처리하고 최대 대기시간·체크포인트를 두었는가? 직렬화와 전체 복원, 동기 I/O를 렌더 경로에서 분리하고 오류·다중 탭·원본 보존을 실측·검증했는가?
- 구현 뒤 같은 사례로 확인하고 실제 결과·미검증 범위를 보고했는가?
- 변경한 장면·파라미터를 실제로 실행해 관찰물(스크린샷·키프레임·로그)을 직접 보고, 그 관찰물을 보고에 첨부했는가?
- 관찰물과 임시 검증 코드를 폐기했는가? 레포에 남긴 테스트·검사는 재사용 근거가 있는가?
- 관찰물을 표준 절차(결정론 확인 → 캡처 진입점 → 장면 지정 → 캡처 → 전후 비교 → 보고 → 폐기)로 얻고 재현 파라미터를 적었는가?
- 보고·문서의 각 부분을 내용 유형에 맞는 포맷(글·이미지·시퀀스·다이어그램·코드·표·목록)으로 썼는가? 코드로 쓸 수 있는 규칙을 산문으로 적지 않았는가?

## 근거와 문서 역할 {#sources}

AI 개발 규칙 원본 작성 2026-10-15 · 공통 모듈 원칙 갱신 2026-10-16 UTC · 같은 날 Farm 0.6.1 저장 경로 사례를 확인해 추가했다. 코드상 반복 비용은 근거로 설명하되 사용자 기기 지연의 원인 단정은 하지 않는다. “최소 한 번 검색·비교하고 구체 사례로 의도를 확정한다”와 “공통 모듈 제약을 스스로 판단해 적합한 개선을 Consumer까지 반영한다”는 **사용자 확정 작업 원칙**이다. 공과 고양이는 사용자 요구를 해석하는 사례이며 새로운 보편 물리 규칙이 아니다.

[NASA · How to Write a Good Requirement](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)는 필요한 결과와 구현 방법을 구분하고 명확성·가정·검증 가능성을 살피는 공식 참고 자료다. [NASA · System Design Processes](https://www.nasa.gov/reference/4-0-system-design-processes/)는 사용 시나리오로 기대를 정리하고 설계를 기대 결과와 대조하는 접근을 설명한다. 이 자료가 AI의 검색 횟수나 이번 게임의 피해식을 정한다는 뜻은 아니다.

자동 저장 사례의 고정 코드는 [Farm 0.6.1의 프레임·저장 호출](https://github.com/byh-playground/budmori-io/blob/990349c08a260bc4cf147b7269f4d295b6296e40/src/farm-app.js#L169-L185), [저장 어댑터](https://github.com/byh-playground/budmori-io/blob/990349c08a260bc4cf147b7269f4d295b6296e40/src/farm-storage.js#L10-L12), [스냅샷·복원](https://github.com/byh-playground/budmori-io/blob/990349c08a260bc4cf147b7269f4d295b6296e40/src/farm-state.js#L11-L37)에서 확인할 수 있다. 브라우저 근거: [MDN Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)의 동기 동작, [IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)의 비동기 트랜잭션, [visibilitychange](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)의 hidden 전환, [pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event)의 모바일 신뢰성 한계를 참고한다. 이는 특정 저장소 선택을 강제하지 않으며 복구 목표와 실제 측정이 선택 기준이다.

[공통 개발 규칙](development.md)은 구조·코딩 원칙, [관리 규칙](project-management.md)은 버전·검증·Git·배포 정책, **이 문서**는 AI의 요청 해석·검색 비교·동작 확정, 공통 모듈 제약 처리, [SVG 자산의 원본·브라우저 렌더 파이프라인](#svg-assets), [자동 저장 비용·검증 기준](#autosave), [논리 틱과 물리 하위 단계](#simulation-cadence)를 소유한다. 검증·배포 정책 전문은 중복하지 않는다.

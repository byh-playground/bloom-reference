예약 버그 탐지와 자동 수정

출근 중 실행하는 QA의 범위, 처리 기준, 판단 가능한 짧은 이력을 정리한 운영 레퍼런스.

핵심 요구
핵심 버그 현상 → 원인 → 수정 방안 순서로, 코드를 모르는 13살도 바로 이해할 수 있게 짧게 쓴다. 전체 10줄은 최대 길이이며 더 짧게 전달할 수 있으면 압축한다. 이력만 읽고 문제와 처리 방향을 판단할 수 있어야 한다.

분류: 개발 운영 · 자동 QA · 버그 보고 | 관련: 공통 프로젝트 관리 규칙 · 공통 개발 규칙 · 레퍼런스 목록

1.개요

예약 QA는 정해진 시간에 현재 실행물을 검사하고, 발견한 문제를 재현하여 사람이 처리할 수 있는 결과로 남기는 작업이다. 효과는 발견한 개수보다 신규 문제의 재현 가능성, 사용자가 판단할 수 있는 이력, 실제 채택되는 수정으로 평가한다.

권장 기본 운영
자동 탐지·재현·중복 확인·짧은 기록을 기본으로 하고, 기대 동작과 원인이 확실한 작은 문제만 격리된 작업 공간에서 수정 PR까지 만든다.

이 문서는 조사한 사실과 BLOOM에 적용할 제안을 구분한다. 구체적인 예약 시각, 검사 시간, 수정 상한은 초기 실행에서 측정해 조정한다. 문서 수록은 실제 스케줄러 등록이나 게임 검증 완료를 뜻하지 않는다.

제품의 기대 동작은 해당 프로젝트의 개발 계약과 사용자 지시에서 확인한다. 밸런스·표현 의도나 아키텍처를 자동 QA가 새로 정하지 않는다. 버전·Stable·Git·배포 기준은 공통 프로젝트 관리 규칙과 각 저장소의 지침을 따른다.

2.전체 이력 10줄 원칙

한 실행의 전체 보고는 최대 10줄이며, 같은 판단을 할 수 있다면 더 짧게 쓴다. 기본 흐름은 핵심 버그 현상 → 원인 → 수정 방안이다. 항목별 줄 수나 문장 수는 정하지 않는다. 줄 수를 채우거나 문단을 한 줄에 몰아 제한을 피하지 않는다.

압축 기준
무슨 문제가 생겼고, 왜 생겼으며, 어떻게 고칠지 바로 이해할 수 있으면 충분하다. 같은 뜻을 반복한 문장과 판단에 영향을 주지 않는 정보는 뺀다.

핵심 버그 현상에는 사용자에게 일어난 문제와 중요한 불편·손해를 함께 쓴다. 원인에는 확인한 이유를 쉬운 말로 쓰고, 아직 모르거나 추정이면 그대로 표시한다. 수정 방안에는 무엇을 바꿀지 쓰며, 원인이 불명확하면 고치기 전에 무엇을 더 확인할지 쓴다.

발생 횟수, 검사 범위, 실행물 식별자와 미검증 사실은 판단에 필요한 만큼만 덧붙인다. 자세한 재현 순서·코드·로그·전체 SHA는 증거에 보존하고 필요하면 링크로 연결한다. 원인이 불명확하거나 검증이 막혀 판단을 제한하는 사실은 압축하면서 숨기지 않는다.

조사할 문제 수는 검사 예산과 중요도로 정하며 보고 양식에 맞춰 고정하지 않는다. 같은 원인은 묶고 누적된 항목은 변한 상태만 남긴다. 여러 발견을 압축할 때도 중요한 문제와 미처리 상태를 누락하지 않는다.

2.1.ELI13 설명을 기본으로

ELI13은 코드를 모르는 13살에게 설명하듯 쓰는 기준이다. 쉬운 말로 정확하게 설명하며 원인·위험·불확실성도 그대로 전달한다. 읽는 사람을 어린아이처럼 대하거나 과장된 비유를 덧붙이지 않는다.

  • 장면부터: 플레이어가 누른 버튼이나 하던 행동과 눈에 보이는 결과를 먼저 쓴다.
  • 차이를 바로: 원래 어떻게 되어야 하는지와 지금 무엇이 다른지 붙여 쓴다. 확인한 금액·횟수 등 구체적인 값이 도움이 되면 사용한다.
  • 불편을 연결: “환불 누락”을 “취소하면 건물도 못 짓고 돈만 잃는다”처럼 사용자에게 생기는 손해로 풀어 쓴다.
  • 원인도 쉽게: 함수명·오류 코드·개발 용어는 증거에 둔다. 본문에는 “취소할 때 돈을 돌려주는 처리가 빠졌다”처럼 풀어 쓴다. 필요한 용어는 처음에 짧게 설명한다.
  • 결정과 이유: “수정 권장”만 적지 않는다. 왜 지금 고칠지, 왜 더 확인해야 할지와 실제로 확인한 결과를 쉬운 말로 쓴다.
같은 문제를 더 직관적으로 설명하기

기술 표현: “건설 예약 취소 경로에서 환불 누락.”

ELI13: “짓기 전에 건설을 취소해도 돈이 돌아오지 않아, 건물도 못 짓고 돈만 잃는다.”

2.2.판단 가능한 이력 예시

아래는 기본 흐름을 짧게 보여 주는 가상 예시이며 실제 발견·검증 결과가 아니다. 이 예시의 줄 수를 맞출 필요는 없다.

핵심 버그 현상: 짓기 전에 건설을 취소하면 건물도 못 짓고 돈만 잃는다.

원인: 짓기 전에 취소했을 때 돈을 돌려주는 처리가 빠져 있다.

수정 방안: 짓기 전에 취소하면 쓴 돈을 전부 돌려주도록 고친다.

보고 완료 판정
코드를 모르는 독자가 현상·원인·수정 방안을 이해하고 판단할 수 있는가? 뜻을 잃지 않고 더 줄일 수 있는가? 이해가 부족하면 보완하고 같은 판단이 가능하면 압축한다. 전체 10줄 이내는 이 과정의 상한이다.

3.조사한 운영 사례

레퍼런스출처에서 확인한 사실BLOOM 적용 해석
GitHub Next · Adhoc QA [1]매일 실행하며 중복을 확인하고 재현 단계가 있는 보고를 남긴다. 매우 확신하는 작은 문제만 Draft PR로 만든다. 예제 제한은 실행 15분, 열린 자동 QA PR 8개 이상일 때 예약 실행 중단이다.매번 수정으로 끝내지 않고 확신도와 검토 대기량을 제한한다. 이 예제는 버그 감소율을 입증한 실험이 아니다.
Meta · Sapienz / SapFix [2]2018년 Android 운영 사례에서 Sapienz가 월 수백 건의 버그 보고를 생성했고 약 ¾이 개발자 수정으로 이어졌다. SapFix는 컴파일·기존 크래시·새 크래시를 검사한 뒤 사람의 승인과 배포를 거쳤다.정확한 이력만으로도 후속 수정에 도움이 된다. ¾은 보고 이후 개발자 수정 비율이며 AI 자동 수정 성공률이 아니다.
SapFix 배포 경험 논문 [3]6개 실제 Android 시스템에 적용하고 초기에는 null pointer exception처럼 위치가 좁은 결함에 집중했다. 테스트를 통과한 패치에도 원인 은폐·잘못된 위치·부작용 우려로 거절된 제안이 있었다.테스트 통과만으로 올바른 수정을 보장하지 않는다. 초기 자동 수정은 재현·원인·기대 동작이 명확한 문제로 제한한다.
Playwright · Retries / Trace Viewer [4] [5]첫 실행 성공, 재시도 성공(flaky), 모든 재시도 실패를 구분한다. Trace Viewer에서 동작별 화면과 실패 경로를 확인할 수 있다.한 번의 실패를 바로 제품 결함으로 확정하지 않는다. 재실행 성공도 안정적인 성공과 구분하고 첫 실패 증거를 보존한다.
GitHub · Measuring Impact [6]실행 성공·비용과 실제 채택 결과를 분리하고 유용한 결과 비율·채택·리뷰 시간·중복을 측정하도록 안내한다.판단 가능한 신규 결과와 채택된 수정이 늘었는지 평가한다. 반복 등록과 불필요한 리뷰 부담도 비용이다.

오래된 산업 사례는 운영 패턴의 근거로 사용한다. 특정 도구의 역사적 성과를 오늘의 Codex나 BLOOM 게임의 성공률로 일반화하지 않는다. 아래 검사 분량과 주기는 이 조사에서 도출한 초기 제안이다.

4.탐지와 수정의 범위

문제 상태진행 범위판단 이유
미재현·환경 불명확이력과 증거를 남기고 추가 재현. 제품 버그 확정과 자동 수정은 보류.검사 환경·외부 서비스·간헐적 실패를 먼저 구분해야 한다.
재현되지만 의도·영향 범위 불명확확정 현상·영향·처리 선택지를 기록하고 사람의 판단 또는 담당 배정으로 연결.밸런스·UX·시각 의도·공통 상태 변경에는 제품 결정이 필요하다.
재현·원인·기대 동작이 명확한 작은 결함중복·담당 겹침 확인 → 격리 worktree 수정 → 필요한 검증 → PR.수정 전 실패와 수정 후 성공, 직접 영향받는 회귀를 같은 조건으로 확인할 수 있다.
넓은 계약·공통 기반 변경재현 이력과 수정 제안까지. 별도 업무로 배정해 검토.넷코드·상태 소유권·저장 구조·SDK·공통 지형/길찾기 변경은 여러 경로에 영향을 준다.

작은 변경은 줄 수나 파일 수로 판단하지 않는다. 함수·Definition·상태 소유자·공통 mechanic·호출 관계에서의 영향을 확인한다. 다른 대화가 맡은 영역이면 기존 PR에 근거를 연결하고 중복 수정하지 않는다.

자동 수정은 기존 계약을 유지한다. 실패를 없애기 위해 검사를 약화하거나 예외를 숨기거나 대체 경로를 임의 추가하지 않는다. 게임 변경에는 해당 프로젝트가 요구하는 실제 UI E2E, 시각 확인, 관련 결정론·성능 검증이 적용된다.

권한의 끝
예약 QA의 기본 끝은 이력 또는 리뷰 가능한 PR이다. 자동 머지·공개 배포·Stable 승격은 이 운영안에 포함하지 않으며 각각 프로젝트 지침과 사용자의 명시적 지시를 따른다. 검증이 부족한 PR은 후보 상태와 미검증 내용을 표시한다.

5.효과적인 검사 구성

기존의 재현 가능한 검사를 먼저 실행하고 에이전트가 결과를 분류한다. 정해진 빌드·검사·수치 비교는 스크립트로 수행하고 AI는 새로운 재현 경로·원인·처리 판단에 사용한다. [6]

검사 묶음대상초기 주기 제안
핵심 사용자 흐름실제 UI에서 시작 → 주요 행동 → 전투/진행 → 정상 종료 → 재시작 또는 결과·리플레이. 예외·멈춤·UI 막힘·자원/상태 이상 확인.평일 1회. 전체 플레이 검증과 짧은 smoke 검사를 구분해 기록.
최근 변경과 경계 상황변경된 기능, 반복 클릭, 취소·환불, 로딩 실패·재시도, 저장·재로드, 손상 파일, blur·탭 복귀 등 한 영역.매 실행 한 영역씩 회전. 같은 커밋에서도 미검사 조건·seed를 탐색할 수 있음.
결정론·복원같은 seed와 입력에서 같은 결과, 저장→복원→다음 틱 동등성, 롤백·리플레이·상태 격리.관련 변경 시 우선 실행하고 회전 검사에도 포함.
시각·성능실제 렌더 화면 확인, 같은 fixture·장비·브라우저에서 프레임/틱 비용 비교.관련 변경은 해당 실행에서 확인. 넓은 반복 비교는 주간 제안.

고정 seed로 재현하고 다른 seed로 범위를 넓힌다. 기준 커밋·빌드·브라우저·환경·입력 순서·첫 실패와 재실행 결과를 증거에 보존한다. 공개 실행물과 개발 실행물을 혼동하지 않으며 과거 PASS를 현재 결과로 사용하지 않는다.

재시도에서 성공한 문제는 간헐적 실패로 남긴다. 제품 결함인지 검사기의 준비 대기·GPU·RTC·네트워크 제약인지 분류한다. timeout 증가만으로 원인을 해결했다고 선언하지 않는다. 재현 횟수는 초기에는 한 번의 확인 재실행부터 시작하되 간헐적 오류에는 필요한 추가 관측을 한다.

software GPU의 FPS를 실제 물리 GPU 성능으로 단정하지 않는다. 실제 모바일 기기, 외부 NAT를 건너는 두 기기 연결, 장시간 다중 브라우저 검사는 장비와 환경을 확보한 별도 검증 범위로 남긴다.

6.실행·중복·업무 관리

기준 실행물 확인→검사→재현·분류→중복 확인→이력 또는 수정 PR

시작할 때 최신 통합 커밋, 열린 PR의 담당과 변경 영역, worktree·미커밋 변경을 확인한다. 이전 실행이 진행 중이면 같은 예약을 겹쳐 실행하지 않는다. 저장소·도구 조회 실패를 “진행 업무 없음”으로 취급하지 않는다.

사용자 현상·발생 조건·원인과 기존 기록을 비교한다. 동일 문제의 재발은 기존 항목의 상태와 증거를 갱신하고 해결된 문제가 새 커밋에서 재발하면 그 기준을 남긴다. 제목만으로 동일 문제를 판단하지 않는다.

각 실행의 짧은 이력은 결과 요약이며, 개별 업무의 의도·담당·현재 상태는 프로젝트가 정한 원본에서 관리한다. PR 본문을 업무 SSOT로 사용하는 저장소에서는 확정 업무를 기존 PR 또는 새 Draft PR로 연결한다. 같은 업무를 issue·계획 파일·인벤토리에 중복 등록하지 않는다. 미확정 후보는 실행 결과에 남긴다.

수정은 대상 저장소의 Git 공통 디렉터리를 공유하는 별도 worktree와 작업 브랜치에서 수행한다. 필요한 후보를 보존하면서 완료된 실행의 불필요한 작업 공간을 정리한다. 예약마다 새 worktree를 무한히 쌓지 않는다.

실행 시간·추론 사용량·수정 시도·열린 자동 PR 수에 상한을 둔다. 예산 소진이나 실행 실패 시 현재 결과와 남은 작업을 최대 10줄 안에서 필요한 만큼만 보고한다. 설치·서버·브라우저 실행이 막힌 경우도 검사하지 못했다는 결과를 남긴다. 정상 검사에 새 발견이 없으면 짧게 끝낸다.

7.스케줄러 선택

방식적합한 상황필요 조건과 고려점
로컬 Codex 예약 실행 [7]기존 PC의 브라우저·파일·검사 도구를 활용하며 출근 중 실행.PC와 데스크톱 앱을 켜 두고 프로젝트 접근·검증 도구를 준비한다. Git 프로젝트는 worktree로 변경을 격리할 수 있다. 무인 실행에 필요한 파일·네트워크 권한이 사전에 동작해야 한다.
GitHub Actions + Codex Action [8]개인 PC가 꺼져도 원격 runner에서 실행하고 결과를 남김.현재 공식 Codex Action 방식은 API 키 secret 설정이 필요하다. runner 실행 시간·AI 사용 비용과 브라우저/GPU/RTC 환경을 확인한다. 게임 실행과 증거를 지원하는 검사 환경이 먼저 필요하다.
GitHub Agentic Workflows [9]조사 권한과 issue·comment·PR 쓰기 작업을 선언적으로 분리.Safe Outputs로 외부 쓰기를 제한할 수 있다. 중복 제거 기능이 원인·재현 비교까지 대신하지는 않는다. 엔진·인증·runner 조건은 선택한 구성에서 확인한다.

초기에는 기존 로컬 QA를 활용하는 방식이 단순하다. PC 가동을 유지하기 어렵거나 원격 운영이 필요하면 Actions 환경으로 옮긴다. 재현 품질과 운영 비용을 확인한 뒤 결정한다.

독립 검사 실행은 매번 같은 저장된 지시로 시작하는 예약이 적합하고 같은 조사 맥락을 이어야 하면 대화에 연결된 예약을 사용할 수 있다. 프롬프트는 기준 실행물·검사 범위·수정 경계·중복 처리·ELI13으로 최대 10줄 안에서 간결하게 보고하는 기준·종료 조건을 포함하며 등록 전에 수동으로 시험한다. [7]

8.초기 운영과 평가

초기 제안 · 최적값으로 검증된 수치가 아님
평일 하루 1회, 핵심 흐름과 경계 영역 하나를 검사한다. 첫 5회는 탐지·재현·기록 중심으로 운영하고 품질 확인 뒤 작은 수정 PR을 하루 최대 하나 허용한다. 실제 출근 시간과 실행 예산은 별도로 정한다.

첫 실행에서 검사별 소요 시간과 실패 양상을 측정해 일일 예산을 정한다. 수정은 해당 게임의 필수 검증까지 가능한 예산을 확보한 경우에만 시작한다. 환경 실패·오탐·중복이 많으면 검사 환경과 범위를 먼저 정리한다.

평가 지표관측 방법
추가 질문 없이 판단된 비율사용자가 이력만으로 수정·보류·기각을 결정한 결과 / 검토한 결과. 질문이 필요했던 이유로 보고 형식을 보완.
재현·오탐·중복신규 제품 결함, 미확정·환경 문제, 기존 항목 재발을 분리. 간헐적 실패를 성공으로 숨기지 않음.
실제 채택접수·수정·머지·보류·기각을 구분. PR 생성 자체를 해결로 계산하지 않음.
운영과 리뷰 비용검사/추론 사용량·실행 시간·사용자 검토 시간·남은 PR 수를 함께 확인.

채택에는 시간이 걸린다. 한 실행의 수치로 효과를 단정하지 않고 추세를 본다. 판단 가능성과 실제 처리율이 좋아질 때만 자동 수정 범위를 넓힌다. [6]

9.RALLY FRONTIER 적용 예

2026-10-08의 main 77e5798을 읽기 전용으로 조사한 예다. 이 조사에서는 게임 검사를 새로 실행하지 않았으며 아래 존재 여부를 현재 PASS로 해석하지 않는다. 코드 현황은 고정 커밋 링크에서 확인하고 실제 예약은 최신 실행물로 다시 점검한다.

  • netcode-ui-e2e.cjs에는 실제 UI·RTC·WebGL·건설/생산·AI 전투·항복 결과·리플레이·로비 복귀 검사가 있다. 항복 종료를 자연 승패 완료 검증으로 확대 해석하지 않으며 자연 승패 종료를 별도로 보강한다.
  • 건설 취소·환불, 캠페인 모듈 실패·재시도, 덱 저장 후 재로드, 손상 리플레이, 포인터 취소·blur·탭 복귀는 실제 기능 중심의 회전 탐색 후보다. 기능 전체가 매번 검증됐다고 보고하지 않는다.
  • 현재 pages.yml은 빌드·배포 중심이며 schedule이 없다. 별도 예약 QA를 구성할 수 있지만 CI를 무조건 무겁게 복구해야 한다는 뜻은 아니다.
  • Node ≥22와 고정 Playwright가 선언돼 있고 회귀·성능 스크립트가 있다. 일부 오래된 스크립트의 소스 제공 방식·경로는 현재 모듈 구조와 맞는지 먼저 확인한다. 지원되는 검사부터 묶고 환경 실패를 제품 버그로 등록하지 않는다.
  • Development Contract가 게임 검증 기준이다. 실제 UI 싱글 한 판과 종료, 시각 변경의 실제 renderer 확인, 해당 결정론·성능 검증을 정적 검사로 대신하지 않는다. 미검증 결과를 VALIDATED/Stable로 표시하지 않는다.

시작할 순서는 지원되는 빌드/실행 검사 묶음 확인 → 수동 기준 실행 → 10줄 결과 평가 → 예약 등록 → 좁은 자동 수정 허용이다. 환경 오류를 매일 재등록하는 상태에서는 자동 수정 범위를 넓히지 않는다.

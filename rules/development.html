Development Rules

공통 개발 규칙

유지보수성과 확장성을 위한 비용 우선순위판. 특정 프로젝트에 종속되지 않는 구조·코딩 원칙.

개발 규칙 SSOTP0 → P1 → P2IS-A / HAS-A / CAN-BE

함께 읽기: AI 개발 규칙 · 의도·검색·동작 확정 · 공통 UI/UX 레퍼런스 · 공통 STAT 사전 · 절차적 지형 생성. 이 문서는 구조 원칙을, 각 전문 문서는 정보 우선순위·수치 계약·생성 파이프라인을 소유한다.

정렬 기준
“얼마나 멋진 원칙인가”가 아니라 초기에 방치했을 때 나중에 고치는 비용이 얼마나 커지는가로 순서를 정한다. 즉, 구조를 뒤엎어야 하는 문제일수록 위에 둔다. 나쁜 예와 좋은 예를 바로 만들 수 없는 원칙은 우선순위를 낮춘다. 적용 장면이 명확하지 않다면 아직 추상적이라는 뜻이다.
우선순위 뜻 방치했을 때
P0 — 초기 구조 초기에 잡아야 하는 구조 결정 데이터 구조·API·의존성 전체를 다시 뜯어야 한다
P1 — 일상 개발 기능 추가·수정 때 매우 자주 마주치는 규칙 변경 범위가 넓어진다
P2 — 누적 부채 즉시 치명적이지 않은 정리 규칙 코드베이스가 서서히 굳고 유지보수 비용이 커진다

1.P0 — 초기에 반드시 잡기

초기 설계를 잘못하면 나중에 단순 리팩터링이 아니라 데이터 구조와 호출 관계를 다시 설계해야 하는 항목들이다.

1.1.하나의 상태에는 하나의 진실과 하나의 소유자

  • DEV-001P0SSOT · Single Ownership — 같은 의미의 상태·공식·판정 로직은 한 곳에서만 정의하고, 그 상태를 생성·수정·삭제하는 주체는 1개만 둔다. 위반 판별: 같은 필드를 2곳 이상에서 대입하거나 같은 공식이 2개 이상 모듈에 있다.

태그: #SSOT #SingleOwnership #SingleWriter

빈도: 매우 높음 · 나중 수정비용: 매우 큼

같은 의미의 상태·공식·판정 로직을 여러 곳에서 따로 관리하지 않는다. mutable state는 누가 생성·수정·삭제하는지 하나로 정한다.

나쁜 예
unit.hp -= damage;
hud.hp = unit.hp;
network.hp = unit.hp;

// 다른 곳에서도 각각 hp 수정
hud.hp -= 10;
좋은 예
unit.applyDamage(damage);

// HUD/Network는 unit의 결과를 읽거나
// unit이 발행한 상태 변화만 구독

1.2.Checkbox 상태와 Radio 상태를 구조적으로 구분

  • DEV-002P0Make Illegal States Unrepresentable · State Machine — 동시에 성립할 수 있는 상태는 독립 boolean으로, 상호배타적인 택 1 상태는 enum/state machine으로 정의한다. 위반 판별: 서로 배타적이어야 하는 boolean 필드가 2개 이상 있다.

태그: #StateMachine #MakeIllegalStatesUnrepresentable

빈도: 높음 · 나중 수정비용: 매우 큼

동시에 성립 가능한 상태는 flag로, 상호배타적인 택 1 상태는 enum/state machine으로 정의한다. 택 1 상태를 여러 boolean을 켜고 끄는 방식으로 구현하지 않는다.

나쁜 예
isIdle = false;
isMoving = true;
isAttacking = true;
isStunned = true;

존재하면 안 되는 조합이 구조적으로 가능하다.

좋은 예
state = UnitState.MOVING;

isSelected = true;
isPoisoned = true;

Radio 상태는 하나만, Checkbox 상태는 독립 flag로 둔다.

1.3.관계의 종류에 따라 구현 방식을 구분한다

  • DEV-003P0IS-A / HAS-A / CAN-BE · Composition over Inheritance — 객체 관계를 IS-A(상속)·HAS-A(composition)·CAN-BE(mixin/trait)로 먼저 구분하고 그 관계에 맞는 구현을 쓴다. CAN-BE capability는 자기 상태와 로직을 mixin이 직접 소유하고, Host가 이미 소유한 HAS-A 객체를 다시 만들지 않는다. 위반 판별: 기능 조합을 상속 계층으로 표현했거나, 단순 capability를 component 배열·registry를 거쳐 호출하거나, mixin이 Host 소유 객체를 중복 생성한다.

태그: #IS_A_HAS_A_CAN_BE #CompositionOverInheritance #Mixin #CapabilityOwnership

빈도: 높음 · 나중 수정비용: 매우 큼

모든 재사용을 composition 하나로 해결하지 않는다. 객체 관계의 의미를 먼저 구분하고, 그 의미에 가장 자연스러운 구현 방식을 사용한다.

관계 질문 기본 구현 대표 예
IS-A “이것은 본질적으로 저것의 한 종류인가?” 상속 / 공통 base type Dragon IS-A Unit
HAS-A “이것이 독립적인 부품/객체를 가지고 있는가?” Composition Unit HAS-A Weapon
CAN-BE “필요하면 이 능력/성질을 가질 수 있는가?” Mixin / Trait / capability method injection Unit CAN-BE Jumpable

핵심: Composition은 기본값이 아니라 HAS-A 관계의 기본값이다. CAN-BE까지 전부 component 배열로 밀어 넣으면 호출 깊이와 간접성이 커져 코드가 오히려 비직관적일 수 있다.

IS-A → 상속

도메인적으로 정말 같은 종류이고, base contract가 작고 안정적일 때만 사용한다.

나쁜 예 — 기능을 상속 계층으로 표현
FlyingPoisonEliteRangedUnit
  extends FlyingRangedUnit
    extends RangedUnit
      extends Unit
좋은 예 — 본질적인 타입 관계만 상속
class Unit {
  update() {}
  destroy() {}
}

class Dragon extends Unit {
  // Dragon도 본질적으로 Unit
}

HAS-A → Composition

독립적인 상태와 생명주기를 가진 부품, 교체 가능한 객체, 별도 소유권이 필요한 경우 composition을 사용한다.

나쁜 예 — 부품을 상속으로 표현
class SwordUnit extends Unit {
  // Sword 때문에 새로운 Unit 타입 생성
}
좋은 예 — 부품을 소유
class Unit {
  constructor(weapon) {
    this.weapon = weapon;
  }

  attack(target) {
    this.weapon.attack(target);
  }
}

CAN-BE → Mixin / Trait

객체의 본질적인 타입도 아니고, 독립 부품을 소유하는 것도 아니지만 선택적으로 “할 수 있는 것”이라면 mixin/trait 계열이 더 직접적일 수 있다.

나쁜 예 — 모든 능력을 component 배열 순회로 처리
unit.components = [
  movement,
  jump,
  shield,
  poison,
  capture
];

for (const c of unit.components) {
  c.update?.(dt);
}

// 실제 jump 호출 위치를 찾으려면
// registry → component → handler를 계속 따라가야 함
좋은 예 — 능력이 객체 API에 직접 드러남
const Jumpable = Base => class extends Base {
  jump() {
    this.velocity.z = this.jump.power;
  }
};

class Unit {
  move() {}
}

class Flea extends Jumpable(Unit) {}

flea.jump();

이 방식의 장점은 호출부가 unit.jump()처럼 평평하고 직관적이라는 것이다. 능력 하나를 실행하기 위해 components[]를 찾고 순회하거나 중간 registry를 통과할 필요가 없다.

CAN-BE를 Composition으로 써도 되는 경우

Mixin을 무조건 쓰는 것도 아니다. 다음 조건이면 composition이 더 적합하다.

  • 능력 자체가 큰 상태를 가진다.
  • 별도의 lifecycle이 있다.
  • 런타임에 교체/탈착되어야 한다.
  • 동일 capability를 여러 구현으로 갈아끼워야 한다.
나쁜 예 — Unit이 capability 내부 구조를 직접 소유/중계
class Unit {
  constructor(jumpAbility) {
    this.jumpAbility = jumpAbility;
  }

  jump() {
    this.jumpAbility.execute(this);
  }
}

Unit이 Jump의 component 존재와 호출 방법을 알아야 하므로 상태·로직 소유권이 분산된다.

좋은 예 — 단순 capability는 Mixin이 직접 상태와 로직을 소유
const Jumpable = Base => class extends Base {
  constructor(...args) {
    super(...args);

    this.jump.power = 12;
    this.jump.cooldown.durationMs = 800;
    this.jump.cooldown.leftMs = 0;
  }

  jump() {
    if (this.jump.cooldown.leftMs > 0) return false;

    this.velocity.z = this.jump.power;
    this.jump.cooldown.leftMs = this.jump.cooldown.durationMs;
    return true;
  }

  updateJump(dt) {
    this.jump.cooldown.leftMs = Math.max(
      0,
      this.jump.cooldown.leftMs - dt
    );
  }
};

class Unit {
  move() {}
}

class Flea extends Jumpable(Unit) {}

flea.jump();

점프 자체가 하나의 capability이므로 별도 JumpAbility component를 만들지 않는다. 점프 전용 상태와 로직은 Jumpable 안에 바로 둔다.

규칙: CAN-BE capability는 가능한 한 자기 상태와 로직을 Mixin/Trait 자체에 직접 가진다. 단순 capability 안에 또 capability용 component를 만들어 한 단계 더 감싸지 않는다.

Jumpable Mixin
 ├─ jump.power
 ├─ jump.cooldown.durationMs
 ├─ jump()
 └─ updateJump()

// Jumpable 안에 JumpAbility를 또 넣지 않음

Mixin이 커져서 내부를 다시 component로 쪼개고 싶어질 정도라면, 우선 그 Mixin 자체가 여러 capability를 떠안고 있는지 본다. 그렇다면 하위 composition을 추가하기보다 capability를 더 작은 Mixin/Trait으로 분리한다.

나쁜 예 — 비대해진 Mixin 안에 다시 내부 component 계층 생성
Jumpable
 ├─ JumpPhysics
 ├─ JumpCooldown
 ├─ JumpLanding
 └─ JumpEffects

좋은 방향 — 독립 capability로 분리

Unit
 ├─ Jumpable
 ├─ Landable
 └─ AirControl

각 capability가 자기 상태와 로직을 직접 소유한다.

Unit
 ├─ weapon               ← Unit이 정당하게 소유하는 HAS-A composition
 │    └─ Sword
 │
 └─ SwordTechnique Mixin ← sword 전용 CAN-BE capability
      └─ base.weapon 참조

이미 Host가 정당하게 소유하는 composition이 있다면 Mixin이 그것을 참조해 특수 기능을 정의할 수 있다. 이 경우 Mixin이 weapon 자체를 다시 소유하거나 중복 생성하지 않는다.

나쁜 예 — 같은 하위 상태를 이중 소유
class Unit {
  constructor() {
    this.weapon = new Sword();
  }
}

const SwordTechnique = Base => class extends Base {
  constructor(...args) {
    super(...args);
    this.sword = new Sword(); // 중복 소유
  }

  parry() {
    this.sword.parry();
  }
};
좋은 예 — 기존 HAS-A를 이용해 새로운 capability를 추가
class Unit {
  constructor(weapon) {
    this.weapon = weapon;
  }
}

const SwordMastery = Base => class extends Base {
  constructor(...args) {
    super(...args);
    this.swordComboStep = 0;
  }

  iaiSlash(target) {
    if (!(this.weapon instanceof Sword)) {
      throw new Error("Sword required");
    }

    const damage =
      this.weapon.getBaseDamage() * 2.5;

    this.weapon.consumeDurability(1);
    target.takeDamage(damage);

    this.swordComboStep = 0;
  }

  advanceSwordCombo() {
    this.swordComboStep =
      (this.swordComboStep + 1) % 3;
  }
};

class SwordMaster extends SwordMastery(Unit) {}

const unit = new SwordMaster(new Sword());
unit.iaiSlash(enemy);

SwordMastery는 weapon.attack()을 다시 감싸지 않는다. 기존 weapon을 재료로 사용해 발도베기·콤보처럼 Unit에 원래 없던 capability를 추가하고, 그 capability 전용 상태도 Mixin이 소유한다.

즉 HAS-A의 소유권은 그대로 유지하고, CAN-BE는 그 소유 객체를 재료로 사용해 기존 객체에는 없던 새로운 능력·규칙·상태를 추가한다. 단순 forwarding/wrapping만 하는 Mixin은 만들지 않는다.

Flat API와 함께 중요한 것은 Single Ownership이다. Mixin은 자신이 추가한 capability의 상태와 로직을 직접 소유한다. 기존 HAS-A 객체를 활용할 수는 있지만 그 객체의 소유권을 복제하지 않는다. Mixin이 비대해져 내부 계층이 필요해지면 먼저 capability 분리를 검토한다.

결정 순서

1. 본질적으로 같은 종류인가?
   → YES: IS-A → 작은 base type / 상속

2. 독립적인 객체·상태·생명주기를 소유하는가?
   → YES: HAS-A → Composition

3. 선택적으로 가질 수 있는 능력/성질인가?
   → YES: CAN-BE → Mixin / Trait 우선 검토

4. CAN-BE 자체가 단순한 capability인가?
   → YES: Mixin/Trait이 상태와 로직을 직접 소유
   → 내부에 같은 의미의 Ability component를 또 만들지 않음

5. Mixin이 너무 커져 내부 하위 계층이 필요해졌는가?
   → YES: 먼저 capability 자체를 더 작은 Mixin/Trait으로 분리
   → 내부 component nesting은 최후 수단

6. CAN-BE가 기존 HAS-A 객체를 이용하는가?
   → YES: 기존 owner의 객체를 참조해 새 capability를 정의
   → 객체 소유권은 기존 owner에 그대로 유지

7. 외부 호출은?
   → 의미 있는 Flat API로 노출
   → 같은 상태/객체의 owner는 끝까지 하나만 유지

1.4.이름이 아니라 능력으로 분기

  • DEV-004P0Capability-based Design — 로직 분기는 유닛명·타입명·ID·맵 이름이 아니라 capability 보유 여부와 데이터로 한다. 위반 판별: type === "..." 또는 맵 이름 비교로 행동이 갈린다.

태그: #CapabilityBasedDesign

빈도: 매우 높음 · 나중 수정비용: 큼

특정 유닛명·타입명·ID가 로직 분기의 핵심이 되지 않게 한다.

보스·맵도 같다. 돌진·소환·단계 전환은 각각 재사용 가능한 capability로 구현하고, 보스별 구성은 능력 조합과 설정으로 표현한다. 맵 이름을 검사해 충돌·스폰을 갈라 놓지 말고 지형 데이터와 이동·스폰 규약을 사용한다. 단, 실제로 행동이 다른 경우에는 새 capability가 필요하며 모든 차이를 거대한 설정 분기로 숨기지 않는다.

나쁜 예

    jump();
}
좋은 예
if (unit.hasCapability("jump")) {
    unit.jump();
}

빈도: 높음 · 나중 수정비용: 큼

나쁜 예

// 모든 독 공격 유닛이
// 같은 damage를 강제로 공유

1.6.Core가 구체 기술을 직접 알지 않게

  • DEV-006P0Dependency Inversion — 도메인/게임 로직은 네트워크·렌더러·저장소·프레임워크 API를 직접 호출하지 않고 교체 가능한 경계(transport 등)를 거친다. 위반 판별: 게임 로직 파일이 peer/renderer/storage API를 직접 import하거나 호출한다.

태그: #DependencyInversion #SeparationOfConcerns

빈도: 중간 · 나중 수정비용: 매우 큼

도메인/게임 로직이 특정 네트워크, 렌더러, 저장소, 프레임워크 API에 직접 종속되지 않게 한다.

빈도: 높음 · 나중 수정비용: 큼

“내게 이런 일이 일어났다”는 통지는 발생 주체의 public signal로 노출한다. 발신자는 subscriber를 알지 않는다.

나쁜 예

2.8.예외는 원본 그대로 올린다

  • DEV-027P1Fail Fast · Preserve the Original Exception — 발생한 예외는 원본 그대로 호출 스택 위로 올리고, 새 Error로 감싸 던지거나 이벤트·콜백에 문자열로 바꿔 알리거나 삼키지 않는다. 새 예외는 내 로직이 직접 오류 조건을 판정한 경우에만 던지고, catch는 그 자리에서 실제로 복구할 수 있을 때만 쓴다. 위반 판별: catch나 이벤트 처리에서 원본 예외 대신 new Error(...)를 만들어 올렸거나, 원본의 이름·메시지·스택이 최상위 로그에 남지 않는다.

태그: #FailFast #ExceptionTransparency #PreserveStackTrace

빈도: 높음 · 나중 수정비용: 중간

예외의 이름·메시지·스택은 원인을 찾는 유일한 단서다. 호출 스택 중간에서 새 Error로 감싸면 스택이 감싼 지점의 것으로 바뀌어 "어디서 잡았는지"만 남고 "무엇이 던졌는지"는 사라진다. 로그에는 감싼 메시지(fatal 같은 이름)만 보이고, 그 뒤에 원본이 다시 올라와도 이미 실패 처리가 끝나 있으면 조용히 버려진다.

상황 하는 일
호출한 코드가 예외를 던졌고 그 자리에서 복구할 수 없다 잡지 않는다. 그대로 올라가게 둔다(정리는 finally)
그 자리에서 실제로 복구할 수 있다 잡아서 복구한다. 복구했으면 예외는 끝난 것이다
내 로직이 오류 조건을 직접 판정했다(잘못된 입력·깨진 불변식) 새 오류를 던진다. 이때만 새 Error를 만든다
이벤트·콜백으로 실패를 알려야 한다 원본 예외 객체를 그대로 넘기고, 받는 쪽이 문자열로 바꿔 새 오류를 만들지 않는다
나쁜 예
// 단계가 던진 예외를 다시 던지기 전에 이벤트로 알린다
catch (error) {
  this.onEvent({ type: 'fatal', error });
  throw error;
}
// 받는 쪽: 이벤트를 받자마자 문자열로 바꿔 먼저 실패 처리한다 → 뒤따라 올라온 원본은 `if (failed) return`에서 버려진다
onEvent(event) {
  if (event.type === 'fatal') fail(new Error(event.reason || event.type)); // 로그에는 "Error: fatal"만 남는다
}
좋은 예
// 받는 쪽은 감싸지 않는다. 원본이 던져지는 경로가 있으면 그 예외가 최상위 로그에 이름·메시지·스택 그대로 남는다.
onEvent(event) {
  if (event.type === 'desync-unrecoverable') fail(new Error(event.reason)); // 던져진 예외가 없어 내 로직이 직접 만든 오류
}

cause로 원본을 붙여 감싸는 것도 같은 규칙으로 막는다. 감싼 스택이 로그의 맨 앞에 오기 때문이다. 사례: 도장깨기 경기 중 단계 예외가 Error: fatal로 감싸져 원인을 알 수 없었다(bloom-takraw v0.15.9에서 감싸기를 제거).

2.9.플레이 중 처음 쓰는 순간에 로드하지 않는다

  • DEV-032P1Preload Before Play · No In-game First-use Load — 플레이 중 처음 쓰이는 순간에 셰이더 프로그램 컴파일·링크, 텍스처 GPU 업로드, 오디오 디코딩, GPU 자원(렌더 타깃·복사 텍스처) 할당이 일어나지 않게 한다. 플레이에 쓰이는 것은 로딩 단계에서 실제 사용 상태(조명·그림자·안개·톤 매핑 등 변종 키가 같은 조건)로 미리 컴파일·업로드·할당하고, 플레이 중 재질의 define을 바꿔 재컴파일이 일어나게 하지 않고 uniform으로 바꾼다. 화면 크기 변경 같은 플레이 밖 동작의 재할당은 예외다. 위반 판별: 로딩 완료 이후 플레이 중에 새 셰이더 프로그램이 컴파일되거나(렌더러의 프로그램 목록이 늘거나 linkProgram 호출이 생긴다), 새 이펙트의 첫 사용 프레임이 이후 프레임보다 눈에 띄게 길다.

태그: #PreloadBeforePlay #NoInGameLoad #ShaderWarmup #FirstUseHitch

빈도: 높음 · 나중 수정비용: 중간

셰이더 컴파일·링크, 텍스처 GPU 업로드, 오디오 디코딩, 렌더 타깃 할당은 한 번 일어나는 큰 동기 작업이다. 플레이 중 처음 쓰이는 순간에 일어나면 그 프레임 하나가 길어지고, 이후 프레임은 정상이라 평균 프레임 시간에는 거의 드러나지 않는다. 성능을 평균으로만 재면 통과하고, 기기에서 첫 사용 때만 끊기는 문제는 놓친다.

자원 로딩 단계에서 하는 일
셰이더 프로그램 실제 사용 상태(조명 수·그림자·안개·톤 매핑·클리핑 등 프로그램 변종 키가 같은 조건)의 장면·카메라로 컴파일한다. 변종 키가 다르면 같은 재질이어도 다시 컴파일된다
후처리 패스 패스의 재질과 렌더 타깃을 로딩 때 만들고, 처음 켜지는 때에 새로 만들지 않는다
텍스처·오디오 GPU 업로드와 디코딩을 로딩 때 끝낸다
복사 텍스처·렌더 타깃 로딩 때 생성하고 플레이 중에는 재사용한다
재질 define 플레이 중 바꾸면 재컴파일된다. 켜고 끄는 값은 uniform으로 둔다

예외는 화면 크기 변경처럼 플레이 밖에서 사용자가 일으키는 동작의 재할당이다.

나쁜 예
// 쇼크웨이브 패스의 셰이더가 경기 중 첫 접촉 때 renderer.render 안에서 처음 컴파일된다
onFirstContact() {
  this.shockwavePass.enabled = true; // 다음 render에서 컴파일·링크 + 복사 텍스처 할당
}

  • 로딩 완료 이후 플레이 중 새 프로그램 컴파일 0회. 렌더러의 프로그램 목록(three.js의 renderer.info.programs.length)이 로딩 완료 시점과 플레이 중 이펙트를 모두 한 번씩 쓴 뒤에 같은지, 또는 linkProgram 호출 횟수가 늘지 않는지 본다.

이 확인은 PR마다 한 번 하는 관찰이며 영구 성능 시험으로 넣지 않는다. 영구 시험은 고정 시나리오 E2E만 두고(PM-009), 성능·프레임 시간을 재는 로직은 머지 전 검사에 넣지 않는다(PM-014). 기능 검증과 성능 검증을 구분하는 이유는 AI-012와 같다.

사례: bloom-takraw 0.17.4에서 화면 왜곡 쇼크웨이브 후처리 패스를 넣으면서 그 셰이더가 경기 중 첫 접촉 때 처음 컴파일되게 두었고, 성능은 평균 프레임 시간만 재서 첫 사용 프레임은 보지 않은 채 통과시켰다. 이후 휴대폰에서 렉이 제보됐다. 원인은 조사 중이며 이 컴파일이 주원인인지는 아직 확정되지 않았다.

2.10.렌더 제출량(드로우콜)을 언제든 읽을 수 있게 한다

  • DEV-033P1Draw Call Visibility · Submission Count First — 실행 중인 게임에서 프레임당 렌더 제출량(드로우콜 수, 가능하면 셰이더 프로그램 수·텍스처 수·삼각형 수)을 디버그 수단으로 언제든 읽을 수 있게 유지한다. 새 재질·메시·입자·후처리·UI 레이어나 배칭 조건처럼 렌더 경로에 영향을 주는 변경은 대표 장면에서 드로우콜 수의 전후를 확인해 PR 본문에 적는다. 성능 문제를 조사할 때는 원인을 추측하기 전에 제출량을 먼저 읽고 개편 전 값과 비교한다. 드로우콜을 줄이는 구현은 공통 모듈(bloom-gamekit)의 수단을 쓰고 게임마다 새로 만들지 않는다. 위반 판별: 실행 중인 게임에서 드로우콜 수를 읽을 방법이 없거나, 렌더 변경 PR에 드로우콜 전후 값이 없거나, 성능 문제 보고에 제출량 수치 없이 원인이 단정돼 있다.

태그: #DrawCallVisibility #SubmissionCountFirst #RenderStats #PerfTriage

빈도: 높음 · 나중 수정비용: 중간

드로우콜을 줄이는 기법(배칭·인스턴싱·텍스처 아틀라스)은 공통 모듈에 이미 있다. 이 규칙은 그 기법을 다시 쓰라는 것이 아니라, 렌더가 느려졌을 때 제출량부터 읽어 원인 범위를 좁힐 수 있게 하는 규칙이다. 제출량을 읽을 수 없으면 "후처리 때문일 것이다", "그림자 때문일 것이다" 같은 추측으로 조사가 시작되고, 틀린 쪽을 먼저 고친다. 렌더 제출량은 프레임 시간과 달리 같은 장면이면 기기와 무관하게 거의 같게 재현되는 숫자라서 개발 PC에서 읽은 값을 제보 기기의 증상과 맞대 볼 수 있다.

  2. 가장 흔한 장면(평소 플레이 화면).
  3. 이번에 바꾼 요소가 화면에 처음 나오는 장면.

수치가 늘었을 때 보는 순서.

  1. 배치가 깨졌는가. 재질·텍스처·셰이더·블렌딩 상태가 객체마다 달라졌는지, 같은 재질을 인스턴스 하나로 묶지 못했는지 본다(gamekit이면 flushReasons).
  2. 투명·정렬 때문에 끊겼는가. 반투명 객체의 그리기 순서가 서로 다른 재질을 번갈아 오가는지 본다.
  3. 패스가 늘었는가. 후처리 패스, 그림자 맵, 렌더 타깃 전환, 화면 복사가 프레임마다 몇 번인지 센다. 패스 하나는 화면 크기만큼의 픽셀 비용을 더하므로 드로우콜이 거의 그대로여도 느려질 수 있다.

제출량이 그대로인데 느리면 정점·픽셀(fill) 비용이나 처음 쓰는 순간의 로드(DEV-032)를 의심한다. 제출량이 같다는 것은 제출 횟수가 원인이 아니라는 뜻이지, 렌더가 원인이 아니라는 뜻이 아니다.

PR에 적는 모양. 장면, 읽은 값(드로우콜·프로그램·삼각형), 전후 비교를 한 줄로 적는다. 예: 대표 장면 3곳 드로우콜 41→42, 프로그램 12→13, 삼각형 변화 없음.

이 확인은 PR마다 한 번 하는 관찰이며, 드로우콜 수 상한을 영구 시험이나 합격 기준으로 넣지 않는다. 영구 시험은 고정 시나리오 E2E만 두고(PM-009), 성능 수치를 재는 로직은 머지 전 검사에 넣지 않는다(PM-014). 기능 검증과 성능 검증을 구분하는 이유는 AI-012와 같다.

사례: bloom-takraw 0.17.4에서 화면 왜곡 후처리 패스(풀스크린 패스 1회)를 포함한 이펙트 개편을 넣은 뒤 휴대폰에서 렉이 제보됐고, 원인은 조사 중이다. 드로우콜이 원인이라는 근거는 없다. 다만 조사 시점의 main에서 게임 안에서 renderer.info를 읽는 화면이 없어, 개편 전후의 제출량을 같은 장면에서 맞대 볼 수 없었다. 제출량을 읽을 수 없으면 이런 제보에서 첫 단계인 범위 좁히기부터 추측에 의존하게 된다.

2.11.드로우콜은 개체 수·종류 수가 아니라 렌더 상태 묶음 수로 정한다

  • DEV-034P1Count-independent Draw Calls · Batch by Render State — 프레임당 드로우콜 수는 화면에 있는 개체의 수나 콘텐츠 종류의 수가 아니라 렌더 상태 묶음의 수(셰이더·블렌드·레이어·패스의 조합)로 정해지게 한다. 텍스처는 텍스처 배열 하나로 묶어 그리므로 텍스처 장수는 묶음을 가르는 기준이 아니다. 같은 종류의 개체가 늘어도, 새 종류(유닛·탄·이펙트·아이템)가 추가돼도 드로우콜은 늘지 않거나 미리 정한 상태 묶음 수만큼만 늘어야 한다. 종류의 차이는 재질이 아니라 데이터(텍스처 배열 레이어·아틀라스 영역, 인스턴스 속성, 팔레트·uniform 배열)로 표현한다. 위반 판별: 대표 장면에서 개체를 N개에서 N+10개(또는 2N개)로 늘렸을 때 드로우콜이 그 수에 비례해 늘거나, 종류를 하나 추가할 때마다 드로우콜이 하나씩 늘거나, 텍스처(아틀라스 페이지) 수가 늘 때 드로우콜이 늘거나, 개체마다 고유 재질·텍스처·캔버스·uniform 묶음을 만들어 개별로 그린다.

태그: #CountIndependentDrawCalls #BatchByRenderState #Instancing #TextureArray

빈도: 높음 · 나중 수정비용: 큼

DEV-033은 드로우콜을 읽을 수 있어야 한다는 규칙이고, 이 규칙은 드로우콜이 어떻게 늘어나면 안 되는가를 정한다. 개체 수는 게임이 진행되면서 늘어나는 값이고 콘텐츠 종류는 개발이 진행되면서 늘어나는 값이다. 드로우콜이 둘 중 하나에 비례하면 지금은 괜찮아도 나중에 반드시 터진다. 렌더 상태 묶음의 수는 설계로 고정할 수 있는 값이다. 개체마다 Mesh·재질·캔버스를 하나씩 두는 구조는 개체 코드 곳곳에 퍼져 있어서 나중에 고치려면 렌더 경로 전체를 다시 짜야 한다.

판단식.

드로우콜 = 렌더 상태 묶음 수 × 패스 수 + 고정분
  • 렌더 상태 묶음은 셰이더·블렌드·레이어(그리는 순서가 의미를 갖는 단위)·패스의 조합이다. 텍스처는 텍스처 배열 하나로 묶으므로 기준에 들어가지 않는다.
  • 개체 수 N과 종류 수 K가 식에 들어가면 위반이다. 개체 10개를 더했을 때 드로우콜 증가분(기울기)이 0이어야 한다.

텍스처 장수는 드로우콜을 늘리는 이유가 아니다. 이미지가 여러 장이어도 텍스처 배열(레이어 번호를 인스턴스·정점 속성으로 넘긴다)에 담아 한 번 바인딩해 그린다. 텍스처(아틀라스 페이지) 수에 비례해 드로우콜이 늘면 위반이다. 배열 하나에 담기지 않는 경우는 "허용되는 증가"가 아니라 자산 구성의 문제로 고친다. 크기를 통일하고 상한 안에 담는다.

  • bloom-gamekit의 device.textureAtlas는 TEXTURE_2D_ARRAY 하나(기본 2048×1024, 레이어 2장)이고 영역마다 레이어 번호와 uvRect를 가진다. 크기가 다른 이미지도 선반 배치로 한 레이어 안에 담는다. 영역은 한 레이어 안에 들어가야 한다.
  • 레이어 수는 WebGLDevice 생성 옵션 textureAtlas: { width, height, layers }이고 MAX_ARRAY_TEXTURE_LAYERS 이하여야 한다. 가득 차면 allocate()가 Texture atlas array is full 오류를 던진다. 늘어나는 한도는 배칭이 아니라 이 상한이므로, 이미지 총량을 상한 안에 두거나 그 옵션의 레이어 수를 키운다.
  • flushReasons에는 텍스처 동일성을 이유로 한 항목이 없다. 아틀라스 영역이 달라도 배칭이 끊기지 않는다. 포즈 텍스처가 다르면 poseBackend(네이티브 경로)나 state(순서 있는 경로)로 끊긴다.
  • three.js를 직접 쓰는 게임(bloom-takraw)에도 같은 원칙이 적용된다. 같은 지오메트리는 InstancedMesh, 여러 이미지는 DataArrayTexture와 인스턴스 속성(레이어 번호)으로 묶는다.

허용되는 증가. 애매한 경계는 아래로 정한다.

  • 새 렌더 상태가 정말 필요한 경우(새 블렌드 방식, 새 셰이더, 새 패스)는 종류가 아니라 상태가 늘어난 것이므로 허용한다. 단 상태 묶음 목록을 한곳에 두고 그 수를 의식적으로 관리한다.
  • 그리는 순서가 의미를 갖는 경우(반투명 정렬, 레이어)는 끊김이 레이어 수에 묶여야 하고 개체 수에 묶이면 위반이다. 순서를 지키면서 묶는 수단(gamekit의 orderedMeshQuads)을 쓴다.
  • 배치 버퍼 용량(인스턴스 수·정점·command 상한)에 닿아 나뉘는 경우는 허용한다. flushReasons의 capacity이며 드로우콜이 개체 수가 아니라 ceil(N / 용량)으로 늘기 때문이다. 이 증가는 용량 단위(MeshRenderer 기본 maxInstances 2048)이고, 용량을 키울 수 있으면 키운다.
  • 수가 설계상 고정이고 작은 경우(정해진 인원의 선수, 화면에 하나뿐인 보스·플레이어)는 개체 수가 변수가 아니므로 이 규칙의 대상이 아니다. 다만 "지금은 적다"는 이유로 변하는 수량을 고정이라고 주장하지 않는다. 상한이 규칙·설계로 고정돼 있어야 한다.

확인 방법. 1회성 관찰이며 영구 시험이 아니다.

  1. 대표 장면에서 개체 수를 두 값(N, N+10 또는 2N)으로 놓고 DEV-033의 수단으로 드로우콜을 읽어 PR에 적는다. 모양: N=… → draw …, N+10=… → draw ….
  2. 종류를 추가하는 PR은 추가 전후를 적는다. 늘었으면 어느 상태 묶음이 늘었는지 적는다. gamekit이면 context.stats().mesh.flushReasons와 drawDispatchReasons의 사유(mesh, clip, depthState, projection, poseBackend, capacity 등)를 본다.
  3. 이 확인에 드로우콜 수 상한을 영구 시험이나 합격 기준으로 넣지 않는다(PM-009·PM-014).

구현은 공통 모듈(bloom-gamekit)의 수단을 쓰고 게임마다 새로 만들지 않는다. 배칭·인스턴싱의 기법과 비용은 A072 GPU Instancing과 A064 Render Batching에 있다. 드로우콜 감소만으로 GPU 비용이 줄었다고 판정하지 않는다(A064의 주의).

사례: budmori-io docs/performance-diagnostics.md의 기록에서 orderedMeshQuads를 켜기 전후 드로우콜 평균이 밀 882마리 장면에서 1765 → 17, 혼합 1,000마리 장면에서 608 → 18이 됐다. Chromium·SwiftShader(소프트웨어 GPU)의 한 환경에서 잰 값이고, 같은 기록에서 GPU 시간은 이 환경에서 크게 줄지 않았다.

3.6.긴 접두어 변수보다 의미 단위 계층으로 상태를 묶는다

  • DEV-020P2Hierarchical Naming · Semantic Namespace — 같은 기능에 속하는 상태는 접두어 반복 대신 기능 단위 namespace 객체로 묶고, 단위는 leaf 이름(Ms, Rad, Px)에 남긴다. 계층은 기능·소유권·하위 개념을 구분하는 데 필요한 만큼만 만든다. 위반 판별: 같은 접두어 필드가 3개 이상 평평하게 나열되거나, 의미 없는 wrapper 계층이 있다.

태그: #HierarchicalNaming #SemanticNamespace #ScopeVisibleNaming

빈도: 매우 높음 · 나중 수정비용: 중간

서로 같은 기능에 속하는 상태를 jump.cooldown.leftMs, jump.power, jumpDurationMs처럼 평평한 이름으로 늘어놓기보다, 기능 단위 namespace 아래에 계층적으로 묶어 스코프와 소유권을 코드 모양 자체로 드러낸다.

나쁜 예 — 접두어를 반복하는 Flat Naming

this.jumpCooldownDurationMs = 800;
this.jumpCooldownLeftMs = 0;
this.jumpDurationMs = 250;

jumpDurationMs처럼 기능명과 하위 의미를 변수명에 계속 이어 붙이면, 필드가 늘수록 이름이 길어지고 스코프와 계층이 문자열 접두어에만 의존하게 된다.

좋은 예 — 기능 단위 계층

  power: 12,

  cooldown: {
    durationMs: 800,
    leftMs: 0
  },

  durationMs: 250
};

Jump.*만 봐도 어느 기능의 상태인지 바로 알 수 있고, 하위 상태도 의미 단위로 묶인다.

단위까지 계층 안에서 명확하게

jump.cooldown.durationMs
jump.cooldown.leftMs

linear.velocity.x
linear.velocity.y

angular.velocity

단위가 중요한 값은 Ms, Rad, Px처럼 leaf 이름에 단위를 남긴다. 계층을 만든다고 단위 정보를 숨기지 않는다.

Mixin 소유권과도 맞춘다

Mixin이 소유하는 상태는 해당 Mixin의 namespace 아래에 둔다.

const Jump = Base =>
  class Jump extends Base {
    constructor(...args) {
      super(...args);

      this.jump = {
        power: 12,
        cooldown: {
          durationMs: 800,
          leftMs: 0
        }
      };
    }

    jump() {
      if (this.jump.cooldown.leftMs > 0) {
        return false;
      }

      this.velocity.z = this.jump.power;
      this.jump.cooldown.leftMs =
        this.jump.cooldown.durationMs;

      return true;
    }
  };

과도한 계층은 피한다

4.JavaScript Mixin 구현 규약

일반 원칙과 달리 이 섹션은 JavaScript에서 실제로 사용할 Mixin 형태를 구체화한다. 구현은 표준 JavaScript의 Subclass Factory 패턴을 기반으로 하고, 프로젝트에서는 읽기 쉬운 mixin(...) 헬퍼 하나만 공개한다.

핵심 공식 Mixin = Base Class → Base를 extends한 Subclass를 반환하는 함수 Mixin끼리도 조합할 수 있고, 조합된 결과 역시 다시 Mixin으로 사용한다.

4.1.별도 Mixin 전용 Base를 만들지 않는다

  • DEV-023Subclass Factory · No Mixin Base — Mixin은 Base를 받아 class extends Base를 반환하는 Subclass Factory로 만들고, Mixin 전용 공통 Base 클래스를 두지 않는다. 위반 판별: MixinBase 같은 클래스를 상속해야만 mixin을 쓸 수 있다.

태그: #SubclassFactory #NoMixinBase

나쁜 예
class MixinBase {}
class Unit extends MixinBase {}

Mixin 사용을 위해 불필요한 공통 상속축이 생긴다.

좋은 예 — 공식적인 Subclass Factory 형태
const Position = Base =>
  class Position extends Base {
    constructor(...args) {
      super(...args);
      this.position = {
        x: 0,
        y: 0
      };
    }
  };

Mixin은 어떤 기존 Base Class에도 적용 가능하다.

4.2.공개 조합 API는 mixin(...) 하나로 통일

  • DEV-024Composable Mixins — 조합 API는 mixin(Base, ...Mixins)와 mixin(...Mixins) 두 형태만 쓰고, 항상 함께 필요한 Mixin은 상위 Mixin 안에서 조합해 사용처가 선행 Mixin을 반복해서 적지 않게 한다. 위반 판별: 사용처가 Position, LinearPhysics처럼 선행 Mixin을 매번 나열한다.

태그: #mixin #ComposableMixins

외부에서 알아야 할 조합 문법은 두 형태뿐이다.

// Base Class + Mixins → 최종 Class
mixin(BaseClass, MixinA, MixinB)

// Mixins만 → Composite Mixin
mixin(MixinA, MixinB)

Mixin 자체 정의

const RectSize = Base =>
  class RectSize extends Base {
    constructor(...args) {
      super(...args);
      this.rect = {
        width: 0,
        height: 0
      };
    }
  };

Mixin이 다른 Mixin을 포함

const LinearPhysics = mixin(
  Position,

  Base => class LinearPhysics extends Base {
    constructor(...args) {
      super(...args);
      this.linear = {
        velocity: {
          x: 0,
          y: 0
        }
      };
    }

    updateLinear(dt) {
      this.position.x +=
        this.linear.velocity.x * dt;

      this.position.y +=
        this.linear.velocity.y * dt;
    }
  }
);

의미는 단순하다.

LinearPhysics
=
Position
+
LinearPhysics 자체 기능

여러 Mixin을 실제 Class에 적용

class Unit {}

class Projectile extends mixin(
  Unit,
  LinearPhysics
) {}

class Crate extends mixin(
  Unit,
  LinearPhysics,
  AngularPhysics,
  RectSize
) {}

LinearPhysics가 이미 Position을 포함하므로 최종 사용자는 prerequisite를 반복해서 적지 않는다.

4.3.구현 시 지켜야 할 최소 규칙

  • DEV-025Mixin Requirements · Dedupe · Super Chain — Mixin constructor는 super(...args)로 인자를 그대로 전달하고, 같은 Mixin은 함수 identity 기준으로 한 번만 적용하며, 조합으로 해결되지 않는 Host 필드·메서드 요구만 Requires.*로 검증하고, 같은 public method를 우연히 덮어쓰지 않는다. 위반 판별: Base constructor 시그니처를 가정하거나, 같은 Mixin이 두 번 적용되거나, super 체인 없이 메서드를 덮어쓴다.

태그: #MixinRequirements #DedupingMixin #SuperChain

규칙 내용
Base → Subclass Mixin은 Base를 받고 class extends Base를 반환한다.
super(...args) Mixin constructor를 정의하면 Base의 constructor signature를 가정하지 말고 인자를 그대로 전달한다.
Mixin Composition 항상 필요한 다른 capability는 Mixin 내부에서 다른 Mixin을 조합해 표현한다.
Deduplication 같은 Mixin이 여러 의존 경로에서 들어와도 한 번만 적용한다. 문자열 이름보다 Mixin 함수 identity를 기준으로 처리한다.
Host Requirement Mixin 조합으로 해결할 수 없는 Host 필드·타입·메서드 요구사항만 별도 Requires.* 검증 대상으로 둔다.
Silent Override 금지 우연히 같은 public method를 덮어쓰는 구조는 피한다. 의도적인 lifecycle/override 조합은 super 체인을 명시적으로 사용한다.
나쁜 예 — prerequisite를 매번 직접 나열
class Projectile extends mixin(
  Unit,
  Position,
  LinearPhysics
) {}
좋은 예 — Mixin 조합으로 prerequisite 압축
const LinearPhysics = mixin(
  Position,
  LinearPhysicsCore
);

class Projectile extends mixin(
  Unit,
  LinearPhysics
) {}

4.4.실제 분리 기준

  • DEV-026Mixin Granularity — Mixin은 실제로 따로 쓰이는 최소 capability 단위로만 나눈다. 위반 판별: 단독 사용처가 없는 Mixin이 있다.

태그: #MixinGranularity #IS_A_HAS_A_CAN_BE

Mixin은 “개념적으로 더 쪼갤 수 있다”는 이유로 나누지 않는다. 실제로 따로 사용하는 경우가 있는 최소 capability만 분리한다.

Position
RectSize
LinearPhysics
AngularPhysics

예를 들면:

// 위치만
class Marker extends mixin(
  Unit,
  Position
) {}

// 위치 + 사각형 크기
class Panel extends mixin(
  Unit,
  Position,
  RectSize
) {}

// 위치 + 선형 물리
class Projectile extends mixin(
  Unit,
  LinearPhysics
) {}

// 위치 + 선형 물리 + 각속도 물리
class Crate extends mixin(
  Unit,
  LinearPhysics,
  AngularPhysics
) {}

판단 기준 따로 실제 사용된다 → 별도 Mixin 유지. 항상 같이 필요하다 → 상위 Mixin이 하위 Mixin을 조합해서 압축. Host가 이미 소유한 객체가 필요하다 → 소유권은 Host에 두고 Requirement만 명시.

  • DEV-028Prettier · Single Formatting Authority — 관리 대상 JS·HTML(인라인 script/style 포함)·CSS·JSON·Markdown은 공통 Prettier 설정(100자·공백 4칸·세미콜론·작은따옴표·trailing comma all·중괄호 공백·화살표 인수 괄호·LF)으로 포맷팅하고, 스타일 검사 규칙을 ESLint에 중복 정의하지 않는다. 위반 판별: 대상 파일에 다른 포맷이 적용됐거나 서로 다른 포맷터가 충돌한다.
  • DEV-029ESLint Recommended · Inline Script Coverage — 브라우저 ESM에 ESLint recommended를 적용하고 HTML 안의 일반 JavaScript script도 실제로 검사하며, Node 도구 스코프와 브라우저 전역을 구별한다. 저장 시 가능한 ESLint fix를 적용한다. 위반 판별: HTML 내부 JS의 미정의 변수가 검출되지 않거나 브라우저·Node 전역이 무분별하게 섞인다.
  • DEV-030Incremental Formatting · Changed Files — 기존 저장소는 수정한 파일부터 해당 파일 전체를 포맷팅하고, PR CI는 변경된 관리 대상 파일의 Prettier 위반과 ESLint error에서 실패한다. warning은 보고만 하고 CI는 소스를 자동 수정하지 않는다. 위반 판별: 변경하지 않은 기존 파일 때문에 PR을 차단하거나 CI가 임의 커밋을 만든다.
  • DEV-031Generated Artifact Exclusion · Tooling Isolation — GLSL·WGSL·자동 생성 파일·외부 소스는 포맷터·린터에서 제외하고, HTML/JS 안의 셰이더 영역은 국소 ignore로 보존한다. 검사 도구는 프로젝트별 devDependencies와 lockfile로 고정하고 게임 실행·배포에 빌드를 추가하지 않는다. 위반 판별: 생성 자산이 재포맷되거나 검사 도구가 게임 런타임에 포함된다.

  • 대상: JS·MJS·CJS·HTML·HTM·CSS·JSON·MD·Markdown. ESLint는 JS·MJS·CJS와 HTML 내부 일반 JavaScript를 검사한다.

  • 별도 GLSL·WGSL, minified 파일, 자동 생성 자산과 외부 소스는 제외한다. 셰이더가 HTML/JS 안에 있으면 가능한 최소 영역만 ignore한다.
  • 변경 파일의 파일 전체를 포맷팅한다. 전체 레거시 저장소의 일괄 포맷팅은 별도 작업이다.
  • CI는 PR 변경 파일만 검사하며 ESLint warning은 통과한다. 검사 도구는 개발 전용으로만 설치하고 게임 빌드·런타임에 추가하지 않는다.

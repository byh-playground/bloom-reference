Development Rules

공통 개발 규칙

유지보수성과 확장성을 위한 비용 우선순위판. 특정 프로젝트에 종속되지 않는 구조·코딩 원칙.

개발 규칙 SSOTP0 → P1 → P2IS-A / HAS-A / CAN-BE

함께 읽기: AI 개발 규칙 · 의도·검색·동작 확정 · 공통 UI/UX 레퍼런스 · 공통 STAT 사전 · 절차적 지형 생성. 이 문서는 구조 원칙을, 각 전문 문서는 정보 우선순위·수치 계약·생성 파이프라인을 소유한다.

정렬 기준
“얼마나 멋진 원칙인가”가 아니라 초기에 방치했을 때 나중에 고치는 비용이 얼마나 커지는가로 순서를 정한다. 즉, 구조를 뒤엎어야 하는 문제일수록 위에 둔다. 나쁜 예와 좋은 예를 바로 만들 수 없는 원칙은 우선순위를 낮춘다. 적용 장면이 명확하지 않다면 아직 추상적이라는 뜻이다.
우선순위 뜻 방치했을 때
P0 — 초기 구조 초기에 잡아야 하는 구조 결정 데이터 구조·API·의존성 전체를 다시 뜯어야 한다
P1 — 일상 개발 기능 추가·수정 때 매우 자주 마주치는 규칙 변경 범위가 넓어진다
P2 — 누적 부채 즉시 치명적이지 않은 정리 규칙 코드베이스가 서서히 굳고 유지보수 비용이 커진다

1.P0 — 초기에 반드시 잡기

초기 설계를 잘못하면 나중에 단순 리팩터링이 아니라 데이터 구조와 호출 관계를 다시 설계해야 하는 항목들이다.

1.1.하나의 상태에는 하나의 진실과 하나의 소유자

  • DEV-001P0같은 의미의 상태·공식·판정 로직은 한 곳에서만 정의하고, 그 상태를 생성·수정·삭제하는 주체는 1개만 둔다. 위반 판별: 같은 필드를 2곳 이상에서 대입하거나 같은 공식이 2개 이상 모듈에 있다.

태그: #SSOT #SingleOwnership #SingleWriter

빈도: 매우 높음 · 나중 수정비용: 매우 큼

같은 의미의 상태·공식·판정 로직을 여러 곳에서 따로 관리하지 않는다. mutable state는 누가 생성·수정·삭제하는지 하나로 정한다.

나쁜 예
unit.hp -= damage;
hud.hp = unit.hp;
network.hp = unit.hp;

// 다른 곳에서도 각각 hp 수정
hud.hp -= 10;
좋은 예
unit.applyDamage(damage);

// HUD/Network는 unit의 결과를 읽거나
// unit이 발행한 상태 변화만 구독

1.2.Checkbox 상태와 Radio 상태를 구조적으로 구분

  • DEV-002P0동시에 성립할 수 있는 상태는 독립 boolean으로, 상호배타적인 택 1 상태는 enum/state machine으로 정의한다. 위반 판별: 서로 배타적이어야 하는 boolean 필드가 2개 이상 있다.

태그: #StateMachine #MakeIllegalStatesUnrepresentable

빈도: 높음 · 나중 수정비용: 매우 큼

동시에 성립 가능한 상태는 flag로, 상호배타적인 택 1 상태는 enum/state machine으로 정의한다. 택 1 상태를 여러 boolean을 켜고 끄는 방식으로 구현하지 않는다.

나쁜 예
isIdle = false;
isMoving = true;
isAttacking = true;
isStunned = true;

존재하면 안 되는 조합이 구조적으로 가능하다.

좋은 예
state = UnitState.MOVING;

isSelected = true;
isPoisoned = true;

Radio 상태는 하나만, Checkbox 상태는 독립 flag로 둔다.

1.3.관계의 종류에 따라 구현 방식을 구분한다

  • DEV-003P0객체 관계를 IS-A(상속)·HAS-A(composition)·CAN-BE(mixin/trait)로 먼저 구분하고 그 관계에 맞는 구현을 쓴다. CAN-BE capability는 자기 상태와 로직을 mixin이 직접 소유하고, Host가 이미 소유한 HAS-A 객체를 다시 만들지 않는다. 위반 판별: 기능 조합을 상속 계층으로 표현했거나, 단순 capability를 component 배열·registry를 거쳐 호출하거나, mixin이 Host 소유 객체를 중복 생성한다.

태그: #IS_A_HAS_A_CAN_BE #CompositionOverInheritance #Mixin #CapabilityOwnership

빈도: 높음 · 나중 수정비용: 매우 큼

모든 재사용을 composition 하나로 해결하지 않는다. 객체 관계의 의미를 먼저 구분하고, 그 의미에 가장 자연스러운 구현 방식을 사용한다.

관계 질문 기본 구현 대표 예
IS-A “이것은 본질적으로 저것의 한 종류인가?” 상속 / 공통 base type Dragon IS-A Unit
HAS-A “이것이 독립적인 부품/객체를 가지고 있는가?” Composition Unit HAS-A Weapon
CAN-BE “필요하면 이 능력/성질을 가질 수 있는가?” Mixin / Trait / capability method injection Unit CAN-BE Jumpable

핵심: Composition은 기본값이 아니라 HAS-A 관계의 기본값이다. CAN-BE까지 전부 component 배열로 밀어 넣으면 호출 깊이와 간접성이 커져 코드가 오히려 비직관적일 수 있다.

IS-A → 상속

도메인적으로 정말 같은 종류이고, base contract가 작고 안정적일 때만 사용한다.

나쁜 예 — 기능을 상속 계층으로 표현
FlyingPoisonEliteRangedUnit
  extends FlyingRangedUnit
    extends RangedUnit
      extends Unit
좋은 예 — 본질적인 타입 관계만 상속
class Unit {
  update() {}
  destroy() {}
}

class Dragon extends Unit {
  // Dragon도 본질적으로 Unit
}

HAS-A → Composition

독립적인 상태와 생명주기를 가진 부품, 교체 가능한 객체, 별도 소유권이 필요한 경우 composition을 사용한다.

나쁜 예 — 부품을 상속으로 표현
class SwordUnit extends Unit {
  // Sword 때문에 새로운 Unit 타입 생성
}
좋은 예 — 부품을 소유
class Unit {
  constructor(weapon) {
    this.weapon = weapon;
  }

  attack(target) {
    this.weapon.attack(target);
  }
}

CAN-BE → Mixin / Trait

객체의 본질적인 타입도 아니고, 독립 부품을 소유하는 것도 아니지만 선택적으로 “할 수 있는 것”이라면 mixin/trait 계열이 더 직접적일 수 있다.

나쁜 예 — 모든 능력을 component 배열 순회로 처리
unit.components = [
  movement,
  jump,
  shield,
  poison,
  capture
];

for (const c of unit.components) {
  c.update?.(dt);
}

// 실제 jump 호출 위치를 찾으려면
// registry → component → handler를 계속 따라가야 함
좋은 예 — 능력이 객체 API에 직접 드러남
const Jumpable = Base => class extends Base {
  jump() {
    this.velocity.z = this.jump.power;
  }
};

class Unit {
  move() {}
}

class Flea extends Jumpable(Unit) {}

flea.jump();

이 방식의 장점은 호출부가 unit.jump()처럼 평평하고 직관적이라는 것이다. 능력 하나를 실행하기 위해 components[]를 찾고 순회하거나 중간 registry를 통과할 필요가 없다.

CAN-BE를 Composition으로 써도 되는 경우

Mixin을 무조건 쓰는 것도 아니다. 다음 조건이면 composition이 더 적합하다.

  • 능력 자체가 큰 상태를 가진다.
  • 별도의 lifecycle이 있다.
  • 런타임에 교체/탈착되어야 한다.
  • 동일 capability를 여러 구현으로 갈아끼워야 한다.
나쁜 예 — Unit이 capability 내부 구조를 직접 소유/중계
class Unit {
  constructor(jumpAbility) {
    this.jumpAbility = jumpAbility;
  }

  jump() {
    this.jumpAbility.execute(this);
  }
}

Unit이 Jump의 component 존재와 호출 방법을 알아야 하므로 상태·로직 소유권이 분산된다.

좋은 예 — 단순 capability는 Mixin이 직접 상태와 로직을 소유
const Jumpable = Base => class extends Base {
  constructor(...args) {
    super(...args);

    this.jump.power = 12;
    this.jump.cooldown.durationMs = 800;
    this.jump.cooldown.leftMs = 0;
  }

  jump() {
    if (this.jump.cooldown.leftMs > 0) return false;

    this.velocity.z = this.jump.power;
    this.jump.cooldown.leftMs = this.jump.cooldown.durationMs;
    return true;
  }

  updateJump(dt) {
    this.jump.cooldown.leftMs = Math.max(
      0,
      this.jump.cooldown.leftMs - dt
    );
  }
};

class Unit {
  move() {}
}

class Flea extends Jumpable(Unit) {}

flea.jump();

점프 자체가 하나의 capability이므로 별도 JumpAbility component를 만들지 않는다. 점프 전용 상태와 로직은 Jumpable 안에 바로 둔다.

규칙: CAN-BE capability는 가능한 한 자기 상태와 로직을 Mixin/Trait 자체에 직접 가진다. 단순 capability 안에 또 capability용 component를 만들어 한 단계 더 감싸지 않는다.

Jumpable Mixin
 ├─ jump.power
 ├─ jump.cooldown.durationMs
 ├─ jump()
 └─ updateJump()

// Jumpable 안에 JumpAbility를 또 넣지 않음

Mixin이 커져서 내부를 다시 component로 쪼개고 싶어질 정도라면, 우선 그 Mixin 자체가 여러 capability를 떠안고 있는지 본다. 그렇다면 하위 composition을 추가하기보다 capability를 더 작은 Mixin/Trait으로 분리한다.

나쁜 예 — 비대해진 Mixin 안에 다시 내부 component 계층 생성
Jumpable
 ├─ JumpPhysics
 ├─ JumpCooldown
 ├─ JumpLanding
 └─ JumpEffects

좋은 방향 — 독립 capability로 분리

Unit
 ├─ Jumpable
 ├─ Landable
 └─ AirControl

각 capability가 자기 상태와 로직을 직접 소유한다.

Unit
 ├─ weapon               ← Unit이 정당하게 소유하는 HAS-A composition
 │    └─ Sword
 │
 └─ SwordTechnique Mixin ← sword 전용 CAN-BE capability
      └─ base.weapon 참조

이미 Host가 정당하게 소유하는 composition이 있다면 Mixin이 그것을 참조해 특수 기능을 정의할 수 있다. 이 경우 Mixin이 weapon 자체를 다시 소유하거나 중복 생성하지 않는다.

나쁜 예 — 같은 하위 상태를 이중 소유
class Unit {
  constructor() {
    this.weapon = new Sword();
  }
}

const SwordTechnique = Base => class extends Base {
  constructor(...args) {
    super(...args);
    this.sword = new Sword(); // 중복 소유
  }

  parry() {
    this.sword.parry();
  }
};
좋은 예 — 기존 HAS-A를 이용해 새로운 capability를 추가
class Unit {
  constructor(weapon) {
    this.weapon = weapon;
  }
}

const SwordMastery = Base => class extends Base {
  constructor(...args) {
    super(...args);
    this.swordComboStep = 0;
  }

  iaiSlash(target) {
    if (!(this.weapon instanceof Sword)) {
      throw new Error("Sword required");
    }

    const damage =
      this.weapon.getBaseDamage() * 2.5;

    this.weapon.consumeDurability(1);
    target.takeDamage(damage);

    this.swordComboStep = 0;
  }

  advanceSwordCombo() {
    this.swordComboStep =
      (this.swordComboStep + 1) % 3;
  }
};

class SwordMaster extends SwordMastery(Unit) {}

const unit = new SwordMaster(new Sword());
unit.iaiSlash(enemy);

SwordMastery는 weapon.attack()을 다시 감싸지 않는다. 기존 weapon을 재료로 사용해 발도베기·콤보처럼 Unit에 원래 없던 capability를 추가하고, 그 capability 전용 상태도 Mixin이 소유한다.

즉 HAS-A의 소유권은 그대로 유지하고, CAN-BE는 그 소유 객체를 재료로 사용해 기존 객체에는 없던 새로운 능력·규칙·상태를 추가한다. 단순 forwarding/wrapping만 하는 Mixin은 만들지 않는다.

Flat API와 함께 중요한 것은 Single Ownership이다. Mixin은 자신이 추가한 capability의 상태와 로직을 직접 소유한다. 기존 HAS-A 객체를 활용할 수는 있지만 그 객체의 소유권을 복제하지 않는다. Mixin이 비대해져 내부 계층이 필요해지면 먼저 capability 분리를 검토한다.

결정 순서

1. 본질적으로 같은 종류인가?
   → YES: IS-A → 작은 base type / 상속

2. 독립적인 객체·상태·생명주기를 소유하는가?
   → YES: HAS-A → Composition

3. 선택적으로 가질 수 있는 능력/성질인가?
   → YES: CAN-BE → Mixin / Trait 우선 검토

4. CAN-BE 자체가 단순한 capability인가?
   → YES: Mixin/Trait이 상태와 로직을 직접 소유
   → 내부에 같은 의미의 Ability component를 또 만들지 않음

5. Mixin이 너무 커져 내부 하위 계층이 필요해졌는가?
   → YES: 먼저 capability 자체를 더 작은 Mixin/Trait으로 분리
   → 내부 component nesting은 최후 수단

6. CAN-BE가 기존 HAS-A 객체를 이용하는가?
   → YES: 기존 owner의 객체를 참조해 새 capability를 정의
   → 객체 소유권은 기존 owner에 그대로 유지

7. 외부 호출은?
   → 의미 있는 Flat API로 노출
   → 같은 상태/객체의 owner는 끝까지 하나만 유지

1.4.이름이 아니라 능력으로 분기

  • DEV-004P0로직 분기는 유닛명·타입명·ID·맵 이름이 아니라 capability 보유 여부와 데이터로 한다. 위반 판별: type === "..." 또는 맵 이름 비교로 행동이 갈린다.

태그: #CapabilityBasedDesign

빈도: 매우 높음 · 나중 수정비용: 큼

특정 유닛명·타입명·ID가 로직 분기의 핵심이 되지 않게 한다.

보스·맵도 같다. 돌진·소환·단계 전환은 각각 재사용 가능한 capability로 구현하고, 보스별 구성은 능력 조합과 설정으로 표현한다. 맵 이름을 검사해 충돌·스폰을 갈라 놓지 말고 지형 데이터와 이동·스폰 규약을 사용한다. 단, 실제로 행동이 다른 경우에는 새 capability가 필요하며 모든 차이를 거대한 설정 분기로 숨기지 않는다.

나쁜 예

    jump();
}
좋은 예

    unit.jump();
}

나쁜 예

// 같은 damage를 강제로 공유

1.6.Core가 구체 기술을 직접 알지 않게

태그: #DependencyInversion #SeparationOfConcerns

빈도: 중간 · 나중 수정비용: 매우 큼

1.7.Signal은 사건을 발생시키는 당사자가 소유

  • DEV-007P0"내게 이런 일이 일어났다"는 통지는 발생 주체가 소유한 public Signal로 노출하고, 발신자는 구독자를 모른다. 위반 판별: 전역 이벤트 버스에 문자열 이벤트명으로 emit하거나, 발생 주체가 점수·VFX·UI 시스템을 직접 호출한다.

태그: #SignalPattern #SignalOwnership

빈도: 높음 · 나중 수정비용: 큼

“내게 이런 일이 일어났다”는 통지는 발생 주체의 public signal로 노출한다. 발신자는 subscriber를 알지 않는다.

나쁜 예
globalSignals.emit("unitDied", unit);

// 또는
unit.die() {
  scoreSystem.addKill(this);
  vfxSystem.spawn(this);
  ui.remove(this);
}
좋은 예
class Unit {
  constructor() {
    this.onDied = new Signal();
  }

  die() {
    this.onDied.emit({
      unitId: this.id,
      position: this.position
    });
  }
}

unit.onDied.on(scoreSystem.handle);
unit.onDied.on(vfxSystem.handle);
의도 방식
무언가 해줘 직접 호출 / Command
값을 알려줘 Query
내게 이런 일이 일어났다 그 당사자가 소유한 Signal

2.6.Behavior는 코드, Parameters는 데이터

  • DEV-013P1behavior는 코드로, 그 behavior의 수치(시간·거리·개수)는 설정 데이터로 둔다. 설정에 없는 독립 행동을 임의 플래그로 흉내 내지 않는다. 위반 판별: 타입별 if문 안에 수치 상수가 박혀 있다.

// 개념 예시. 특정 런타임 API나 공통 기본값을 강제하지 않는다.

3.6.긴 접두어 변수보다 의미 단위 계층으로 상태를 묶는다

  • DEV-020P2같은 기능에 속하는 상태는 접두어 반복 대신 기능 단위 namespace 객체로 묶고, 단위는 leaf 이름(Ms, Rad, Px)에 남긴다. 계층은 기능·소유권·하위 개념을 구분하는 데 필요한 만큼만 만든다. 위반 판별: 같은 접두어 필드가 3개 이상 평평하게 나열되거나, 의미 없는 wrapper 계층이 있다.

태그: #HierarchicalNaming #SemanticNamespace #ScopeVisibleNaming

빈도: 매우 높음 · 나중 수정비용: 중간

서로 같은 기능에 속하는 상태를 jump.cooldown.leftMs, jump.power, jumpDurationMs처럼 평평한 이름으로 늘어놓기보다, 기능 단위 namespace 아래에 계층적으로 묶어 스코프와 소유권을 코드 모양 자체로 드러낸다.

나쁜 예 — 접두어를 반복하는 Flat Naming
this.jumpPower = 12;
this.jumpCooldownDurationMs = 800;
this.jumpCooldownLeftMs = 0;
this.jumpDurationMs = 250;

jumpDurationMs처럼 기능명과 하위 의미를 변수명에 계속 이어 붙이면, 필드가 늘수록 이름이 길어지고 스코프와 계층이 문자열 접두어에만 의존하게 된다.

좋은 예 — 기능 단위 계층
this.jump = {
  power: 12,

  cooldown: {
    durationMs: 800,
    leftMs: 0
  },

  durationMs: 250
};

Jump.*만 봐도 어느 기능의 상태인지 바로 알 수 있고, 하위 상태도 의미 단위로 묶인다.

단위까지 계층 안에서 명확하게

jump.cooldown.durationMs
jump.cooldown.leftMs

linear.velocity.x
linear.velocity.y

angular.velocity
angular.angleRad

rect.width
rect.height

단위가 중요한 값은 Ms, Rad, Px처럼 leaf 이름에 단위를 남긴다. 계층을 만든다고 단위 정보를 숨기지 않는다.

Mixin 소유권과도 맞춘다

Mixin이 소유하는 상태는 해당 Mixin의 namespace 아래에 둔다.

const Jump = Base =>
  class Jump extends Base {
    constructor(...args) {
      super(...args);

      this.jump = {
        power: 12,
        cooldown: {
          durationMs: 800,
          leftMs: 0
        }
      };
    }

    jump() {
      if (this.jump.cooldown.leftMs > 0) {
        return false;
      }

      this.velocity.z = this.jump.power;
      this.jump.cooldown.leftMs =
        this.jump.cooldown.durationMs;

      return true;
    }
  };

이렇게 하면 상태 이름만 봐도 어느 capability가 소유하는 상태인지가 드러난다.

과도한 계층은 피한다

나쁜 예 — 의미 없이 너무 깊은 계층
Unit.State.Physics.Linear
  .Movement.Velocity.Current.x
좋은 예 — 실제 의미 경계까지만
linear.velocity.x
jump.cooldown.leftMs
Weapon.reload.leftMs

규칙: 계층은 기능/소유권/하위 개념을 구분하는 데 필요한 만큼만 만든다. 단순히 “정리돼 보이게” 하기 위한 wrapper 계층은 추가하지 않는다.

판단 기준 같은 접두어가 2~3개 이상 반복되기 시작한다 → namespace 후보. 같은 기능의 상태가 함께 생성·변경·삭제된다 → 같은 namespace에 묶기. 서로 다른 owner의 상태라면 같은 namespace에 억지로 넣지 않기.

  • DEV-022P2특수 케이스 분기가 반복되면 분기를 덧대지 않고 공통 capability/contract로 구조를 교체한다. 위반 판별: 같은 함수에 특수 케이스 else-if가 4개 이상이다.

태그: #ReplaceNotLayer #RefactorForChangeability

나쁜 예

// 반복되는 특수 케이스의

4.JavaScript Mixin 구현 규약

일반 원칙과 달리 이 섹션은 JavaScript에서 실제로 사용할 Mixin 형태를 구체화한다. 구현은 표준 JavaScript의 Subclass Factory 패턴을 기반으로 하고, 프로젝트에서는 읽기 쉬운 mixin(...) 헬퍼 하나만 공개한다.

핵심 공식 Mixin = Base Class → Base를 extends한 Subclass를 반환하는 함수 Mixin끼리도 조합할 수 있고, 조합된 결과 역시 다시 Mixin으로 사용한다.

4.1.별도 Mixin 전용 Base를 만들지 않는다

  • DEV-023Mixin은 Base를 받아 class extends Base를 반환하는 Subclass Factory로 만들고, Mixin 전용 공통 Base 클래스를 두지 않는다. 위반 판별: MixinBase 같은 클래스를 상속해야만 mixin을 쓸 수 있다.

태그: #SubclassFactory #NoMixinBase

나쁜 예
class MixinBase {}
class Unit extends MixinBase {}

Mixin 사용을 위해 불필요한 공통 상속축이 생긴다.

좋은 예 — 공식적인 Subclass Factory 형태
const Position = Base =>
  class Position extends Base {
    constructor(...args) {
      super(...args);
      this.position = {
        x: 0,
        y: 0
      };
    }
  };

Mixin은 어떤 기존 Base Class에도 적용 가능하다.

4.2.공개 조합 API는 mixin(...) 하나로 통일

  • DEV-024조합 API는 mixin(Base, ...Mixins)와 mixin(...Mixins) 두 형태만 쓰고, 항상 함께 필요한 Mixin은 상위 Mixin 안에서 조합해 사용처가 선행 Mixin을 반복해서 적지 않게 한다. 위반 판별: 사용처가 Position, LinearPhysics처럼 선행 Mixin을 매번 나열한다.

태그: #mixin #ComposableMixins

외부에서 알아야 할 조합 문법은 두 형태뿐이다.

// Base Class + Mixins → 최종 Class
mixin(BaseClass, MixinA, MixinB)

// Mixins만 → Composite Mixin
mixin(MixinA, MixinB)

Mixin 자체 정의

const RectSize = Base =>
  class RectSize extends Base {
    constructor(...args) {
      super(...args);
      this.rect = {
        width: 0,
        height: 0
      };
    }
  };

Mixin이 다른 Mixin을 포함

const LinearPhysics = mixin(
  Position,

  Base => class LinearPhysics extends Base {
    constructor(...args) {
      super(...args);
      this.linear = {
        velocity: {
          x: 0,
          y: 0
        }
      };
    }

    updateLinear(dt) {
      this.position.x +=
        this.linear.velocity.x * dt;

      this.position.y +=
        this.linear.velocity.y * dt;
    }
  }
);

의미는 단순하다.

LinearPhysics
=
Position
+
LinearPhysics 자체 기능

여러 Mixin을 실제 Class에 적용

class Unit {}

class Projectile extends mixin(
  Unit,
  LinearPhysics
) {}

class Crate extends mixin(
  Unit,
  LinearPhysics,
  AngularPhysics,
  RectSize
) {}

LinearPhysics가 이미 Position을 포함하므로 최종 사용자는 prerequisite를 반복해서 적지 않는다.

4.3.구현 시 지켜야 할 최소 규칙

  • DEV-025Mixin constructor는 super(...args)로 인자를 그대로 전달하고, 같은 Mixin은 함수 identity 기준으로 한 번만 적용하며, 조합으로 해결되지 않는 Host 필드·메서드 요구만 Requires.*로 검증하고, 같은 public method를 우연히 덮어쓰지 않는다. 위반 판별: Base constructor 시그니처를 가정하거나, 같은 Mixin이 두 번 적용되거나, super 체인 없이 메서드를 덮어쓴다.

태그: #MixinRequirements #DedupingMixin #SuperChain

규칙 내용
Base → Subclass Mixin은 Base를 받고 class extends Base를 반환한다.
super(...args) Mixin constructor를 정의하면 Base의 constructor signature를 가정하지 말고 인자를 그대로 전달한다.
Mixin Composition 항상 필요한 다른 capability는 Mixin 내부에서 다른 Mixin을 조합해 표현한다.
Deduplication 같은 Mixin이 여러 의존 경로에서 들어와도 한 번만 적용한다. 문자열 이름보다 Mixin 함수 identity를 기준으로 처리한다.
Host Requirement Mixin 조합으로 해결할 수 없는 Host 필드·타입·메서드 요구사항만 별도 Requires.* 검증 대상으로 둔다.
Silent Override 금지 우연히 같은 public method를 덮어쓰는 구조는 피한다. 의도적인 lifecycle/override 조합은 super 체인을 명시적으로 사용한다.
나쁜 예 — prerequisite를 매번 직접 나열
class Projectile extends mixin(
  Unit,
  Position,
  LinearPhysics
) {}
좋은 예 — Mixin 조합으로 prerequisite 압축
const LinearPhysics = mixin(
  Position,
  LinearPhysicsCore
);

class Projectile extends mixin(
  Unit,
  LinearPhysics
) {}

4.4.실제 분리 기준

  • DEV-026Mixin은 실제로 따로 쓰이는 최소 capability 단위로만 나눈다. 위반 판별: 단독 사용처가 없는 Mixin이 있다.

태그: #MixinGranularity #IS_A_HAS_A_CAN_BE

Mixin은 “개념적으로 더 쪼갤 수 있다”는 이유로 나누지 않는다. 실제로 따로 사용하는 경우가 있는 최소 capability만 분리한다.

Position
RectSize
LinearPhysics
AngularPhysics

예를 들면:

// 위치만
class Marker extends mixin(
  Unit,
  Position
) {}

// 위치 + 사각형 크기
class Panel extends mixin(
  Unit,
  Position,
  RectSize
) {}

// 위치 + 선형 물리
class Projectile extends mixin(
  Unit,
  LinearPhysics
) {}

// 위치 + 선형 물리 + 각속도 물리
class Crate extends mixin(
  Unit,
  LinearPhysics,
  AngularPhysics
) {}

판단 기준 따로 실제 사용된다 → 별도 Mixin 유지. 항상 같이 필요하다 → 상위 Mixin이 하위 Mixin을 조합해서 압축. Host가 이미 소유한 객체가 필요하다 → 소유권은 Host에 두고 Requirement만 명시.
